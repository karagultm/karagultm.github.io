OOP: The Four Pillars, Access Modifiers, Abstract Classes and Interfaces

Programming 101, Part 4

Part 3 put structured, functional and object-oriented programming side by side. There I said that OOP splits a program into objects that keep data and the code working on that data together. This post opens up that part: how are objects designed, and what rules do they follow?

In OOP interviews the questions usually come from the same place. The four pillars, the difference between overloading and overriding, access modifiers, and the choice between an abstract class and an interface. All examples are in Java, because most of these questions are asked through Java and a few version-dependent details show up there.

Below I first cover the difference between a class and an object, then the four pillars one by one. After that come access modifiers, the abstract class vs. interface question and a short note on composition. At the end there are common interview questions with short answers.

1. Class and object

A Class is a template that defines what data an object holds and what it can do. An Object is a concrete instance created from that template, and it takes up space in memory. That is why an object is also called an Instance.

A class is like a house plan, and objects are the houses built from it. There is one plan, and any number of houses can be built from it. Each house can have different wall colors, but the room layout is the same.

public class Account {
    String owner;        // state
    double balance;

    void deposit(double amount) {   // behavior
        balance += amount;
    }
}

Account a = new Account();   // a new object in memory
Account b = new Account();   // a separate object, separate balance

When new is called, the object is created on the heap and the Constructor runs. A constructor has the same name as the class and no return type. If a class has no constructor at all, the compiler adds a no-argument one. A constructor in Java does the job that __init__ does in Python.

2. Encapsulation

Encapsulation means keeping an object’s data so that it cannot be changed directly from outside, and letting that data be accessed only through the object’s own methods.

A bank account shows this well. Nobody edits the balance by hand. To deposit or withdraw money you go to the counter, and the counter applies rules: negative amounts are rejected, and you cannot withdraw more than the balance.

public class Account {
    private double balance;   // not visible from outside

    public void deposit(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Amount must be positive");
        balance += amount;
    }

    public void withdraw(double amount) {
        if (amount > balance) throw new IllegalStateException("Insufficient funds");
        balance -= amount;
    }

    public double getBalance() { return balance; }   // reading allowed, writing not
}

There is deliberately no setBalance method here. Encapsulation is often explained as “make the fields private and write a getter and a setter for each”. But adding an unconditional setter to every field opens the data to the outside again. The real goal is to keep the rules that stop the object from reaching an invalid state in one place. If the balance only changes through deposit and withdraw, a bad value can only come from those two methods.

The second benefit is that the internals can change. If the balance is later stored as a long in cents instead of a double, outside code does not notice. Money calculations use BigDecimal or integers rather than double. I used double here only to keep the example short.

3. Inheritance

Inheritance is a class taking over the fields and methods of another class. The class that passes them on is the Superclass (or parent), the one that receives them is the Subclass (or child). In Java this is done with extends.

Consider a vehicle class. A car and a truck are both vehicles, and both have a plate number and a speed. That shared part is written once in the vehicle, and the subclasses only add what is different.

class Vehicle {
    protected String plate;
    protected int speed;

    void accelerate(int amount) { speed += amount; }
}

class Truck extends Vehicle {
    private int loadCapacity;   // only trucks have this

    void load(int tons) { /* ... */ }
}

Truck t = new Truck();
t.accelerate(20);   // method inherited from Vehicle

Inheritance models an is-a relationship. If the sentence “a truck is a vehicle” is true, inheritance fits. If the sentence sounds forced, for example “a customer is an address”, the wrong tool has probably been chosen.

In Java a class can extend only one class. This is called Single Inheritance. The reason is the Diamond Problem: if two superclasses define a method with the same name in different ways, it is unclear which one the subclass should use. A class can, however, implement as many interfaces as it needs. I come back to this in section 7.

A few more rules:

  • Constructors are not inherited. A subclass constructor calls the superclass constructor with super(...) on its first line. If it does not, the compiler inserts a no-argument super().
  • A class marked final cannot be extended. String is the well-known example.
  • Every class implicitly descends from Object. toString, equals and hashCode come from there.

4. Polymorphism

Polymorphism is the same call producing different behavior on different objects. The “power” button on a universal remote works this way. The button is the same, but pressed at the TV it brings up a picture, and pressed at the air conditioner it brings cold air.

Java does this in two ways, and interviewers almost always ask about the difference.

Overloading: compile-time polymorphism

Overloading means writing methods in the same class with the same name but different parameter lists. The number, types or order of the parameters must differ. Changing only the return type is not enough, and the compiler reports it as an error.

class Calculator {
    int add(int a, int b)          { return a + b; }
    int add(int a, int b, int c)   { return a + b + c; }
    double add(double a, double b) { return a + b; }
    // long add(int a, int b) { ... }  compile error: only the return type differs
}

The compiler decides which method runs by looking at the argument types at compile time. That is why overloading is called Compile-time (Static) Polymorphism.

Overriding: runtime polymorphism

Overriding is a subclass rewriting a superclass method with the same signature.

class Animal {
    String sound() { return "..."; }
}

class Cat extends Animal {
    @Override
    String sound() { return "Meow"; }
}

class Dog extends Animal {
    @Override
    String sound() { return "Woof"; }
}

Animal a = new Cat();          // reference type Animal, object Cat
System.out.println(a.sound()); // "Meow"

The variable a has type Animal, but the method that runs is Cat’s. The decision is made at runtime, based on the object’s actual type. This is called Dynamic Method Dispatch or Runtime Polymorphism. Code that loops over a List<Animal> and calls sound() on each element keeps working unchanged when a new kind of animal is added.

@Override is not required, but it is worth writing. If the signature has a typo, say Sound(), the compiler reports that the method does not override anything. Without the annotation a new method quietly appears instead.

The rules of overriding:

  • The method name and parameter list must be the same. The return type can be the same or a subtype of it (Covariant Return Type).
  • Access cannot be narrowed. A method that is public in the superclass cannot become protected in the subclass.
  • private, static and final methods cannot be overridden. A private method is not visible to the subclass. A static method with the same signature in the subclass does not override the one in the superclass, it hides it (Method Hiding). Which one runs is decided at compile time from the reference type.
  • Fields are not overridden. A field with the same name in the subclass hides the superclass field, and which one is read also depends on the reference type.
Overloading Overriding
Where In the same class (or a subclass) In a subclass
Signature Same name, different parameters Same name and parameters
Decided At compile time At runtime
Based on Reference and argument types The object’s actual type
static methods Can be overloaded Cannot be overridden, only hidden

5. Abstraction

Abstraction means showing what something does while hiding how it does it. The user only sees the interface they need.

Driving a car needs a steering wheel, an accelerator and a brake. You do not need to know how fuel is injected in the engine when you press the pedal. If the engine changes, say from petrol to electric, the pedals stay the same.

interface PaymentMethod {
    void pay(double amount);
}

class CardPayment implements PaymentMethod {
    public void pay(double amount) { /* card check, bank request */ }
}

class BankTransfer implements PaymentMethod {
    public void pay(double amount) { /* IBAN check, transfer */ }
}

void completeOrder(PaymentMethod method, double amount) {
    method.pay(amount);   // does not know which method it is, and does not need to
}

completeOrder only knows that a pay method exists. When a new payment method is added later, this method does not change.

Encapsulation and abstraction are often confused, because both hide something. Encapsulation locks data and the rules protecting it inside the class, and its question is “who can touch this data, and how?” Abstraction works at the design level and answers “which operations do I show to the outside, and which details do I hide?” Java has two tools for abstraction: abstract classes and interfaces.

6. Access modifiers

An Access Modifier decides which code can see a class, field or method. Java has four levels. One of them is not a keyword. It is the default level that applies when nothing is written.

Modifier Same class Same package Subclass in another package Other code in another package
public Yes Yes Yes Yes
protected Yes Yes Yes (through inheritance) No
default (nothing written) Yes Yes No No
private Yes No No No

A house is a useful picture. The name on the door is public, anyone can see it. The PIN of your bank card is private, only the owner knows it, not even their child. Default is the apartment building: everyone living in the same building knows, people from outside do not. protected covers the building and the family. A child living in a different building can access it too.

Default (package-private)

When no modifier is written, the member is open only to classes in the same package. This is called Package-Private. Notes written with C# in mind often skip this level, because C# has a different default (private for class members). In Java, forgetting to write private opens the field to the whole package.

A top-level (non-nested) class can only be public or default. private class and protected class are only valid for classes declared inside another class.

The package rule of protected

protected is often summarized as “only subclasses can access it”. In Java that is incomplete. Every class in the same package can access a protected member, even if it is not a subclass. So protected gives everything default gives, plus subclasses in other packages.

There is a limit for a subclass in another package, too. It accesses the protected member through itself (or through a reference of its own type). It cannot create a separate object of the superclass type and reach into its protected field.

package bank;
public class Account {
    protected double balance;
}

package promo;               // different package
import bank.Account;

public class SavingsAccount extends Account {
    void addInterest() {
        balance *= 1.02;             // valid: its own inherited field

        Account other = new Account();
        // other.balance = 0;        compile error: a different Account object
    }
}

The subclass can only reach the part it inherited. It cannot look inside another object of the parent type.

Which one in practice?

Fields are almost always private. Methods are opened as far as needed: operations offered to the outside are public, helpers inside the package are default, and extension points that subclasses are expected to override are protected. Starting from the most restrictive level and opening up when needed is easier than trying to close something later. Once something is public, it is not always possible to find and change all the code that uses it.

7. Abstract class vs. interface

Both define gaps that subclasses must fill, and neither can be instantiated directly with new. The differences have changed across Java versions. The claim “an interface can only have abstract methods”, which still appears in older notes, has not been true since Java 8.

Abstract class

An Abstract Class is declared with the abstract keyword. It can contain abstract methods without a body as well as normal methods. It can have fields, constructors and members at any access level. A class can extend only one abstract class.

abstract class Employee {
    private final String name;
    protected Employee(String name) { this.name = name; }   // can have a constructor

    abstract double calculatePay();                           // subclass fills this in

    String payrollLine() {                                    // shared, ready-made code
        return name + ": " + calculatePay();
    }
}

class FullTime extends Employee {
    FullTime(String name) { super(name); }
    double calculatePay() { return 40000; }
}

An abstract class has a constructor, but new Employee(...) cannot be written. The constructor runs when a subclass calls it with super(...), to set up the shared fields. A class with an abstract method must be abstract. The reverse is not required: a class with no abstract methods can also be declared abstract just to prevent instantiation. A subclass that is not itself abstract must implement every abstract method.

Interfaces and version changes

An Interface is a contract that defines the operations a class will offer. A class can implement more than one interface. An interface has no object state (instance fields). Every variable declared in it is implicitly public static final, which means a constant. It has no constructor either.

On the method side, the following were added across versions:

Version What an interface can contain
Java 7 and earlier Only abstract methods (implicitly public abstract) and constants
Java 8 default methods (with a body, implementing classes may override them) and static methods
Java 9 private methods and private static methods 
interface Notifier {
    void send(String message);                    // abstract

    default void sendAll(List<String> messages) { // Java 8
        messages.forEach(m -> send(format(m)));
    }

    static Notifier silent() {                    // Java 8
        return message -> { };
    }

    private String format(String m) {             // Java 9
        return "[notice] " + m;
    }
}

default methods were added so that a new method could be added to an existing interface without breaking every class that implements it. stream(), added to Collection in Java 8, and forEach, added to Iterable, are examples. private methods exist so that several default methods can share code without exposing it.

Two details can come up in interviews:

  • A static method in an interface is not inherited by implementing classes. It is called with the interface name, Notifier.silent(). EmailNotifier.silent() does not compile.
  • If a class implements two interfaces with a default method of the same signature, the compiler reports an error. The class must override that method itself. To pick one from inside, it writes A.super.method(). This is how Java handles the diamond problem: behavior can be inherited, but when there is a conflict the class decides. State (fields) is never inherited from an interface.

Comparison

Abstract class Interface
Inheritance A class extends only one A class implements several
Fields Any instance fields Only public static final constants
Constructor Allowed Not allowed
Method bodies Always allowed default and static since Java 8, private since Java 9
Member access public, protected, default, private Methods are public by default, private is also allowed since Java 9
Relationship is-a: sharing a common root can-do: having a capability

When to choose which

An interface is chosen to describe a shared capability of classes that are not otherwise related. Comparable, Runnable and AutoCloseable are of this kind. A file and a database connection can both be closed, but they have no common ancestor. The contract a type offers to the outside is also usually defined as an interface, so the code that uses it is not tied to one concrete class.

An abstract class is chosen when closely related classes share state and code. If all subclasses have the same fields, a constructor must set them up, or protected helper methods are needed, an interface is not enough, because an interface cannot hold state.

The two can also be used together. In the Java library, List is an interface and AbstractList is an abstract class that partly implements it. Someone writing a new list extends AbstractList and fills in a few methods. The code using the list only knows about List.

8. Composition over inheritance

Composition is a class using another class’s behavior by holding it as a field rather than inheriting from it. The relationship is not is-a but has-a. “A car is an engine” is wrong, “a car has an engine” is right.

The “composition over inheritance” principle says that when sharing code, composition should be considered first. Inheritance ties the subclass tightly to the internal details of the superclass. A change in the superclass can break subclasses it never anticipated. The subclass also inherits every public method of the superclass, whether it wants them or not.

Java’s own library has a well-known example. java.util.Stack extends Vector. Because of that, methods that touch the middle of the stack, such as get(index) and add(index, element), can be called on a stack. The stack rule of “push and pop only at the top” is broken this way. The Java documentation now recommends the Deque interface and ArrayDeque for stacks.

class SafeStack<T> {
    private final Deque<T> items = new ArrayDeque<>();   // has-a

    void push(T e)    { items.push(e); }
    T pop()           { return items.pop(); }
    boolean isEmpty() { return items.isEmpty(); }
    // no access to the middle, because it was never exposed
}

This does not mean inheritance should never be used. When there is a real is-a relationship and the subclass can safely be used anywhere the superclass is expected, inheritance is the right tool. The trouble starts when inheritance is used only to avoid repeating code.

Interview questions

1. What are the four pillars of OOP? Encapsulation keeps data inside the class and lets it change only through methods. Inheritance is a class taking over the members of another class. Polymorphism is the same call behaving differently depending on the object’s type, and abstraction is hiding details and showing only the interface that is needed. Common mistake: Defining encapsulation as “writing a getter and a setter for every field”.

2. What is the difference between overloading and overriding? Overloading is methods with the same name and different parameter lists, and the choice is made at compile time. Overriding is a subclass rewriting a superclass method with the same signature, and the choice is made at runtime, based on the object’s actual type. Common mistake: Calling two methods that differ only in return type an overload. That is a compile error.

3. Can a static method be overridden? No. A static method with the same signature in a subclass hides the superclass method (method hiding). Which one runs is decided at compile time from the reference type, not from the object. Common mistake: Reusing the signature without @Override and thinking it is an override. Adding @Override makes the compiler report an error.

4. What does protected mean in Java? The member is accessible from the same class, from every class in the same package, and from subclasses in other packages. A subclass in another package can only use that access through the member it inherited. It cannot reach the protected field of another object of the superclass type. Common mistake: Saying “only subclasses can access it” and forgetting package access.

5. What happens if no access modifier is written? The member becomes package-private. Classes in the same package can access it. Classes in other packages, subclasses included, cannot. Common mistake: Assuming the default is private, as it is in C#.

6. What is the difference between an abstract class and an interface? An abstract class can have fields, constructors and members at any access level, and a class extends only one. An interface holds no state, its fields are only constants, and a class can implement several. Since Java 8 an interface can have default and static methods, and since Java 9 private methods. Common mistake: Saying “an interface can only have abstract methods”. That was true up to Java 7.

7. Why does an abstract class have a constructor if it cannot be instantiated? The constructor runs when a subclass calls it with super(...), to set up the shared fields of the abstract class. The object is always an instance of a concrete subclass, and the abstract class prepares part of it. Common mistake: Saying “an abstract class cannot have a constructor”.

8. What does composition over inheritance mean? When sharing code, first consider holding an object as a field (has-a), and use inheritance (is-a) when there is a real type relationship. Inheritance ties the subclass tightly to the superclass’s internals and also exposes methods that were not wanted. Common mistake: Reading the principle as “never use inheritance”.
