Big O: Measuring Code Speed

Programming 101, Part 1

This post is about measuring how fast a piece of code is without depending on the hardware it runs on.

Two pieces of code both finish 100 items in a millisecond. With a million items, one still finishes almost instantly and the other takes 17 minutes. The difference comes from how the code grows, not from the hardware.

Most algorithm questions in an interview end with the same question: “What’s the complexity?” Below I explain how to answer it by reading the code and counting. At the end there are common interview questions with short answers.

1. Why growth is measured instead of seconds

Seconds are misleading. The same code can take 2 seconds on a laptop and 0.3 seconds on a server. The language, the compiler and whatever else is running at the moment also change the result.

Big O measures something else: how much the work grows as the data grows. The input size is called n, and the step count is written as a function of n.

Parcel delivery works the same way. “This parcel arrives in 3 hours” depends on the driver, traffic and weather. “Double the parcels and delivery takes twice as long” says something about the delivery method itself. Big O measures the method.

There are two kinds of complexity:

  • Time Complexity: how many steps are taken as the input grows.
  • Space Complexity: how much extra memory is needed as the input grows.

2. Complexity classes

Class Name Typical example
O(1) Constant Array access by index arr[5]
O(log n) Logarithmic Binary search
O(n) Linear One pass over a list
O(n log n) Linearithmic Merge sort, good sorting algorithms
O(n²) Quadratic Two nested loops, bubble sort
O(2ⁿ) Exponential Trying every subset of a set
O(n!) Factorial Trying every ordering (permutation)

O(1) is like a warehouse. Whether it holds 100 boxes or a million, a clerk who knows where box 1 is goes straight to it.

O(log n) works like a number-guessing game. For a number between 1 and 100, the first guess is “50”, the answer is “lower”, and 50 options are gone in one move. Each step halves the range. 100 numbers need at most 7 guesses, a million need 20 (2²⁰ ≈ 1,048,576).

For O(n), the boxes are jumbled and the task is to find the one with a red ball. Every box has to be checked one by one. 10 boxes means 10 checks, 1,000 boxes means 1,000 checks.

O(n²) is everyone in a room shaking hands with everyone else. 10 people make 45 handshakes, 100 people make 4,950. Ten times the people means about 110 times the work. The exact count is n(n−1)/2. Drop the constants and O(n²) remains.

On a machine doing a billion simple operations per second, n = 1 million takes about 17 minutes at O(n²) and 0.02 seconds at O(n log n). At n = 100, O(2ⁿ) takes about 4×10¹³ years. That is thousands of times the age of the universe.

3. Reading complexity from code

The method is simple: count the work that repeats depending on the input.

A single loop gives O(n):

def total(arr):
    t = 0
    for x in arr:      # n times
        t += x         # O(1)
    return t

Nested loops give O(n²):

def pairs(arr):
    for i in range(len(arr)):          # n times
        for j in range(len(arr)):      # n times for each
            print(arr[i], arr[j])

Sequential loops add, nested loops multiply. Two separate for loops are O(n) + O(n) = O(2n) = O(n). Two nested for loops are O(n · n) = O(n²).

Code that halves the range at each step gives O(log n):

def binary_search(arr, target):         # arr must be sorted
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] == target: return mid
        if arr[mid] < target: lo = mid + 1
        else: hi = mid - 1
    return -1

With Recursion, count the call tree:

def fib(n):
    if n < 2: return n
    return fib(n - 1) + fib(n - 2)     # each call spawns two

Each call branches into two, and the tree grows to roughly 2ⁿ nodes, so it is O(2ⁿ). The tighter bound is ≈1.618ⁿ, but O(2ⁿ) is a valid upper bound. If results are cached in a dictionary (Memoization), each fib(k) is computed once and the complexity drops to O(n).

Constants and lower terms are dropped

Code that takes 3n² + 5n + 100 steps is O(n²). At n = 1 million, 3n² is 3×10¹² while 5n is only 5×10⁶, which is negligible next to it. The constant 3 changes with the hardware anyway and does not change the shape of growth. On a 500 km drive, nobody counts the 2 minutes spent leaving the car park.

For the same reason the log base is not written. log₂ n and log₁₀ n differ only by a constant factor (≈3.32).

4. O, Ω and Θ: upper bound, lower bound, tight bound

All three notations are bounds. A pizza order makes them easy to explain:

  • Big O (upper bound): the courier says “even in traffic, I’ll be there within 60 minutes.” Delivery is never slower than that.
  • Big Omega, Ω (lower bound): “even on empty roads, it takes at least 15 minutes.” Delivery is never faster than that.
  • Big Theta, Θ (tight bound): “30 to 35 minutes, every time.” The upper and lower bounds grow at the same rate.

If the step count of an algorithm draws an uneven curve on a graph, O is the ceiling the curve never goes above and Ω is the floor it never goes below. When both settle on the same growth rate, the result is Θ.

A common confusion comes up here. O, Ω and Θ are kinds of bound. Best, average and worst case are kinds of scenario. They are separate axes. “O = worst case, Ω = best case” is a common but wrong shortcut, and each scenario can have its own Θ. In everyday use, “Big O” usually means the tight bound on the worst case.

5. Best, average and worst case

Linear Search as an example:

def find(arr, target):
    for i, x in enumerate(arr):
        if x == target: return i
    return -1
Scenario What happens Complexity
Best Target is the first item Θ(1)
Average Target is around the middle ~n/2 steps -> Θ(n)
Worst Target is last or missing Θ(n)

Unless told otherwise, interviews mean the worst case, because the goal is to be sure the system holds up on its worst day. For some algorithms the gap between scenarios is large. Quicksort is O(n log n) on average and O(n²) in the worst case (with bad pivot choices).

6. Space complexity

The same logic applies to memory:

  • O(1) space: a million numbers are summed, but only a single total variable is kept.
  • O(n) space: the numbers are copied into a new list or loaded into a dictionary.

The memory cost that is easy to miss is recursion. Each call opens a frame on the stack. A recursive total(arr, i) goes n levels deep and uses O(n) space even without extra variables.

The input itself is usually not counted. What is discussed is Auxiliary Space.

7. Amortized O(1): appending to a dynamic array

Dynamic arrays such as Python’s list.append and Java’s ArrayList.add keep a fixed-size array underneath. When it fills up, a new, larger array is allocated by a fixed factor and every element is copied into it. The growth factor is 1.5× in Java, 2× in many C++ implementations and a smaller factor in Python. That copy is O(n).

Append is still counted as O(1). If capacity doubles, the total number of elements copied over n appends is 1 + 2 + 4 + … + n < 2n. Dividing 2n work across n appends leaves about 2 copies per append. This is called Amortized O(1).

It works like rent. There is a small payment every month and a moving bill every few years. Moving is expensive, but spread across the months it barely changes the monthly cost.

Amortized is not the same as average case. Average case looks at random inputs. Amortized analysis guarantees the total cost even for the worst sequence of operations.

8. Worked example: two-sum

Problem: find the indices of two numbers in an array that add up to target.

The Brute Force solution is O(n²):

def two_sum(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return [i, j]
    return None

In the worst case n(n−1)/2 pairs are checked. For n = 10,000 that is about 50 million comparisons.

The Hash Map solution is O(n):

def two_sum(nums, target):
    seen = {}                          # value -> index
    for i, x in enumerate(nums):
        if target - x in seen:         # O(1) on average
            return [seen[target - x], i]
        seen[x] = i
    return None

Each element is visited once. Whether its partner has already been seen is answered in the dictionary in O(1) on average. For n = 10,000 that is about 10,000 steps, 5,000 times less work.

The cost is memory. Time dropped from O(n²) to O(n), while space rose from O(1) to O(n). Interviewers expect this Time–Space Trade-off to be stated explicitly.

At a party, instead of asking every guest their birthday one by one, the birthdays are written in a notebook at the door. Each newcomer only checks the notebook. The hash map is that notebook.

Interview questions

1. What is Big O, and why is it used instead of seconds? It is an upper bound on how the step count grows as the input grows. Seconds depend on hardware and environment. The growth rate belongs to the algorithm itself. Common mistake: defining Big O as “how many seconds the code takes.”

2. Is there a difference between O(2n) and O(n)? No. Constants are dropped, so both are O(n). In practice the constant can matter, but the complexity class is the same. Common mistake: calling two separate loops O(n²). Sequential loops add, they do not multiply.

3. Are two nested loops always O(n²)? No. If the outer loop walks n items and the inner loop m items, it is O(n·m). If the inner loop always runs 10 times, it is O(n). Common mistake: writing two different inputs with a single n.

4. What is the difference between O, Ω and Θ? O is an upper bound, Ω a lower bound, and Θ a tight bound where both are the same. These are kinds of bound. Best and worst case are scenarios. Common mistake: saying “Θ is the average case.”

5. Why is binary search O(log n)? Each step halves the search range. Reducing n elements to 1 takes log₂ n steps. The array must be sorted. Common mistake: forgetting the sorting cost. Sorting an unsorted array first is O(n log n).

6. Why is appending to a dynamic array O(1)? A single append can take O(n) because of a resize. Since capacity grows geometrically, n appends cost O(n) in total, which is amortized O(1) per append. Common mistake: confusing amortized with average case.

7. What is the space complexity of a recursive function? At least the recursion depth, because every call holds a frame on the stack. A function that goes n levels deep uses O(n) space even without extra variables. Common mistake: saying “I didn’t create an array, so it’s O(1) space.”

8. How do you speed up two-sum from O(n²)? Seen values are kept in a hash map, and target − x is looked up for each element in O(1) on average. That gives O(n) time and O(n) space. If the array is sorted, two pointers solve it with O(1) extra space. Common mistake: never mentioning that hash map lookups can degrade to O(n) in the worst case, or the extra O(n) space.
