Programming Paradigms: Structured, Functional and Object-Oriented

Programming 101, Part 3

This post is about why two pieces of code that solve the same problem can look nothing alike. One walks through the data with a loop and a counter, another passes the data through functions, a third spreads the work across objects. All of them give the right answer. The difference is in how the programmer breaks the problem down.

Below I cover what a paradigm is, the split between imperative and declarative, and three common paradigms: structured (procedural), functional and object-oriented. Then I solve the same problem in all three. At the end there are common interview questions with short answers.

1. What is a paradigm?

A Programming Paradigm is a way of thinking about and building a program. It decides how the code is divided, where the data lives and how it changes.

A paradigm is not a language. The language is the tool, the paradigm is a way of using it. In the same kitchen with the same ingredients, one cook follows a recipe step by step while another splits the kitchen into stations and gives each one a task. The ingredients are the same, the organization of the work is different.

A language makes some paradigms easy and others awkward. Haskell pushes toward a functional style, Java toward an object-oriented one. Most widely used languages today, such as Python, Java, C# and JavaScript, support more than one paradigm. I come back to this in section 7.

2. Imperative vs. declarative

Paradigms roughly fall into two large groups.

In Imperative programming, the computer is told how to do the work, step by step. A program is a sequence of commands that change the values of variables. Structured and procedural programming belong here. OOP also sits on an imperative base in most languages, because an object’s state is changed through its methods.

In Declarative programming, the desired result is described and the steps to get there are left to the language or the runtime. SQL, HTML and the logic programming language Prolog belong here. Functional programming is usually counted in this group too.

The imperative style is like giving someone a recipe (“crack the eggs, whisk them, pour them into the pan”). The declarative style is like ordering at a restaurant (“an omelette, please”). How the omelette gets made is the kitchen’s business.

The same task in both styles, the names of products in stock:

# imperative: every step is written out
names = []
for product in products:
    if product["in_stock"]:
        names.append(product["name"])
-- declarative: only the desired result is described
SELECT name FROM products WHERE in_stock = 1;

The SQL query does not say in what order to scan the table or whether to use an index. The database’s query planner makes those decisions.

The split is not a hard line but a spectrum. In Python, [p["name"] for p in products if p["in_stock"]] is more declarative than the loop above, but less declarative than SQL.

3. Structured and procedural programming

The two terms are often used as synonyms, but they describe different things.

Structured Programming is about control flow. A program is built from only three constructs:

  • Sequence: Statements run in the order they are written.
  • Selection: Branching with if / else.
  • Iteration: for and while loops.

A theorem proved in 1966 showed that any algorithm can be written with these three constructs. Structured programming argued against the habit of jumping to arbitrary lines with goto. Since every block has one entry and one exit, the code can be read from top to bottom.

Procedural Programming is about how the code is divided. The program is split into Procedures, or functions, each doing one job, and the main flow calls them in order. C and Pascal are the classic languages of this style.

In practice the two come together. Today “procedural code” usually means imperative code that uses structured control flow and is split into functions.

def add_vat(price, rate):
    return price * (1 + rate)

def invoice_total(items, rate):
    total = 0
    for price, qty in items:            # iteration
        if qty > 0:                     # selection
            total += add_vat(price, rate) * qty
    return total

Data and the functions that work on it live apart. Functions take the data as parameters and either change it or return a new value.

This style is direct and readable in small and medium programs. The trouble starts as the program grows and many functions begin to modify the same data, making it hard to see what a change has broken. The cure is not to abandon structured programming but to limit who is allowed to change the data. OOP and functional programming do this in two different ways.

4. Functional programming

Functional Programming builds a program as a composition of functions, as in mathematics. Data is not kept in one place and changed step by step. It passes through a function and comes out as a new value. It resembles an assembly line: raw material goes in at one end, each station transforms it, the finished product comes out at the other end.

The style rests on four ideas.

Pure functions and side effects

A Pure Function meets two conditions. It always returns the same output for the same input, and it changes nothing outside itself.

A Side Effect is any change a function makes to the outside world other than returning a value. Modifying a global variable or a list passed in as a parameter, printing to the screen, writing to a file or a database, and sending a network request are all side effects. Reading has a similar issue: a function that reads the clock, a random number or a global variable can return different outputs for the same input, so it is not pure either.

vat_rate = 0.20

def with_vat(price):              # not pure: depends on an outside variable
    return price * (1 + vat_rate)

def with_vat_pure(price, rate):   # pure: result depends only on inputs
    return price * (1 + rate)

If vat_rate is changed somewhere else, with_vat(100) returns a different result. with_vat_pure(100, 0.20) always returns 120.

Pure functions are easy to test. There is no environment to set up and no global state to reset: give an input, check the output. Caching the result is also safe, because the same input always gives the same result.

A whole program cannot be pure. A program that never prints or saves anything is useless. The goal of the functional style is not to remove side effects but to push them to the edges of the program. Computation happens in pure functions, and reading and writing stay in a few known places.

Immutability

Immutability means a value is not changed after it is created. When a change is needed, the old value is kept and a new one is produced.

In Python, list and dict are mutable, while tuple, str and frozenset are immutable. Passing a mutable list to a function is a classic source of bugs:

def apply_discount(prices):
    for i in range(len(prices)):
        prices[i] *= 0.9                 # the caller's list changes

def discounted(prices):
    return [p * 0.9 for p in prices]     # returns a new list, input unchanged

Code that calls the first function may not notice that its own list has changed. With the second, the original prices are kept.

Immutable data also makes parallel work easier. If no thread modifies shared data, the data race that comes from two threads writing to the same variable at once cannot happen. That does not make parallelism free. The work still has to be split and the results combined, and ordering problems remain when accessing outside resources such as files or databases.

The cost is memory and copying. Functional languages soften this with data structures in which the new version shares the unchanged parts with the old one.

Higher-order and first-class functions

If a language lets functions be assigned to variables, passed as parameters and returned from other functions, it has First-Class Functions. Python, JavaScript and C# work this way. Java has offered something close to it since Java 8, through lambda expressions.

A Higher-Order Function is a function that takes another function as a parameter or returns one as its result.

def multiplier(k):
    return lambda x: x * k                # returns a function

triple = multiplier(3)
print(triple(5))                          # 15

fruits = ["watermelon", "apple", "kiwi", "fig"]
print(sorted(fruits, key=len))            # takes a function
# ['fig', 'kiwi', 'apple', 'watermelon']

multiplier is higher-order because it returns a function, and sorted is higher-order because it takes one through its key parameter. First-class is a property of the language, higher-order is a property of individual functions.

map, filter and reduce

In the functional style, most loops are replaced by three higher-order functions:

Function What it does On [1, 2, 3, 4]
map(f, items) Applies f to each element x * x -> [1, 4, 9, 16]
filter(p, items) Keeps elements for which p is true is even -> [2, 4]
reduce(f, items, start) Folds the elements into one value addition -> 10 
from functools import reduce

numbers = [1, 2, 3, 4]
squares = list(map(lambda x: x * x, numbers))            # [1, 4, 9, 16]
evens = list(filter(lambda x: x % 2 == 0, numbers))      # [2, 4]
total = reduce(lambda a, b: a + b, numbers, 0)           # 10

Two details are specific to Python. reduce is not a built-in in Python 3, it comes from functools. map and filter do not return lists but lazy iterators that produce values on demand, so list(...) is needed to see the result. In Python, list comprehensions and ready-made functions like sum are often preferred over these.

Functional languages also use recursion in place of loops. In Python this is not a good idea. The default recursion limit is around 1000 and the language does no tail call optimization.

5. Object-oriented programming: a short introduction

Object-Oriented Programming (OOP) keeps data and the code that works on it in a single unit. That unit is an Object, and its template is a Class. An object’s data is its state, and its methods are its behavior.

In procedural code the data sits in one place and the functions in another. In OOP the answer to “who can change this data?” is clear: only the object’s own methods. A bank account’s balance is not changed directly from outside. It changes through deposit and withdraw methods, and those methods enforce the rules themselves, such as no negative balance.

A library makes the difference easy to see. In the procedural style a single librarian does every job from one to-do list. In OOP every job has someone responsible for it (a registrar, a shelver, a member), and they hand work to each other. When a new kind of item is added to the system, say DVD lending, a new responsible party can be added without touching most of the existing ones.

OOP is built on four principles: Encapsulation, Inheritance, Polymorphism and Abstraction. These, and questions about class design, are the topic of the next post. Here it is enough to see where OOP sits among the paradigms.

It is often said that OOP is designed bottom-up and structured programming top-down. These are tendencies, not rules.

6. The same problem in three paradigms

The problem: find the total price of the items in a shopping cart that are in stock. The cart:

Item Price Qty In stock
pen 12 3 yes
notebook 45 2 yes
bag 300 1 no

The expected result is 12 × 3 + 45 × 2 = 126.

Structured / procedural

cart = [
    {"name": "pen",      "price": 12.0,  "qty": 3, "in_stock": True},
    {"name": "notebook", "price": 45.0,  "qty": 2, "in_stock": True},
    {"name": "bag",      "price": 300.0, "qty": 1, "in_stock": False},
]

def in_stock_total(cart):
    total = 0
    for item in cart:
        if item["in_stock"]:
            total += item["price"] * item["qty"]   # total changes every step
    return total

print(in_stock_total(cart))   # 126.0

The steps are spelled out. The only variable holding state is total, and its value changes on every pass.

Functional

from functools import reduce

in_stock = filter(lambda i: i["in_stock"], cart)
amounts = map(lambda i: i["price"] * i["qty"], in_stock)
total = reduce(lambda a, b: a + b, amounts, 0)
print(total)   # 126.0

# In Python the same thing is usually one line:
total = sum(i["price"] * i["qty"] for i in cart if i["in_stock"])

No variable changes its value. The data passes through three stages: filter, transform, fold. The cart itself is never touched.

Object-oriented

class Item:
    def __init__(self, name, price, qty, in_stock=True):
        self.name, self.price, self.qty, self.in_stock = name, price, qty, in_stock

    def amount(self):
        return self.price * self.qty

class Cart:
    def __init__(self):
        self._items = []                   # not meant to be accessed directly

    def add(self, item):
        self._items.append(item)

    def total(self):
        return sum(i.amount() for i in self._items if i.in_stock)

cart = Cart()
cart.add(Item("pen", 12.0, 3))
cart.add(Item("notebook", 45.0, 2))
cart.add(Item("bag", 300.0, 1, in_stock=False))
print(cart.total())   # 126.0

The code is longer, but the responsibilities are spread out. Item knows how to compute its own amount, Cart knows what goes in and what gets counted. If discounted items are added tomorrow, the change stays in Item, and code that uses the cart is not affected.

The leading underscore in _items is a warning in Python, not an enforcement. Java’s private is checked by the compiler, while in Python it is a convention and outside access is still possible.

Note also that Cart.total uses a functional expression inside. In real code the paradigms mix like this.

Structured / procedural Functional Object-oriented
Basic unit Procedure / function Pure function Object (data + methods)
Data and code Separate Separate, data does not change Together
State change Variables change in place New values are produced Through the object’s own methods
Repetition for, while map, filter, recursion Loops inside methods
Strong at Short, linear tasks Data transformation, testing, concurrency Modeling entities with state and rules

7. When to use which, and multi-paradigm languages

These three are not rivals. They are tools that fit different problems.

The structured / procedural style is the natural choice for short scripts, one-off data processing, and code close to the hardware where performance is critical (embedded systems, operating system kernels). The flow reads top to bottom with no extra abstraction.

The functional style stands out in data transformation: filtering, transforming, grouping and reporting on a collection. Pure functions are the easiest code to test. In concurrent systems, immutable data prevents most of the bugs that come from writing to shared memory.

OOP fits systems where many entities with state and rules talk to each other: user interfaces, games, business applications with concepts like orders, accounts and products. In large teams, giving each class its own responsibility makes it easier to divide the work.

One observation that goes over well in interviews: in OOP, adding a new type is easy (write a new class), but adding a new operation to all types means touching every class. In the functional style it is the other way around. A new operation is a single function, but a new data type affects every function that handles that data. The choice depends on which direction the system is expected to grow.

Multi-paradigm languages

Most of today’s languages are not tied to a single paradigm:

  • Python: Classes, first-class functions, map/filter, comprehensions and plain procedural scripts all side by side.
  • Java: All code lives inside a class, but lambda expressions and the Stream API, added in Java 8, made the functional style possible.
  • C# and JavaScript: Classes and lambdas together. In C#, LINQ’s Where, Select and Aggregate methods correspond to filter, map and reduce.
  • Haskell: A purely functional language. Side effects are marked separately in the type system.

The functional version of the cart example in Java:

double total = cart.stream()
        .filter(Item::isInStock)
        .mapToDouble(i -> i.getPrice() * i.getQty())
        .sum();

A common application layout uses all three. The skeleton of the application is built with classes, the computation logic is written as pure functions where possible, and file, database and network work stays at the edges in imperative code. This layout is called “functional core, imperative shell”.

Interview questions

1. What is a programming paradigm? Is it the same as a language? A paradigm is a way of building a program and breaking down a problem. A language is the tool used to apply it. Most modern languages support more than one paradigm. Common mistake: Mapping languages to paradigms one to one, as in “Python is a functional language” or “Java is only OOP”.

2. What is the difference between imperative and declarative programming? Imperative code writes out the steps toward the result and changes state along the way. Declarative code describes the desired result and leaves the steps to the language or the runtime. SQL is declarative, a sum written with a for loop is imperative. Common mistake: Treating it as a strict binary. It is a spectrum, and a list comprehension sits between the two.

3. Are structured programming and procedural programming the same thing? No. Structured programming is about control flow: it builds programs from sequence, selection and iteration and avoids goto. Procedural programming is about splitting code into procedures. In practice they are usually used together. Common mistake: Associating structured programming with spaghetti code. Structured programming was created to fight the spaghetti code that goto produced.

4. What is a pure function? Give an example of a side effect. A function that always returns the same output for the same input and changes nothing outside itself. Modifying a global variable or a list passed in as a parameter, printing, writing to a file and sending a network request are side effects. Common mistake: Only checking whether it returns a value. A function that reads the clock or a global variable is not pure, even if it changes nothing.

5. Why does immutability matter, and what does it cost? Because values do not change, a function is not affected by some other code modifying its data behind its back. Threads do not write to shared data, so data races do not occur. The cost is the extra memory and copying of producing a new value on every change. Common mistake: Saying “with immutable data there are no concurrency problems at all”. Data races go away, but the work still has to be split and access to outside resources still has to be ordered.

6. What is the difference between a higher-order function and a first-class function? First-class functions are a property of the language: functions can be assigned to variables, passed as arguments and returned. A higher-order function uses that property by taking or returning another function. map, filter and sorted(key=...) are examples. Common mistake: Treating them as the same concept.

7. What do map, filter and reduce do? map applies a function to each element and produces a result of the same length. filter keeps the elements that satisfy a condition. reduce folds the elements into a single value with a combining function. Common mistake: Assuming map and filter return lists in Python 3. Both return lazy iterators that are exhausted after one pass.

8. When is OOP the better choice, and when is the functional style? OOP fits when modeling entities that have state and rules and talk to each other. The functional style stands out when data goes through a series of transformations, or when concurrency and ease of testing matter. Most real projects use both. Common mistake: Declaring one paradigm superior in every case, or wrapping everything in a class.
