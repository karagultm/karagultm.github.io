Software Testing: Test Levels, Unit Tests, Mocks and TDD

Programming 101, Part 14

The earlier parts of this series covered how code is written and how it runs: data structures, OOP, design patterns, concurrency, networking. This part asks a different question: how do you make sure the code you wrote actually works?

Testing questions in interviews usually come from two directions. The first is concepts: test levels, black box and white box, the difference between a regression test and a smoke test. The second is practice: how to write a unit test, when to use a mock, what coverage tells you. The examples use unittest from Python’s standard library, and all of them were run to check them. The same ideas apply in JUnit 5 and pytest.

Below I first cover the purpose of testing and the difference between verification and validation. Then come test levels, test design techniques, the anatomy of a unit test, test doubles and TDD. After that are regression, smoke and sanity tests, non-functional tests and coverage. At the end there are common interview questions.

1. The purpose of testing

Software Testing is the process of running software under given conditions and comparing the expected result with the actual one in order to find defects. The goal is to gain confidence that the software meets its requirements and to see defects before users do.

One of the basic principles of testing is this: testing can show that defects are present, but it cannot prove they are absent. If a hundred tests pass, you cannot say the code has no bugs. You can only say no bug showed up in those hundred cases. Trying every input combination (exhaustive testing) is impossible outside trivial functions. A function that takes two int values already has 2^64 possible input pairs.

So testing is a matter of choice. You decide deliberately which inputs are worth trying. Two other principles guide that choice. Defects tend to cluster in a few modules (defect clustering), and the later a defect is found, the more expensive it is to fix. A mistake caught at the requirements stage is a one-paragraph edit. The same mistake found in production means changing code, data and possibly how you talk to customers.

The order of the terms is also a common question. The developer’s mistake is called an Error (Mistake). The result of that mistake in the code is a Defect, also called a fault or a bug. The wrong behavior observed when defective code runs is a Failure. Not every defect becomes a failure. A defect on a code path that never runs can go unnoticed for years.

2. Verification and validation

The two terms look very close, but they answer different questions.

Verification checks whether the product was built according to its specification: “Are we building the product right?” Validation checks whether the product meets the user’s real need: “Are we building the right product?”

An example makes the difference clear. The specification says “the report should be downloadable as a PDF”, and the system does that flawlessly. Verification passes. But users want to work with the report in a spreadsheet and copy the PDF by hand every time. Validation fails. The product matches the specification but does not meet the need.

Verification Validation
Question Are we building the product right? Are we building the right product?
Measured against Specification, design, requirements document The user’s real need
Typical activities Code review, requirements review, unit and integration tests Acceptance tests, user trials, beta

The source notes need a correction here. They pair verification with “static testing done without running the software” and validation with “dynamic testing done by running it”. That pairing is incomplete. Static activities such as code review are verification, but a unit test is also verification even though it runs the code, because it checks conformance to the specification. The distinction is about what you measure against, not about the technique.

3. Test levels and the test pyramid

Tests are split into four levels by how large a part of the system they cover.

A Unit Test tests the smallest testable piece, usually a function or a class, in isolation from the other pieces. It runs in milliseconds, and when it fails the location of the problem is obvious.

An Integration Test tests how units talk to each other. Whether a service sends the right query to the database and reads the result correctly is an integration test concern. Units can each work correctly and still fail together: one may expect dates as day/month/year and the other as month/day/year.

A System Test tests the whole deployed system against its requirements. Besides functional behavior, non-functional properties such as performance and security are covered at this level.

An Acceptance Test checks whether the system meets the user’s or customer’s needs and forms the basis for the release decision. User Acceptance Testing (UAT) is its best-known form. Alpha testing happens in the developer’s environment, beta testing in the user’s.

There are two approaches to integration testing. In the big bang approach all modules are combined at once and tested together. Little preparation is needed, but when something fails it is hard to tell which interface caused it. In the incremental approach modules are added one at a time. A Stub replaces a lower-level module that is not written yet, and a Driver replaces a higher-level module, the caller, that is not written yet.

The Test Pyramid is a model of how tests should be distributed across these levels. Many unit tests at the base, fewer integration tests in the middle, a small number of end-to-end tests at the top. The reason is cost. Higher up, tests get slower, harder to set up, and harder to diagnose when they break. A unit test finishes in a millisecond. An end-to-end test that opens a browser and fills in a form takes seconds and can occasionally fail for no reason because of network latency.

The inverse of the pyramid, where most tests are end-to-end and only a few are unit tests, is called the “ice cream cone”. A suite shaped like that is slow, and developers start avoiding running it after each change.

4. Black box and white box testing

There are two viewpoints in test design. The difference is whether the person writing the test knows what is inside the code.

Black Box Testing tests the system only through inputs and outputs. It does not look at how the code is written, it looks at what the specification says. The test asks what the software does.

White Box Testing designs tests from the internal structure of the code. The goal is to run every if branch and every loop at least once. The test asks how the software does it. A mix of the two, with partial knowledge of the internals, is called Gray Box Testing.

Two black box techniques come up most often.

Equivalence Partitioning splits inputs into groups that the system treats the same way and picks one representative from each group. If one value in a group works, the other values in that group are assumed to work too.

Boundary Value Analysis is based on the observation that defects cluster at the boundaries between groups. Values on both sides of each boundary are tested. Mistakes such as writing <= instead of < are caught exactly here.

An example rule: a ticket discount depends on age. Ages 0–17 get 50%, ages 18–64 get no discount, ages 65–120 get 30%, and anything outside that range is invalid.

Partition Range Representative Boundary values
Invalid (low) age < 0 −5 −1
Child 0–17 10 0, 17
Adult 18–64 30 18, 64
Senior 65–120 80 65, 120
Invalid (high) age > 120 150 121

Five representatives from five partitions and eight boundary values stand in for more than a hundred and twenty possible ages.

class DiscountRateTest(unittest.TestCase):
    def test_boundary_values(self):
        expected = {0: 0.5, 17: 0.5, 18: 0.0, 64: 0.0, 65: 0.3, 120: 0.3}
        for age, rate in expected.items():
            with self.subTest(age=age):
                self.assertEqual(discount_rate(age), rate)

    def test_out_of_range_ages(self):
        for age in (-1, 121):
            with self.subTest(age=age):
                with self.assertRaises(ValueError):
                    discount_rate(age)

subTest reports each value in the loop as a separate case. If 17 fails, the test keeps checking the other values and the report shows which age broke. In pytest the same thing is done with @pytest.mark.parametrize, in JUnit 5 with @ParameterizedTest.

5. Anatomy of a unit test: Arrange-Act-Assert

A good unit test has three parts. This structure is called Arrange-Act-Assert (AAA).

  • Arrange: the objects and data the test needs are set up.
  • Act: the behavior under test is triggered with a single call.
  • Assert: the result is checked against the expected value.
import unittest

def cart_total(prices, discount=0.0):
    if not 0 <= discount < 1:
        raise ValueError("discount must be between 0 and 1")
    return round(sum(prices) * (1 - discount), 2)

class CartTotalTest(unittest.TestCase):
    def test_discount_lowers_total(self):
        prices = [100, 50]                           # Arrange
        total = cart_total(prices, discount=0.1)     # Act
        self.assertEqual(total, 135.0)               # Assert

    def test_invalid_discount_raises(self):
        with self.assertRaises(ValueError):
            cart_total([100], discount=1.5)

The test name says what is tested and what the expected result is. When test_discount_lowers_total shows up as failed in the report, the problem is clear without opening the code. Names like test1 or test_cart do not give that information.

Tests should be independent of each other. If one test relies on data produced by another, changing the order or running a test on its own leads to failures nobody can explain. setUp in unittest, @BeforeEach in JUnit 5 and fixtures in pytest exist to give each test a clean start.

A test should check one behavior. Several asserts that check different aspects of the same behavior are fine. The problem is trying three unrelated scenarios, such as placing, cancelling and refunding an order, in one test. When the first assert fails, the state of the other two is unknown.

The test itself must also be deterministic. A test that depends on the clock, random numbers or the network passes sometimes and fails other times. Such tests are called Flaky Tests, and after a while the team stops taking red results seriously.

6. Test doubles: stub, mock, fake, spy

The class under test usually depends on other objects: a database, a payment service, an email sender. Using the real ones in a unit test makes it slow and ties it to external systems. Nobody wants a request sent to a real payment service every time the tests run. The general name for an object that stands in for a dependency in a test is a Test Double. The name comes from the stunt double who replaces an actor in a film.

Four kinds are commonly asked about.

  • Stub: Returns a predetermined answer. It provides the data the test needs, and how it was called is not checked.
  • Mock: At the end of the test, which method was called, with which arguments and how many times is verified. The test looks at whether an interaction happened.
  • Fake: A working implementation that is too simple to use in production. An in-memory dictionary instead of a database is the typical example.
  • Spy: Wraps a real object. The real method runs, but the calls are recorded and can be checked afterwards.
from unittest.mock import Mock

class OrderService:
    def __init__(self, payment, email):
        self.payment, self.email = payment, email

    def place_order(self, customer, amount):
        if not self.payment.charge(customer, amount):
            return False
        self.email.send(customer, "Your order was received")
        return True

class OrderServiceTest(unittest.TestCase):
    def test_email_sent_when_payment_succeeds(self):
        payment = Mock()
        payment.charge.return_value = True   # stub: canned answer
        email = Mock()                       # mock: call will be verified

        result = OrderService(payment, email).place_order("customer-42", 250)

        self.assertTrue(result)
        email.send.assert_called_once_with("customer-42", "Your order was received")

In Python the same Mock class can serve as both a stub and a mock. What decides the difference is the object’s role in the test, not its type: payment is a stub because it only answers, email is a mock because a call on it is verified. In Java, Mockito’s when(...).thenReturn(...) and verify(...) cover the same two roles.

Short examples of a fake and a spy:

class FakeUserRepository:                    # fake: in-memory repository
    def __init__(self):
        self._records = {}
    def save(self, id, name):
        self._records[id] = name
    def find(self, id):
        return self._records.get(id)

class RealCalculator:
    def add_vat(self, amount):
        return amount * 1.2

spy = Mock(wraps=RealCalculator())           # spy: the real method runs
spy.add_vat(100)                             # returns 120.0
spy.add_vat.assert_called_once_with(100)     # and the call was recorded

When mocks do harm

Mocks are a strong tool, but when overused the test starts checking how the code works instead of what it does. Tests that verify which helper method is called in which order inside a method break on every refactor, even when behavior does not change at all. The suite stops being a safety net and becomes an obstacle to change.

The second problem is that a mock can behave differently from the real object. A mock may return None where the real service throws an exception. The tests pass and the system breaks in production. When the dependency’s interface changes, the mock keeps imitating the old behavior and no test notices. In Python, using Mock(spec=RealClass) or create_autospec at least catches calls to methods that do not exist.

A few rules help in practice. If the outcome can be checked through a return value, check that value instead of using a mock. Mock only the boundaries to the outside world: network, file system, clock, payments, email. Do not mock a class from a library you do not own. Write a small wrapper around it first and mock that wrapper. Do not mock simple data objects or classes that only compute something. Use the real ones.

7. TDD: red-green-refactor

Test-Driven Development (TDD) is a development method in which the test is written before the code. It consists of a short cycle repeated over and over.

  • Red: A test is written for behavior that does not exist yet and is run. It must fail. If it does not, either the behavior already exists or the test checks nothing.
  • Green: The simplest code that makes the test pass is written. Clean code is not the goal at this step.
  • Refactor: With the tests green, the code is cleaned up: duplication removed, names fixed. The tests are rerun after every step.

For a cart total, the first test might be “the total of an empty cart is 0”. Writing return 0 makes it pass. The second test is “the total of two items is the sum of their prices”, return 0 is no longer enough, and sum comes in. When the discount test arrives, the discount calculation is added. At each step the code grows only as much as one test demands.

The main payoff of TDD is in design. Because the test comes first, the code is designed to be testable, meaning small pieces that receive their dependencies from outside. There is a cost too: in an exploratory phase where requirements are still unclear, tests may need to be rewritten constantly. TDD is not a kind of test, it is an order of writing.

8. Regression, smoke and sanity tests

These three terms are not test levels. They describe when a test is run and for what purpose.

A Regression Test checks, after a change, that features that worked before still work. Fixing a bug or adding a feature can break something elsewhere. Running the automated suite on every commit is regression testing in practice. When a bug is fixed, adding a test that reproduces it prevents the same bug from coming back.

A term often confused with regression is Retesting (Confirmation Testing). Retesting reruns the test that found a bug to confirm the fix actually worked. Regression testing looks at whether the fix broke anything around it.

A Smoke Test is a short, shallow check to decide whether a new build is worth testing in more detail. It looks at critical flows: does the application start, can you log in, does the home page load. The name comes from hardware: if no smoke comes out when a new circuit is powered on for the first time, you move on to detailed measurement.

A Sanity Test is a narrow test that, after a small change or bug fix, checks only that the affected area behaves sensibly. A smoke test is broad and shallow and touches every part of the system briefly. A sanity test is narrow and a bit deeper and focuses on one area. The boundary between the two terms varies between sources. In an interview it is enough to state this difference in breadth and depth.

9. Non-functional tests

Functional testing measures what the system does. Non-functional Testing measures how well it does it: speed, capacity, security, usability. Interviews usually ask about the performance family.

Type Question
Performance test What are the response time and resource usage under a given load?
Load test Does the system respond within the target time at the expected peak number of users?
Stress test Under load beyond what is expected, where and how does the system fail, and does it recover?
Spike test What happens when load suddenly jumps tenfold?
Soak (endurance) test Is there a memory leak or slowdown under normal load sustained for hours?

The difference between load and stress tests comes up often. A load test confirms that the system meets its targets at the expected load. A stress test pushes the load past the limit on purpose and looks at how the system fails. A system that rejects connections and recovers is very different from one that corrupts data as it goes down. Tools such as JMeter, k6 and Gatling are used for these tests.

10. Code coverage and its limits

Code Coverage is a measure of how much of the code runs while the tests run. coverage.py does this for Python, JaCoCo for Java. The two most common kinds are:

  • Line (statement) coverage: the share of lines executed.
  • Branch coverage: whether both the true and the false branch of each if were executed.

Branch coverage is stricter. If if x > 0: y = 1 is run with x = 5, line coverage is 100%, but the case x <= 0 was never tried.

100% coverage does not mean bug-free code. Coverage only says a line ran, not that its result was checked. A test with no asserts at all still raises coverage. And coverage cannot be measured for code that was never written. A missing check does not show up in a coverage report.

def average(numbers):
    return sum(numbers) / len(numbers)

class AverageTest(unittest.TestCase):
    def test_average(self):
        self.assertEqual(average([2, 4]), 3)   # coverage 100%

This test runs the function’s only line and coverage shows 100%. But average([]) throws ZeroDivisionError. Nobody decided what should happen for an empty list and no test asked. The coverage report does not reveal this. Boundary value analysis does.

Coverage is most useful when read in reverse. Low coverage points to untested areas. High coverage only shows that those areas were executed. Imposing coverage as a target can lead to meaningless tests written just to pass an 80% threshold. To measure whether tests actually catch bugs, Mutation Testing is used. The tool injects small defects into the code, for example replacing < with <=, and checks whether the tests catch the change.

Common interview questions

1. What is the difference between verification and validation? Verification checks whether the product was built according to the specification and answers “are we building the product right”. Validation checks whether the product meets the user’s real need and answers “are we building the right product”. Common mistake: Treating verification as static testing only and validation as dynamic testing only. A unit test runs the code, but it is verification because it measures against the specification.

2. What is the test pyramid and why is it shaped like a pyramid? It is a model that says there should be many unit tests at the base, fewer integration tests in the middle and a small number of end-to-end tests at the top. Higher up, tests get slower and more expensive, and failures are harder to diagnose. Common mistake: Reading the pyramid as “don’t write end-to-end tests”. They are needed, in small numbers, for critical flows.

3. What are equivalence partitioning and boundary value analysis? Equivalence partitioning splits inputs into classes the system treats the same way and tests one value from each class. Boundary value analysis tests values on and just outside the edges of those classes, because mistakes like mixing up < and <= show up there. Common mistake: Testing only the valid classes and skipping invalid inputs such as −1 or 121.

4. What is the difference between a mock and a stub? A stub returns a predetermined answer, and the test looks at the resulting state. On a mock, which method was called with which arguments is verified, and the test looks at the interaction. Common mistake: Mocking every dependency and verifying the order of internal calls. Those tests break on refactors that leave behavior unchanged.

5. What is TDD? A method in which the test is written before the code. First a failing test is written (red), then the simplest code that passes it (green), then the code is cleaned up while the tests stay green (refactor). Common mistake: Skipping the red step. A test that was never seen failing may not be checking the right thing.

6. What is the difference between regression testing, retesting and smoke testing? Retesting confirms that a fixed bug is actually fixed, using that bug’s test. Regression testing checks that a change did not break other features that worked before. A smoke test is a short, shallow check of whether a new build is worth detailed testing. Common mistake: Treating retesting and regression testing as the same thing.

7. Does 100% code coverage mean bug-free code? No. Coverage shows that a line was executed, not that its result was checked correctly. A check that was never written, such as the empty list case, never appears in a coverage report. Common mistake: Treating line coverage and branch coverage as the same. An if line with only one branch executed shows as fully covered in line coverage.

8. What is the difference between a load test and a stress test? A load test checks whether the system meets its target response time at the expected peak load. A stress test deliberately pushes load beyond capacity and looks at how the system fails and whether it recovers. Common mistake: Thinking the goal of a stress test is to show the system does not crash. The goal is to see how it crashes.
