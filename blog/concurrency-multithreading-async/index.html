Concurrency: Multithreading and Async, CPU-Bound and I/O-Bound

Programming 101, Part 10

Part 8 covered processes and threads and how the operating system hands out CPU time. Part 9 looked at the problems of shared memory, race conditions and locks. This post is about the application side: when a program needs to run several jobs at once, should it use threads, processes or async?

The answer depends mostly on what the job is waiting for. A job that computes and a job that waits for a network response do not get faster with the same tool. Below I cover that distinction, thread pools, how an event loop runs on a single thread, the Python and Java equivalents, and the common mistakes in async code. I took the Python measurements by running the code on my own machine. At the end there are interview questions.

1. Concurrency and parallelism

Concurrency is several jobs making progress during the same period of time. The jobs do not have to run at the same instant. They can advance piece by piece, taking turns. Parallelism is several jobs actually running at the same instant, on different cores.

A single cook can manage three pots in a kitchen. Stir one, turn down the heat under the next, salt the third. All three dishes cook within the same hour, but at any moment the cook is doing one thing. That is concurrency. Three cooks standing at three pots and working at the same time is parallelism.

Concurrency Parallelism
Meaning Jobs progress in the same period Jobs run at the same instant
On a single core Possible Not possible
Goal Use waiting time well, structure the program Speed up computation
Typical tool Async/await, threads Several threads or processes, many cores

Parallelism can be seen as a special case of concurrency. Jobs that run in parallel are concurrent, but not every concurrent program is parallel. The single-core Round Robin example in Part 8 is concurrency without parallelism.

2. CPU-bound and I/O-bound

This distinction came up briefly at the end of Part 8. I expand on it here, because the choice of tool rests entirely on it.

  • CPU-Bound: The job spends most of its time computing. Image processing, compression, encryption, sorting a large list. To get faster it needs more cores.
  • I/O-Bound: The job spends most of its time waiting. An HTTP request, a database query, reading a file. The CPU is idle during the wait. To get faster, it is enough to overlap the waits.

A typical request on a web server is I/O-bound. Most of its time goes to waiting for answers from the database and other services. The code itself runs in under a millisecond, while the waiting takes tens of milliseconds.

The practical way to tell them apart is to measure. If a job keeps one core at 100% while it runs, it is CPU-bound. If CPU usage is low and the job still takes long, it is waiting for something.

Different parts of the same program can be of different kinds. A service downloads images from outside (I/O-bound), then shrinks them (CPU-bound). The two parts can use different tools.

3. Threads and thread pools

In Part 8 I defined a thread as a unit of execution inside a process. Threads managed by the operating system are called OS Threads or Platform Threads. The scheduler places them on cores, so several threads can really run in parallel.

They are not free. For each thread the operating system reserves a stack, usually on the order of megabytes. Creating a thread takes a system call, and switching between threads carries the cost of a context switch. A server that opens a new thread for every incoming request starts spending its memory and time on managing threads once there are thousands of concurrent requests.

A Thread Pool solves this. A fixed number of threads is created up front, and they take jobs from a queue. A thread that finishes does not exit, it picks up the next job in the queue. It works like the couriers at a delivery depot: nobody hires a new courier for each parcel, the existing couriers take the parcels from the warehouse in turn.

The pool size depends on the kind of work:

  • For CPU-bound work, around the number of cores. More threads do not help, they only add context switches.
  • For I/O-bound work, more than that, because most threads sit waiting. A rough formula: threads = cores × (1 + wait time / compute time).

For example, on an 8-core machine where each job waits 90 ms and computes for 10 ms, 8 × (1 + 9) = 80 threads is a reasonable starting point. The formula gives an estimate. The final number comes from measurement.

Threads have a limit for I/O-bound work. Every waiting thread still holds its stack and takes up space. Ten thousand OS threads for ten thousand concurrent connections is expensive. This is where the async model comes in.

4. Async/await and the event loop

Async/Await is a model for writing code that waits without blocking the thread. A function defined with async (a Coroutine in Python) pauses when it reaches an await and gives control back. When the awaited work finishes, it continues from where it stopped.

The structure that takes control back is the Event Loop. It runs on a single thread and repeats this cycle:

  1. Take one of the ready tasks and run it.
  2. When the task reaches an await, it pauses and control returns to the loop.
  3. The loop asks the operating system which of the pending I/O operations have finished (epoll on Linux, kqueue on macOS, IOCP on Windows).
  4. A task whose I/O has finished goes back into the ready queue.

A waiter in a restaurant fits this well. The waiter passes the order to the kitchen and does not stand at that table until the food is cooked. The waiter takes orders from other tables and carries out plates that are ready. One waiter can keep up with dozens of tables while the kitchen works. The waiter is the event loop, and the kitchen is the operating system and the other end of the network.

Step 4 is the same as the Waiting -> Ready transition from Part 8. A task whose I/O has finished does not run right away. It enters the ready queue first.

Two points matter here. First, the async model uses Cooperative Multitasking. Tasks give up control themselves, and the loop never stops anyone by force. It is the same logic as non-preemptive scheduling in Part 8. A task that runs for a long time without an await locks up the whole loop.

Second, async alone does not give parallelism. Only one task runs at any moment. The gain comes from overlapping the waits. A loop waiting on a thousand connections does the job with one thread and a thousand small coroutine objects instead of a thousand threads.

5. Python: the GIL, threading, multiprocessing, asyncio

The GIL (Global Interpreter Lock) is a lock in CPython that allows only one thread at a time to execute Python bytecode. The consequence: Python threads do not run CPU-bound work in parallel.

The GIL is released during I/O. While one thread waits in time.sleep or a network call, another thread can run Python code. That is why threads are useful for I/O-bound work in Python. Some C extensions (large array operations in NumPy, hashlib) also release the GIL while they compute.

Python 3.13 offers an experimental free-threaded build without the GIL (PEP 703, python3.13t) as a separate install, while the default build still has the GIL.

I/O-bound measurement

I simulated five network requests with time.sleep(1). Sequentially, with a thread pool, and with asyncio:

import time, asyncio
from concurrent.futures import ThreadPoolExecutor

def fetch(i):
    time.sleep(1)            # 1 s wait standing in for a network request
    return i

async def afetch(i):
    await asyncio.sleep(1)
    return i

async def main():
    return await asyncio.gather(*(afetch(i) for i in range(5)))

start = time.perf_counter()
[fetch(i) for i in range(5)]                         # sequential
with ThreadPoolExecutor(max_workers=5) as pool:      # threads
    list(pool.map(fetch, range(5)))
asyncio.run(main())                                  # asyncio

Each block was timed separately. Result:

Method Time
Sequential 5.00 s
ThreadPoolExecutor (5 threads) 1.00 s
asyncio.gather 1.01 s

Both threads and async overlapped the five waits. With five requests there is no difference between them. The difference shows up in memory and thread management cost once the number of requests reaches the thousands.

CPU-bound measurement

I ran a function that computes in a plain Python loop four times:

from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def count(n):
    total = 0
    for i in range(n):
        total += i * i
    return total

N = 20_000_000

if __name__ == "__main__":                       # required on Windows and macOS
    [count(N) for _ in range(4)]                 # sequential
    with ThreadPoolExecutor(4) as pool:          # threads
        list(pool.map(count, [N] * 4))
    with ProcessPoolExecutor(4) as pool:         # processes
        list(pool.map(count, [N] * 4))
Method Time (several runs)
Sequential 6.5–9.3 s
ThreadPoolExecutor (4 threads) 5.4–8.7 s
ProcessPoolExecutor (4 processes) 2.2–2.8 s

The machine was under load, so the times moved between runs. The threaded version stayed in the same band as the sequential one, sometimes a little faster, sometimes a little slower. The process version was about three times faster every time. It is not four times faster because of the cost of starting processes and copying data between them (pickle).

Which one when?

Work Tool Why
A few I/O calls, synchronous library threading / ThreadPoolExecutor The GIL is released while waiting, existing code runs unchanged
Many concurrent I/O calls (thousands of connections) asyncio One thread, low memory, needs async libraries
CPU-bound pure Python multiprocessing / ProcessPoolExecutor Each process has its own GIL
CPU-bound with a library that releases the GIL, such as NumPy Threads may be enough The computation happens on the C side

multiprocessing has a cost too. Each process starts its own interpreter, and arguments and results are copied with pickle. Splitting small jobs across processes can be slower than running them sequentially because of the transfer cost.

6. Java: ExecutorService, CompletableFuture, virtual threads

Java has no GIL. Threads run in parallel for CPU-bound work too. Instead of creating threads by hand, Java code uses an ExecutorService, which is Java’s thread pool interface.

try (ExecutorService pool = Executors.newFixedThreadPool(4)) {
    List<Future<String>> futures = new ArrayList<>();
    for (int i = 0; i < 4; i++) {
        int id = i;
        futures.add(pool.submit(() -> fetch(id)));   // fetch: sleeps 1 s
    }
    for (Future<String> f : futures) {
        System.out.println(f.get());                 // blocks until the result arrives
    }
}   // Java 19 and later: close() waits for the jobs to finish

The four jobs finished in 1.02 seconds. submit returns a Future. A Future represents a result that is not ready yet. Its weak points are that get() blocks the calling thread and that Futures cannot be chained together.

CompletableFuture fills that gap. What to do when the result arrives is written as a chain:

CompletableFuture<String> user  = CompletableFuture.supplyAsync(() -> fetch(1));
CompletableFuture<String> order = CompletableFuture.supplyAsync(() -> fetch(2));

String page = user.thenCombine(order, (u, o) -> u + " + " + o)  // combine when both finish
                  .thenApply(String::toUpperCase)                // transform the result
                  .exceptionally(ex -> "error: " + ex.getMessage())
                  .join();

The two calls ran in parallel and the total time was 1.02 seconds. By default supplyAsync uses the common ForkJoinPool. That pool is sized for CPU-bound work. For blocking I/O calls it is better to pass a separate executor as the second argument.

Virtual threads (Java 21)

A Virtual Thread, introduced in Java 21, is a lightweight thread managed by the JVM. Virtual threads run on a small number of platform threads (carriers). When a virtual thread makes a blocking I/O call, it detaches from its carrier, and the carrier runs another virtual thread.

try (ExecutorService vt = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        int id = i;
        vt.submit(() -> fetch(id));   // a separate virtual thread per job
    }
}

Ten thousand jobs, each sleeping for 1 second, finished in 1.08 seconds in total. Doing the same with ten thousand platform threads would mean gigabytes of stack.

What virtual threads offer is this: code is written in the ordinary blocking style, and it scales close to async code. No await and no callback chains are needed. They have limits too. They do not speed up CPU-bound work, because the number of cores does not change. They should not be pooled. They are cheap, so one is created per job. In Java 21, a virtual thread that blocks inside a synchronized block is stuck to its carrier (pinning). This restriction was largely removed in Java 24.

7. Common mistakes in async code

Blocking the event loop

If a blocking call is made inside an async function, the loop cannot run any other task for that whole time.

import asyncio, time

async def bad(i):
    time.sleep(1)            # blocks the loop
    return i

async def good(i):
    await asyncio.sleep(1)   # gives control back to the loop
    return i

# each run three times with asyncio.gather
# bad:  3.00 s
# good: 1.06 s

In the bad version the three tasks ran one after another. time.sleep put the thread to sleep, and since the loop lives on that thread, the loop stopped too. In real code the same mistake is made with a synchronous HTTP library, a synchronous database driver or reading a large file.

If a library has no async version, the call is moved to a separate thread:

def legacy_call(i):
    time.sleep(1)            # library without async support
    return i

await asyncio.gather(*(asyncio.to_thread(legacy_call, i) for i in range(3)))
# 1.01 s

CPU-bound work has the same effect. A long computation inside an async function locks the loop until it finishes. For that, loop.run_in_executor is used with a ProcessPoolExecutor.

Leaving out await

A coroutine called without await does not run. The call only creates a coroutine object.

async def save():
    await asyncio.sleep(0.1)
    print("saved")

async def main():
    save()          # no await
    print("done")

asyncio.run(main())
# done
# RuntimeWarning: coroutine 'save' was never awaited

“saved” was never printed. Python gives a warning, but the program continues without an error, so this can slip through tests. In C# and JavaScript the same situation starts the work but nobody waits for its result or its error, and an exception can be lost silently.

Sequential awaits

Two calls written back to back with await run one after the other:

a = await fetch_user()     # 1 s
b = await fetch_orders()   # 1 more s, 2 s in total

Independent calls are started together with asyncio.gather, and the total time is that of the longest one. Writing async code does not mean the waits will overlap on their own.

Not keeping a reference to a task

If the reference to a task started with asyncio.create_task is not stored, the garbage collector can clean it up before it finishes. For this reason the Python documentation recommends keeping the reference in a variable or a set.

8. Which one in which situation?

Situation Choice
CPU-bound, Python Processes (multiprocessing)
CPU-bound, Java / C# As many threads as cores (thread pool, parallel streams)
I/O-bound, a few concurrent jobs A thread pool is enough
I/O-bound, thousands of concurrent connections Async/await, or virtual threads in Java
UI application Keep long work off the UI thread: async for I/O, a background thread for computation

This topic is often reduced to a single rule: if it is CPU-bound, use multithreading (Task.Run in C#), and if it is I/O-bound, use async/await. The direction is right, but it misses two things. In Python, because of the GIL, CPU-bound work does not get faster with threads and needs processes. And Task.Run alone does not split and parallelize a job. It moves the job to a thread pool thread. To spread a computation across cores, the work has to be split into pieces (Parallel.For or several Tasks). Also, I/O-bound work gets faster with threads too, as the measurement showed. The advantage of async shows up with many concurrent requests, not with a few.

Interview questions

1. What is the difference between concurrency and parallelism? Concurrency is several jobs making progress during the same period, and it happens on a single core too. Parallelism is jobs actually running at the same instant on different cores. Every parallel program is concurrent, but not the other way around. Common mistake: Using the two terms as synonyms.

2. Which tool do you pick for CPU-bound and for I/O-bound work? CPU-bound work has to be spread across several cores, with threads or processes, and in Python with processes. For I/O-bound work it is enough to overlap the waits, with a thread pool or async/await. Common mistake: Trying to speed up CPU-bound work with async.

3. How does async/await run several jobs on one thread? Each task pauses at an await and hands control to the event loop. The loop learns from the operating system which tasks have finished their I/O and runs them in turn. Only one task runs at a time, and the gain comes from overlapping the waits. Common mistake: Thinking async opens hidden threads in the background.

4. What is the GIL? Why are threads still useful in Python? The GIL is a lock in CPython that lets only one thread at a time execute Python bytecode. It is released during I/O and time.sleep, so threads can overlap waits in I/O-bound work. In CPU-bound pure Python code, adding threads does not help. Common mistake: Saying “threads are useless in Python”.

5. Why use a thread pool, and how do you choose its size? Creating threads and giving each one a stack is expensive. A pool reuses a fixed number of threads. For CPU-bound work the size is around the number of cores, for I/O-bound work it is larger depending on the wait ratio, and the result is checked by measuring. Common mistake: Saying “the more threads, the faster”.

6. What happens if you call time.sleep(1) inside an async function? The thread the event loop runs on is blocked, and no other task makes progress for that second. The correct call is await asyncio.sleep(1). If a synchronous library is unavoidable, the call is moved to a separate thread with asyncio.to_thread. Common mistake: Thinking the problem is limited to sleep. Synchronous HTTP and database calls have the same effect.

7. What is the difference between Future and CompletableFuture in Java? With a Future the result is read with get(), and that call blocks the thread. With a CompletableFuture the steps to run when the result arrives are chained with thenApply, thenCombine and exceptionally. This makes it possible to combine several asynchronous jobs without blocking. Common mistake: Piling blocking I/O onto the common ForkJoinPool through supplyAsync.

8. Do Java 21 virtual threads speed up CPU-bound work? No. Virtual threads release their carrier thread while waiting, which makes large numbers of concurrent I/O jobs cheap. They do not add cores, so they bring no gain for computation-heavy work. Common mistake: Pooling virtual threads, or treating them as “faster threads”.
