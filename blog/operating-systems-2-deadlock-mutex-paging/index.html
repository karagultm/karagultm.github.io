Operating Systems 2: Deadlock, Mutex and Paging

Programming 101, Part 9

Part 8 looked at how the operating system shares the CPU between processes and threads. I mentioned there that threads see the same memory and that this comes at a price. This post starts with that price.

The first half is about concurrency: what breaks when several threads touch shared data, how locks prevent it, and how locks themselves lead to deadlock. The second half is about memory: virtual memory, paging, page replacement algorithms, and why a system acts frozen when memory runs out. At the end there are common interview questions.

1. Race conditions and the critical section

A race condition happens when several threads access shared data at the same time, at least one of them writes, and the result depends on the order of operations. Threads that only read cause no trouble.

The classic example is incrementing a counter. balance += 1 looks like one line but it is three steps: read, add one, write back. If two threads read the same value, both write the same result and one increment is lost.

import threading, time

balance = 0

def deposit(n):
    global balance
    for _ in range(n):
        current = balance      # read
        time.sleep(0)          # give other threads a chance to run
        balance = current + 1  # write

threads = [threading.Thread(target=deposit, args=(10_000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(balance)   # expected 40000

The expected result is 40,000. On Python 3.13, two runs printed 10,296 and 10,711, different each time. The time.sleep(0) line is there to make the bug visible. Without it the same bug can still happen, just less often.

The part of the code that touches shared data is called the critical section. A correct solution is expected to provide three things:

  • Mutual exclusion: At most one thread is inside the section at any time.
  • Progress: If the section is free and someone wants in, the decision about who enters is made in finite time.
  • Bounded waiting: No thread is kept waiting forever.

It works like a single fitting room in a shop. While someone is inside the door is locked, and the next person waits outside.

2. Mutexes, semaphores and monitors

Pure software solutions such as Peterson’s algorithm are not reliable on modern processors without extra barriers, because the hardware reorders memory operations. In practice we use tools built on atomic CPU instructions such as test-and-set and compare-and-swap.

Mutex

A mutex (mutual exclusion lock) is a lock acquired before entering the critical section and released on the way out. The earlier example is fixed with one line:

lock = threading.Lock()

def deposit(n):
    global balance
    for _ in range(n):
        with lock:                 # critical section
            current = balance
            time.sleep(0)
            balance = current + 1

This version prints 40,000 on every run.

The defining property of a mutex is ownership: the thread that acquired the lock releases it. If the lock is taken, the waiting thread is usually put to sleep and uses no CPU. A lock that keeps checking “is it free yet?” in a loop is a spinlock, and that kind of waiting is busy waiting. When a lock is held very briefly, spinning can be cheaper than sleeping and waking up.

Semaphore

A semaphore is an integer counter with two operations. wait() (P, acquire) decrements the counter and blocks if it is zero. signal() (V, release) increments it and wakes a waiting thread.

  • Counting semaphore: The counter starts at N, so at most N threads use the resource at once. Like the “spaces free: 3” sign at a car park entrance.
  • Binary semaphore: The counter can only be 0 or 1.
slots = threading.Semaphore(3)   # at most 3 connections at once

def use_connection(i):
    with slots:
        time.sleep(0.1)          # use the connection

With ten threads calling this at once, an instrumented version never saw more than 3 threads inside. Connection pools and concurrent request limits are built this way.

Mutex vs. binary semaphore

Both behave like 0 and 1, which is why they are often confused. The difference is in ownership and purpose.

Mutex Binary semaphore
Ownership Yes, the thread that locks it unlocks it No, any thread can call signal()
Typical use Protecting shared data Telling another thread an event has happened

A mutex is the lock on a fitting room door, and the person inside opens it. A binary semaphore is the flag that starts a race. The official raises it, the runner runs.

Java makes the difference visible:

ReentrantLock lock = new ReentrantLock();
lock.lock();                                  // main thread holds the lock
new Thread(() -> {
    try { lock.unlock(); }                    // another thread tries to release it
    catch (IllegalMonitorStateException e) { System.out.println("mutex: not allowed"); }
}).start();

Semaphore ready = new Semaphore(0);           // starts at 0
new Thread(ready::release).start();           // signal comes from another thread
ready.acquire();                              // main waits for the signal

ReentrantLock rejects an unlock() from a thread that does not own it. Semaphore lets another thread call release(), and the main thread continues.

How strictly ownership is enforced depends on the library. Python’s threading.Lock can be released by a different thread, and it is threading.RLock that checks ownership. In POSIX, unlocking a default mutex from a non-owning thread is undefined behaviour. Saying “the program always crashes if another thread unlocks it” is not accurate.

Monitor

A monitor is a language-level construct that hides the lock and the waiting conditions inside an object. Only one thread at a time can be inside its methods. To wait for a condition (such as a non-empty queue), a thread uses a condition variable: wait() releases the lock and sleeps, and another thread wakes it with notify(). Java’s synchronized with wait()/notify() follows this model. Because the lock is taken on method entry and released on exit, mistakes like a missing signal() become less likely.

3. Deadlock

A deadlock is a situation in which each thread in a group waits for a resource held by another member of the group, so none can make progress. Two cars entering a single-lane bridge from opposite ends end up like this. Each waits for the other to back off.

The most common form in code is two threads taking two locks in opposite order:

a, b = threading.Lock(), threading.Lock()

def worker(first, second, name):
    with first:
        time.sleep(0.1)                  # let the other thread take its first lock
        if second.acquire(timeout=1):
            second.release()
            print(name, "done")
        else:
            print(name, "could not get the second lock")

threading.Thread(target=worker, args=(a, b, "T1")).start()
threading.Thread(target=worker, args=(b, a, "T2")).start()  # reverse order

Both threads print “could not get the second lock”. Without the timeout the program would wait forever. If both threads take a first and then b, the problem disappears.

The Coffman conditions

A deadlock requires four conditions to hold at the same time:

  1. Mutual exclusion: Only one thread can use the resource at a time.
  2. Hold and wait: A thread holds one resource while waiting for another.
  3. No preemption: A resource cannot be taken away from the thread holding it.
  4. Circular wait: T1 waits for T2’s resource and T2 waits for T1’s.

Break any one and deadlock cannot occur.

Prevention, avoidance and detection

Prevention makes one of the conditions impossible by design. Hold and wait is broken by having a thread request all its resources at once. No preemption is broken by having a thread that cannot get its second lock release what it holds and retry (tryLock, locks with timeouts). Circular wait is broken by numbering the locks and having everyone acquire them in increasing order. The last one is the most widely used in practice. Breaking mutual exclusion is usually impossible.

Avoidance checks on every request whether the system will stay safe. The well-known example is the Banker’s algorithm. Each process declares up front the maximum resources it may need. When a request comes in, the system checks whether, after granting it, there is still an order in which every process can finish. If there is, the state is a safe state and the request is granted. Otherwise the process waits. A bank behaves the same way when it refuses a new loan because its cash could no longer cover every customer’s worst-case demand. Since maximum needs must be known in advance, general-purpose operating systems rarely use it.

Detection and recovery lets deadlocks happen and checks for them periodically. The system builds a wait-for graph showing who waits for whom and searches it for a cycle. If one is found, a process is terminated or its resources are taken back. Databases work this way: of two transactions waiting for each other, one is rolled back.

The fourth option is to ignore the problem. Most general-purpose operating systems do this for application-level deadlocks, and getting the lock order right is left to the programmer.

4. Livelock and starvation

Livelock is a state in which threads are not blocked and keep doing something, yet none makes progress. Two people in a narrow corridor both step right, then both step left, and so on. Two threads that release their lock and retry immediately on failure can fall into the same rhythm. The fix is to wait a random amount of time before retrying.

Starvation happens when a thread is able to run but its turn never comes. The scheduling case from Part 8 shows up with locks too. An unfair lock may keep going to the same threads. Fair locks in Java, such as new ReentrantLock(true), hand the lock to waiters in arrival order.

5. Virtual memory and paging

Virtual memory gives each process the impression of a large address space of its own, starting from zero. The virtual address a process sees is translated by the hardware MMU (memory management unit) into a physical address in RAM. As a result, processes cannot see each other’s memory, and parts of a program not in use can stay on disk.

Pages, frames and the page table

Paging does the translation in fixed-size blocks. The virtual address space is split into equal pages, and physical RAM into frames of the same size. A typical size is 4 KB. Which page sits in which frame is recorded in each process’s own page table. It is like the loose pages of a ring binder: each page can go into any free slot on the shelf, and an index records where it is.

Translation starts by splitting the address into a page number and an offset within the page. With 4096-byte pages, for virtual address 20000:

  • Page number = 20000 / 4096 = 4 (integer division)
  • Offset = 20000 − 4 × 4096 = 3616

If page 4 is in frame 9, the physical address is 9 × 4096 + 3616 = 40480. The offset stays the same, and only the page number is replaced by the frame number.

TLB

The page table itself lives in memory. If every access had to read it first, memory accesses would be at least twice as slow. The TLB (translation lookaside buffer) is a small hardware cache of recently used page-to-frame mappings. On a TLB hit translation is almost free. On a TLB miss the page table is read and the result is stored in the TLB. Programs keep accessing the same regions, so the hit rate is very high. The “cold TLB” mentioned in Part 8 as an indirect cost of context switches comes from here.

Page fault

When a process accesses a page that is not in RAM, the MMU raises a page fault. Despite the name, it is usually routine work for the operating system:

  1. The CPU switches to the kernel.
  2. The kernel finds where the page is on disk.
  3. It picks a free frame, or evicts a page if there is none.
  4. It reads the page into the frame and updates the page table.
  5. The faulting instruction is restarted.

Loading pages only when they are needed is called demand paging. A process touching an address it has no right to access is a different case: the kernel terminates it (a segmentation fault on Linux).

6. Page replacement algorithms

When RAM is full and a new page is needed, a page replacement algorithm decides which page to evict.

  • FIFO (first in, first out): The page that entered RAM first is evicted. It may evict an old page that is still in heavy use.
  • LRU (least recently used): The page unused for the longest time is evicted. Exact LRU is expensive in hardware, so operating systems use approximations such as Clock (Second Chance).
  • Optimal (OPT): The page that will be used furthest in the future is evicted. It gives the fewest faults but needs to know the future, so it serves only as a yardstick.

Worked example: 3 frames, 12 accesses

The reference string is 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5, there are 3 frames, and all are empty at the start. The “Fault” row shows whether a page fault occurred, with the evicted page in brackets.

FIFO:

Access 1 2 3 4 1 2 5 1 2 3 4 5
F1 1 1 1 4 4 4 5 5 5 5 5 5
F2 2 2 2 1 1 1 1 1 3 3 3
F3 3 3 3 2 2 2 2 2 4 4
Fault yes yes yes yes (1) yes (2) yes (3) yes (4) no no yes (1) yes (2) no

9 page faults in total. When 4 arrives, page 1 is the oldest, so it goes, and right after that 1 is requested and loaded again. FIFO does not look at how often a page is used, which is why it loses pages like this.

LRU:

Access 1 2 3 4 1 2 5 1 2 3 4 5
F1 1 1 1 4 4 4 5 5 5 3 3 3
F2 2 2 2 1 1 1 1 1 1 4 4
F3 3 3 3 2 2 2 2 2 2 5
Fault yes yes yes yes (1) yes (2) yes (3) yes (4) no no yes (5) yes (1) yes (2)

10 page faults in total. The first seven steps match FIFO. When 3 arrives, 1 and 2 were just used, so 5 goes, but 5 is requested again two steps later. LRU usually beats FIFO, but not on this string.

With Optimal, when 4 arrives, 1 and 2 are needed soon and 3 last, so 3 goes. When 5 arrives, 4 goes for the same reason. When 3 arrives, neither 1 nor 2 is used again, so either can go. 7 page faults in total. With 3 frames, no algorithm can do better on this string.

Algorithm 3 frames 4 frames
FIFO 9 10
LRU 10 8
Optimal 7 6

I checked these numbers with a small Python simulation, and they match the hand calculation.

The second column holds a surprise. With FIFO, going from 3 frames to 4 raises the faults from 9 to 10, so more memory gives a worse result. This is called Belady’s anomaly. LRU and Optimal do not show it, because the pages they keep in k frames are always a subset of what they would keep in k+1 frames.

7. Thrashing

Thrashing is the state in which a system spends most of its time moving pages between disk and RAM and gets almost no useful work done. It is like working with four books on a desk that holds two. All the time goes into carrying books between shelf and desk.

The set of pages a process actively uses over a short window is its working set. When the combined working sets of the running processes exceed RAM, each process keeps asking for a page another one has just evicted. The symptom is typical: the disk is constantly busy, CPU usage is low, and the system feels frozen. Some old schedulers saw the low CPU usage, admitted more processes and made it worse.

The fix is to reduce the number of processes running at once (the degree of multiprogramming) or to add RAM. Operating systems try to do this automatically with the working set model (run a process only if its working set fits) or with page fault frequency (give more frames to a process whose fault rate rises).

Paging and swapping are often used as if they meant the same thing. Paging is managing memory in pages, and it works even when RAM is plentiful. Writing pages out to disk and reading them back (swapping) happens on top of it. Thrashing is that traffic getting out of control.

8. Fragmentation and segmentation

Fragmentation means free memory exists but cannot be used.

Internal fragmentation: If an allocated block is larger than needed, the unused part inside the block is wasted. With 4 KB pages, 10 KB of data takes three pages and 2 KB of the last page goes unused. It is like shipping a small item in a large box.

External fragmentation: The total free memory is enough, but it is not contiguous. With 15 MB free but the largest gap at 5 MB, a 10 MB request cannot be satisfied. It is like a cinema with ten empty seats where a group of four still cannot sit together.

Internal External
Where the waste is Inside an allocated block Between allocated blocks
Cause Fixed-size blocks Variable-size allocation
Where it appears Paging, fixed partitioning Segmentation, dynamic partitioning
Mitigation Smaller block size Compaction, paging

“Best fit” is sometimes given as the fix for internal fragmentation, which is wrong. Best fit, first fit and worst fit are strategies for choosing a hole in variable-size allocation, so they address external fragmentation. What reduces internal fragmentation is a smaller block size, at the cost of a larger page table.

Compaction slides allocated blocks to one end of memory and merges the gaps. It is expensive, because everything that moves gets a new address. Disk defragmentation is a separate job that deals with file pieces on a disk. Paging solves the problem at the root: every frame is the same size, so any free frame fits any page. What remains is a little internal fragmentation in the last page.

Segmentation divides memory into the logical parts of a program (code, data, stack, heap) instead of fixed pages. Each segment has its own size and access permissions. Because segments vary in size, it is prone to external fragmentation. On today’s 64-bit systems segmentation is largely disabled and memory is managed with paging.

Interview questions

1. What is a race condition and how do you prevent it? It is when several threads access shared data concurrently, at least one writes, and the result depends on execution order. The code that touches shared data is treated as a critical section and protected with a lock such as a mutex. Atomic operations or immutable data can also solve it. Common mistake: Assuming count += 1 is a single operation.

2. What is the difference between a mutex and a binary semaphore? A mutex has an owner: the thread that locks it unlocks it, and its purpose is to protect shared data. A binary semaphore has no owner, so one thread can call wait() while another calls signal(). That is why it is used for signalling between threads. Common mistake: Saying “both take 0 and 1, so they are the same thing”.

3. What are the four conditions for deadlock, and how is it prevented? Mutual exclusion, hold and wait, no preemption and circular wait. All four must hold at once, and breaking one prevents deadlock. In practice circular wait is the easiest to break, by acquiring all locks in a fixed order. The Banker’s algorithm takes a different route and runs every request through a safe-state check, which is avoidance. Common mistake: Listing the conditions without being able to say how each one can be broken.

4. How do deadlock, livelock and starvation differ? In deadlock the threads are blocked and none progresses. In livelock the threads keep running, yet none progresses. In starvation the system makes progress, but one thread’s turn never comes. Common mistake: Calling livelock a kind of deadlock. A livelock burns CPU.

5. What is a page fault? Is every page fault an error? It is an access to a page that is not in RAM. The operating system loads the page from disk and the instruction runs again. This is normal, and demand paging depends on it. Common mistake: Confusing a page fault with a segmentation fault.

6. What is the TLB and why is it needed? It is a small hardware cache of virtual-to-physical address mappings. Without it, every memory access would first need a page table lookup in memory. After a context switch its contents are largely useless. Common mistake: Confusing the TLB with the CPU’s data caches (L1/L2).

7. The system is very slow, the disk is constantly busy, but CPU usage is low. What could be wrong? Most likely thrashing. The working sets of the running processes do not fit in RAM and the system spends its time servicing page faults. The fix is to run fewer processes at once or add RAM. Common mistake: Seeing low CPU usage and starting more work.
