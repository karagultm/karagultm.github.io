Memory: The Stack and the Heap, Garbage Collection and Memory Leaks

Programming 101, Part 5

Part 4 said in passing that when new is called, the object is created on the heap. This post opens up that sentence: what is the heap, what is the stack next to it for, and where do objects go when they are no longer needed?

Memory questions in interviews usually come as a follow-up to OOP questions. The difference between the stack and the heap, the difference between == and equals, when the garbage collector removes an object, and whether a memory leak is possible when there is a garbage collector are the most common ones. Most examples are in Java. At the end I look briefly at how Python and C/C++ do the same job.

The order is: first the stack and the heap, then values and references, == vs. equals, two memory errors, the garbage collector, memory leaks in Java, Python and C/C++. At the end there are common interview questions with short answers.

1. The stack and the heap

A running Java program splits memory into regions with different purposes. The two that come up in interviews are the stack and the heap.

The Stack is a memory region that belongs to a single thread and keeps track of method calls. When a method is called, a Stack Frame for that call is pushed on top of the stack. The frame holds the method’s parameters, its local variables, and the information about where to return when the method finishes. When the method returns, the frame is popped and everything in it goes with it.

This layout works like a stack of plates. A new plate goes on top, and the top plate is the one taken off. Pulling a plate out of the middle is not possible. That is why allocating and freeing on the stack is very cheap: a single pointer moves up or down.

The Heap is the memory region where every object created with new lives, and it is shared by all threads of the program. The lifetime of an object on the heap is not tied to the method that created it. The method ends, the object stays. The object lives until no path leads to it any more, and then the garbage collector cleans it up.

void createOrder() {
    int quantity = 3;                    // stack: inside the frame, the value itself
    Order o = new Order("pen");          // o is on the stack, the Order object on the heap
    o.setQuantity(quantity);
}   // method done: quantity and o are gone, the Order object stays on the heap

The variable o is not the object itself but a reference to it. The reference is removed with the frame. If nothing else refers to the object, it is now unreachable and goes away in the next collection.

Stack Heap
Owned by Each thread has its own stack Shared by all threads
Holds Frames: parameters, local variables Objects and arrays created with new
Lifetime Ends when the method returns Lasts until unreachable
Cleaned by Automatically, when the frame is popped The garbage collector
Size Small, fixed (1 MB on most 64-bit systems, changed with -Xss) Large, limited by -Xmx
When it overflows StackOverflowError OutOfMemoryError

Because each thread has its own stack, local variables are not shared between threads, so they cannot have a race condition. If two threads can reach the same object on the heap at the same time, synchronization is needed.

2. Values and references

Java variables come in two kinds. Primitive Type variables hold the value itself: int, long, double, boolean, char, byte, short, float. Reference Type variables point to where an object lives on the heap. Classes, arrays, String and wrapper classes such as Integer belong to this group.

On assignment, both kinds copy the value stored in the variable. For a primitive that value is the number itself. For a reference, what gets copied is the address. The object is not copied, and the two variables now point to the same object.

Method calls work the same way. Java always uses Pass-by-Value. For a reference type, the value passed is a copy of the reference.

static void change(int number, Point p) {
    number = 99;   // only the local copy changes
    p.x = 99;      // the copied reference points to the same object, the object changes
}

static void reassign(Point p) {
    p = new Point(0, 0);   // the local reference now points elsewhere, the caller's does not
}

int a = 5;
Point pt = new Point(1, 2);
change(a, pt);       // a is still 5, pt.x is now 99
reassign(pt);        // pt.x is still 99

When a field of the object changes inside the method, the change is visible outside, because both references point to the same object. But when a new object is assigned to the parameter itself, the caller’s variable is not affected. That is why “Java passes objects by reference” is wrong. With real pass-by-reference, reassign would also change the caller’s variable.

Primitives do not always live on the stack

The summary “objects live on the heap, primitives live on the stack”, which shows up often in notes, is incomplete. Where a primitive lives is decided by where it is declared, not by its type.

  • A primitive that is a local variable or a parameter lives on the stack, in that method’s frame.
  • A primitive that is a field of an object is part of that object and lives on the heap with it.
  • The elements of an array live on the heap too. new int[1000] allocates a thousand ints on the heap as a single object.
  • static fields belong to the class, not to any frame. They do not live on the stack either.
class Account {
    private double balance;   // a primitive, but inside the Account object: heap
}

void calculate() {
    double rate = 0.02;           // local primitive: stack
    int[] days = new int[30];     // the reference is on the stack, the 30 ints on the heap
}

The reverse also holds: a local reference variable is on the stack, and the object it points to is on the heap. There is also an optimization done by the JIT compiler. If Escape Analysis shows that an object never leaves the method, the JIT may skip creating the object and keep its fields like local variables. This is a runtime detail and does not change the meaning of the language. In an interview, “objects live on the heap” is the correct answer.

3. == vs. equals

For primitives, the == operator compares values. For references it checks whether the two references point to the same object, which means it compares addresses. The equals method says whether the contents of two objects count as equal, and each class defines what equality means for itself.

The default equals inherited from Object does the same thing as ==. Classes such as String, Integer and the collections override it to compare contents. Anyone who overrides equals in their own class must also override hashCode. Otherwise two objects that are equal end up in different places inside a HashMap.

String s1 = "java";
String s2 = "java";
String s3 = new String("java");

System.out.println(s1 == s2);        // true: both are the same object from the pool
System.out.println(s1 == s3);        // false: new created a separate object
System.out.println(s1.equals(s3));   // true: same contents

Integer i1 = 127, i2 = 127;
Integer i3 = 128, i4 = 128;
System.out.println(i1 == i2);        // true
System.out.println(i3 == i4);        // false
System.out.println(i3.equals(i4));   // true

The first true comes from the String Pool. String literals written in source code are kept once in a pool on the heap, and every place that writes the same text gets the same object. new String(...) skips the pool and creates a new object.

The Integer example is trickier. Writing Integer i = 127 makes the compiler turn it into a call to Integer.valueOf(127) (Autoboxing). valueOf returns a ready-made cached object for values between -128 and 127, and creates a new object for anything outside that range. That is why == happens to give the right answer at 127 and the wrong one at 128. This is the classic cause of code whose tests pass with small numbers and which breaks on real data. Objects are always compared with equals.

4. StackOverflowError and OutOfMemoryError

Both regions have a limit, and overflowing each one leads to a different error.

A StackOverflowError is thrown when a thread’s stack is full. The cause is almost always recursion that never ends or goes too deep. Each call pushes a new frame, and since none of them returns, none is popped.

static int factorial(int n) {
    return n * factorial(n - 1);   // no base case: every call adds a new frame
}

When I ran a simple method that calls itself unconditionally with default settings, the error came after about 19 thousand calls. The number depends on the frame size and the stack size. Recursion that is correct but very deep can cause the same error. In that case the fix is not a bigger stack but rewriting the algorithm with a loop or an explicit stack data structure.

An OutOfMemoryError is thrown when there is no room on the heap for a new object and the garbage collector cannot free any. The message points to the cause:

  • Java heap space: the heap is full and the live objects do not fit. Either the heap really is too small or there is a memory leak somewhere.
  • GC overhead limit exceeded: the program spends almost all its time in garbage collection and recovers very little space.
  • Metaspace: the area that holds class information is full. This shows up when many classes are generated and loaded at runtime.
static final List<byte[]> cache = new ArrayList<>();

public static void main(String[] args) {
    while (true) cache.add(new byte[1024 * 1024]);   // 1 MB per iteration
}
// java -Xmx32m ... -> OutOfMemoryError: Java heap space

Neither of them extends Exception. Both extend Error, which is for serious problems that the normal flow of a program is not expected to catch and recover from. Technically they can be caught with catch, but a program that catches OutOfMemoryError and carries on usually carries on in an inconsistent state.

5. The garbage collector

The Garbage Collector is the runtime component that finds objects on the heap that are no longer used and reclaims their space. Java has no command for deleting an object. The programmer creates objects, and the garbage collector decides when they are removed.

Reachability

The garbage collector decides whether an object is in use through Reachability. The starting points are references called GC Roots:

  • Local variables and parameters in the stack frames of running threads
  • static fields of loaded classes
  • The running thread objects themselves, and references held from native code

Every object that can be reached by starting at a root and following references is alive. An object that cannot be reached from any root is garbage, even if other objects still refer to it. If two objects point to each other but there is no path to either of them from outside, both are collected together. This is why Java does not use reference counting. Circular references are not a problem for it.

Mark-and-sweep

The most basic implementation of this idea is the Mark-and-Sweep algorithm. It has two phases. In the mark phase, every object reached from the roots is marked. In the sweep phase, the heap is scanned from start to end and the space of every unmarked object is recorded as free.

What is left is a heap full of gaps. Even when the total free space is enough, there may be no single block large enough for a big object. This is called Fragmentation. To prevent it, most collectors slide the live objects to one end of the heap (Compaction). It is like pushing the remaining books on a shelf to the left after some were taken out, so that the free space on the right is one piece.

Generational GC

Scanning the whole heap every time is expensive. In real programs most objects are short-lived: a temporary string created inside a loop, a list used while building the response to a request. This observation is called the Weak Generational Hypothesis, and Java’s collectors split the heap according to it.

  • Young Generation: new objects are placed here, in an area called Eden. When Eden fills up, only this region is scanned (Minor GC). Most short-lived objects are already dead by the first scan. The survivors are copied to the survivor spaces.
  • Old Generation: objects that survive several minor GCs are moved here (Promotion). This region is cleaned by a rarer and more expensive collection (Major GC or Full GC).

Since the share of garbage in the young generation is high, the cost of a scan there depends on the small number of live objects, not on the dead ones. That is why minor GCs run often but finish quickly.

Stop-the-world

While the collector works, the object graph must not change under it. The simplest way to ensure that is to stop all application threads. This pause is called Stop-the-World (STW). On the user’s side it shows up as a sudden jump in response time.

Most modern collectors do most of their work concurrently, while the application runs, and keep STW pauses short. Since Java 9 the default collector is G1. For cases where pauses must stay under a millisecond there are low-latency collectors such as ZGC. The choice is a trade-off between total work done (throughput) and pause time.

Two more details come up often. System.gc() does not force a collection, it is only a hint to the JVM. The finalize() method is not a reliable place for cleanup before an object is removed either. It is not known when, or whether, it will run, and it has been deprecated since Java 9.

6. Memory leaks in Java

A Memory Leak is memory that is no longer used but is never given back. In C this usually happens when a call to free is forgotten. In a language with a garbage collector the definition shifts a little: the program will never use an object again, but there is still a path to it from a root. The garbage collector cannot know the program’s intent. It treats every reachable object as alive.

A leak is not noticed right away. The heap fills slowly, the garbage collector runs more and more often, and finally an OutOfMemoryError arrives. Often the application has to run for days before this shows.

A growing static collection

The most common cause is a static collection that keeps getting new elements and never loses any. A static field is a GC root, and everything in it lives until the program ends.

static final Map<String, Session> sessions = new HashMap<>();

static void loggedIn(String userId) {
    sessions.put(userId, new Session());
}
// if remove is forgotten in loggedOut(), every session stays forever

Maps used as caches have the same problem. The fix is a cache with a size limit or an expiry time, or removing the element explicitly when its work is done. WeakHashMap helps in some cases. An entry drops out on its own once there is no other strong reference to its key.

A resource that is never closed

Resources such as files, database connections and sockets also take up space outside the heap, on the operating system side. The garbage collector only manages the heap. A file that is never closed holds the operating system’s file handle until the Java object representing it is collected, which may be at some unknown time or never. In connection pools, a connection that is not closed never returns to the pool, and the pool runs dry.

Since Java 7 there is the try-with-resources statement for this. Any resource that implements the AutoCloseable interface and is opened inside the parentheses is closed automatically when the block ends. It is closed even if the block ends with an exception.

static String firstLine(Path path) throws IOException {
    try (BufferedReader r = Files.newBufferedReader(path)) {
        return r.readLine();
    }   // r.close() is called here, with or without an error
}

This is shorter and safer than the old try/finally pattern. Several resources can go in the same parentheses, separated by semicolons, and they are closed in the reverse order of opening.

A listener that stays registered

An object registers itself as a listener on an event source, then its work ends, but the registration is never removed. The event source’s list holds the listener, and the listener usually holds the object that registered it. In this way a screen that was already closed, or a task that already finished, stays in memory with all its fields.

class Screen {
    private final byte[] buffer = new byte[10_000_000];

    Screen(EventSource source) {
        source.add(s -> draw(s));   // the lambda captures this, so Screen stays in the source
    }
    void draw(String s) { }
}

When I tried this, creating 50 of these screens with a 256 MB heap gave an OutOfMemoryError, even though nothing outside held a reference to any screen. Each lambda captures this because it calls the draw method, and the source’s list holds the lambdas. The fix is to remove the registration with source.remove(...) when the object’s life ends. Non-static inner classes carry the same kind of hidden reference to an instance of the outer class.

7. Python: reference counting and the cycle collector

In Python (in CPython, the standard implementation) everything is an object and every object lives on the heap, int included. Local variables are only names bound to these objects.

CPython’s main mechanism is Reference Counting. Every object counts how many references point to it. The count goes up when a name is bound to the object and down when the binding is broken. The moment the count reaches zero the object is freed, with no scan to wait for.

import sys

a = []
print(sys.getrefcount(a))   # 2: a, plus the function's own argument
b = a
print(sys.getrefcount(a))   # 3
del b                       # deletes the name b, not the object
print(sys.getrefcount(a))   # 2

Reference counting has a well-known weakness: cycles. If two objects point to each other, their counts never reach zero even when no path from outside is left. For this, CPython runs a second mechanism, the cycle collector in the gc module. It only looks at objects that can hold other objects (lists, dicts, class instances), works by generations, and finds and frees unreachable cycles.

import gc

class Node:
    def __init__(self):
        self.other = None

x, y = Node(), Node()
x.other, y.other = y, x    # a cycle
del x, y                   # the counts do not reach zero
print(gc.collect())        # number of unreachable objects found, greater than zero

The difference from Java: in Python most objects are freed the moment their last reference is gone, so the point of removal is largely predictable. Even so, files are opened with a with block. It is the counterpart of Java’s try-with-resources and does not leave closing to the reference count.

8. C and C++: manual memory management

C has no garbage collector. Memory is taken from the heap with malloc and given back with free, and the programmer writes both. In C++ the counterparts are new and delete. You wash the plate you used and put it back in the cupboard yourself, because nobody tidies up after you.

int *arr = malloc(100 * sizeof(int));   // space from the heap
if (arr == NULL) return -1;             // allocation failed
/* ... use it ... */
free(arr);                              // give it back
arr = NULL;                             // so the old address is not kept around

This model is fast and predictable, with no garbage collection pauses. The price is that mistakes are left to the programmer:

  • Memory leak: free is forgotten. The memory stays taken until the process ends.
  • Dangling Pointer and Use-after-free: memory that was already freed is still accessed. The program can crash or overwrite some other data. Bugs of this kind are a common source of serious security vulnerabilities.
  • Double Free: the same memory is freed twice.

Modern C++ reduces this burden a lot with RAII. A resource is acquired in an object’s constructor and released in its destructor. Since the object lives on the stack, the destructor runs on its own when the object goes out of scope. Smart pointers such as std::unique_ptr and std::shared_ptr manage heap memory this way. shared_ptr counts references, so it has the same cycle problem as Python, solved with weak_ptr.

C / C++ Java Python (CPython)
Getting heap memory malloc / new new Whenever an object is created
Giving it back The programmer: free / delete (RAII in C++) The garbage collector, by tracing When the reference count hits zero, gc for cycles
Circular references The programmer’s problem Not a problem Handled by the cycle collector
Closing resources Destructor (RAII) try-with-resources with block
Typical bug Leak, use-after-free Unneeded object that stays reachable Cycles and global caches

A note on the operating system side: when a process ends, the operating system takes back all of its memory. The damage from a leak shows in long-running programs, such as servers. There memory use grows over time and the process eventually dies from running out of memory.

Interview questions

1. What is the difference between the stack and the heap? The stack belongs to a single thread and holds the frames of method calls, which are removed automatically when the method returns. The heap is shared by all threads and holds the objects created with new. Objects on the heap are cleaned up by the garbage collector once they become unreachable. Common mistake: Confusing them with the stack and heap data structures. The names are the same, the jobs are different.

2. Do primitives always live on the stack? No. A primitive that is a local variable or a parameter is on the stack. A primitive that is a field of an object or an element of an array is on the heap, together with that object. Common mistake: Deciding the location by type. What decides it is where the variable is declared.

3. Is Java pass-by-value or pass-by-reference? Always pass-by-value. For reference types the value passed is a copy of the reference, which is why a method can change an object’s fields. But assigning a new object to the parameter does not change the caller’s variable. Common mistake: Seeing a field change and concluding that “objects are passed by reference”.

4. What is the difference between == and equals? For references, == checks whether two variables point to the same object. equals compares contents, and the class defines what equality means. If equals is overridden, hashCode must be overridden too. Common mistake: Comparing Integer values with ==. It works between -128 and 127 because of the cache, and breaks at 128.

5. What is the difference between StackOverflowError and OutOfMemoryError? StackOverflowError comes when a thread’s stack is full, usually from recursion that never ends or goes too deep. OutOfMemoryError comes when there is no room on the heap and the garbage collector cannot free any. Both are Errors and are not meant to be caught and recovered from in the normal flow. Common mistake: Explaining StackOverflowError as “memory is full”. What is full is not the heap but one thread’s stack.

6. How does the garbage collector decide that an object can be removed? It starts from GC roots (local variables on stacks, static fields, running threads) and follows references. Every object that cannot be reached is garbage, including objects that point to each other. The heap is split into a young and an old generation, and short-lived objects are cleaned up by frequent, cheap collections. Common mistake: Saying that Java uses reference counting. Circular references do not cause leaks in Java.

7. Can a memory leak happen in a language with a garbage collector? Yes. If the program keeps a reference to an object it will never use again, the object stays reachable and is not collected. Growing static collections, listener registrations that are never removed and unclosed resources are the most common causes. Common mistake: Leaving resource cleanup to the garbage collector. Files and connections are handled with try-with-resources.

8. How does Python’s memory management differ from Java’s? CPython counts references first and frees an object the moment its count reaches zero. A separate cycle collector handles the cycles that reference counting cannot catch. Java does not count references and uses a tracing collector based on reachability. Common mistake: Thinking that del x deletes the object. It only deletes the name, and the object is freed when its last reference is gone.
