Operating Systems 1: Processes, Threads and Scheduling

Programming 101, Part 8

This post is about the most basic question in operating systems: there are only a few CPUs and many programs that want to run. Who gets the CPU next, and for how long?

Music is playing, a few browser tabs are open, and a project is compiling in the background. All of it seems to run at once, but a core executes one thing at any given moment. The operating system creates the impression of parallel work by switching between jobs thousands of times per second.

Below I cover what processes and threads are, how the operating system switches between them, and which algorithms decide the order. At the end there are common interview questions with short answers.

1. What does an operating system do?

An Operating System (OS) is the software that sits between the hardware and the programs. It divides CPU time, memory, files and devices among programs.

At the center of this work is the Kernel. The kernel is the piece of code that always stays in memory and has the widest privileges.

It works like a building manager. Residents do not go down to the boiler room themselves, they tell the manager the heating is off. Programs do not touch the hardware either, they pass their requests to the kernel.

2. User mode, kernel mode and system calls

The CPU runs in two modes:

  • User Mode: Applications run here. They cannot access hardware directly.
  • Kernel Mode: The kernel runs here. It can access the disk, the network card and all of memory.

When a program wants to open a file, it cannot do it on its own and has to ask the kernel. That request is a System Call. The flow:

  1. The program makes a system call (“open this file”).
  2. The CPU switches to kernel mode.
  3. The kernel does the work.
  4. Control returns to user mode.

Opening a file, sending data over the network and creating a new process all go through this path.

In Python, open("log.txt") turns into an openat system call on Linux. You can see this with strace:

strace -e trace=openat,read,write cat log.txt

The output shows openat(...), read(...) and write(...) lines. Even cat does not read the file itself, it asks the kernel.

The reason for the split is safety and stability. A program that crashes in user mode only takes itself down. It cannot lock up the system.

3. Program vs. process

A Program is a passive file sitting on disk. A Process is that program while it runs. A program is like a recipe, and a process is the cook making the dish from that recipe in a kitchen.

Several processes can run from the same program. Open three browser windows and look at Task Manager or the output of ps aux, and the same program shows up as several rows. Each has its own PID (Process ID) and its own memory space. One recipe, several cooks.

4. PCB: the record of a process

The operating system keeps a PCB (Process Control Block) for every process. On Linux this structure is called task_struct.

It can be compared to a patient file in a hospital. When the shift changes, the new doctor reads the file and continues the treatment from where it stopped. When the CPU returns to a process, it reads from the PCB where that process left off. A PCB contains:

Field Purpose
PID, parent PID Identity and who the parent is
State ready, running, waiting…
Program counter + registers To resume where it left off
Scheduling info Priority, how much CPU it has used
Memory info Address mappings such as the page table
Open files List of file descriptors

5. Process states

A process goes through five states during its life:

  1. New: Being created.
  2. Ready: Ready to run, waiting for its turn on the CPU.
  3. Running: Currently executing on a core.
  4. Waiting / Blocked: Waiting for an event. This can be a disk read, a network response or user input.
  5. Terminated: Finished.

A bank queue maps well onto these states. When you walk into the bank and take a number, you are ready. When the teller calls you, you are running. If the teller asks for a signed document, you leave to get it, and that is waiting. When you come back with the document, you cannot walk straight to the counter. You take a new number and you are ready again.

Transitions to watch

  • Running -> Ready: Its time ran out and the scheduler took it off the CPU.
  • Running -> Waiting: It started I/O (a request to the disk or network).
  • Waiting -> Ready: The I/O finished and the process went back into the queue.

The last one is where most interview mistakes happen. A process whose I/O has finished does not go straight to running. It enters the ready queue first.

6. Processes and threads: what is shared and what is not

A Thread is a unit of execution inside a process. A process can have more than one thread.

A useful picture is a process as a house and its threads as housemates. The kitchen and the fridge are shared (code, heap). Each person has their own notebook and their own page in it (stack, program counter). Separate processes are separate houses, and nobody can open the neighbor’s fridge.

Between threads
Shared Code, global variables, heap, open files
Not shared Stack, registers, program counter, thread ID

A small example shows the difference:

import threading, multiprocessing

data = []  # shared list

def add(x):
    data.append(x)

if __name__ == "__main__":
    t = threading.Thread(target=add, args=(1,))
    t.start(); t.join()
    print(data)   # [1]  the thread saw the same memory

    p = multiprocessing.Process(target=add, args=(2,))
    p.start(); p.join()
    print(data)   # [1]  the process wrote to its own copy

The thread appended to the list and the main program saw it. The separate process wrote to its own copy of memory, so the list in the main program did not change.

Threads are lightweight and communicate easily because they see the same memory. The cost is the bugs that appear when shared memory is written at the same time. Processes are isolated from each other, so if one crashes the others are not affected. In exchange, communication between them takes more work. Part 2 covers the problems of shared memory.

7. Context switches and their cost

When the CPU moves from one process or thread to another, it performs a Context Switch. The registers and program counter of the running job are saved to its PCB, and the values of the next job are loaded from its own PCB. If the switch is to a different process, the memory mapping changes as well.

It is like two people sharing one computer: the one getting up saves their game, the one sitting down loads theirs. Nobody is playing in between.

The cost has two parts:

  • Direct cost: The time to save and load. It is on the order of microseconds, and no user work happens during it. This part is pure overhead.
  • Indirect cost: The CPU caches and the TLB start cold for the new process’s data, and the data it needs has to be loaded again. In practice this is usually the expensive part.

Switching between threads of the same process is generally cheaper, because the memory mapping does not change.

8. Scheduling: who gets the CPU?

The Scheduler decides which of the jobs waiting in the ready queue will run. The first distinction is whether a running job can be interrupted.

Non-Preemptive

The running job stays on the CPU until it finishes or gives up the CPU itself (for example, by going to I/O). A bank teller works this way. However long the current customer’s business takes, the teller does not stop halfway, even if the person behind is in a hurry.

Preemptive

The operating system can stop the running job when its time runs out or when a more important job arrives. A doctor in the emergency room who is changing a dressing will leave it if someone comes in with a heart attack. The cost is more frequent context switches.

All of today’s general-purpose desktop and mobile operating systems are preemptive. Otherwise a single program stuck in an infinite loop would lock the whole machine, and the mouse pointer would not move.

Algorithms

  • FCFS (First Come, First Served): Jobs run in arrival order. It is simple. The problem is that a long job at the front makes the short jobs behind it wait. This is called the Convoy Effect, similar to being stuck behind a truck on the highway.
  • SJF (Shortest Job First): The shortest job runs first. It minimizes the average waiting time. But the length of a job is not known in advance, it has to be estimated. The preemptive version is called SRTF.
  • Round Robin (RR): Each job gets a fixed Time Quantum in turn. A job whose time runs out moves to the end of the queue.
  • Priority: The job with the highest priority runs. It can be preemptive or non-preemptive.

Round Robin is easy to picture as three friends sharing one computer. The rule: everyone plays for 10 minutes in turn. P1 sits down, and when the 10 minutes are up, P1 gets up and goes to the back of the line even if the level is not finished. Then P2 and P3 play. When it is P1’s turn again, P1 continues from where it stopped. For interviews, the phrase to keep in mind for Round Robin is “in turn, with equal time”.

Worked example: 3 processes, 3 algorithms

All three processes arrive at t=0, in the order P1, P2, P3. Context switch time is taken as zero.

Process Burst (CPU time)
P1 8
P2 4
P3 2

Formulas used:

  • Turnaround = completion − arrival
  • Waiting = turnaround − burst

FCFS: P1 [0–8], P2 [8–12], P3 [12–14] Waiting: 0, 8, 12 -> average 6.67

SJF: P3 [0–2], P2 [2–6], P1 [6–14] Waiting: P3=0, P2=2, P1=6 -> average 2.67

Round Robin (quantum = 2):

Time 0–2 2–4 4–6 6–8 8–10 10–12 12–14
On CPU P1 P2 P3 (done) P1 P2 (done) P1 P1 (done)
Remaining P1:6 P2:2 P3:0 P1:4 P2:0 P1:2 P1:0
Process Completion Turnaround Waiting First time on CPU
P1 14 14 6 0
P2 10 10 6 2
P3 6 6 4 4
Avg. 10 5.33 2

SJF gives the best average waiting time, but it requires knowing job lengths in advance. Where RR does well is Response Time. No process waited more than 4 units to get on the CPU for the first time, and the average was 2. In FCFS, P3 did not see the CPU at all for 12 units.

How long should the quantum be?

If the quantum is too short, most of the time goes to context switches and the real work moves slowly. If it is too long, RR effectively turns into FCFS, the jobs in line wait a long time and the system feels frozen.

Starvation and Aging

Starvation is when a process never gets its turn. In a system using priority scheduling, if high-priority jobs keep arriving, a low-priority backup job can wait indefinitely. The same happens in SJF, where long jobs can starve.

Aging means raising the priority of a waiting process over time. For example, its priority goes up by 1 for every 100 ms it waits. Eventually it reaches the top level and runs. It is like moving someone who has waited in line for a long time to the front after a while.

9. Zombie and orphan processes

A Zombie Process is a process that has finished and released its memory but has not yet been removed from the process table. The name sounds odd, but it is part of the normal working of the operating system.

On Linux, a process creates a Child process with fork(). When the child finishes, it is not removed completely right away. It keeps a row in the process table until the Parent reads its Exit Status. The row is kept so the parent can find out whether the child succeeded.

It is like a customer in a restaurant who has finished eating but cannot leave because the waiter has not come to take the bill. The customer no longer consumes anything, but the table still shows as taken. Here the waiter is the parent, and taking the bill is the wait() call.

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {              // child: work is done
        printf("child %d done\n", getpid());
        exit(0);
    }
    sleep(30);                   // parent waits without calling wait()
    wait(NULL);                  // child is reaped after 30 s
    return 0;
}

During those 30 seconds, in another terminal:

ps -o pid,ppid,stat,cmd
# 4122 4121 Z   [a.out] <defunct>

The Z state and the <defunct> label mark the zombie. The fix is to call wait() right away, or to handle the SIGCHLD signal and reap the child there.

When does it become a problem?

A few zombies are not a problem. They use no CPU or RAM and take up one row in the table. If a buggy server creates thousands of children and reaps none of them, the PIDs run out and no new process can start, because there are no ID numbers left to hand out.

A zombie cannot be killed with kill -9, because it has already finished. The fix is to correct the parent or terminate it.

Orphan processes

In the reverse case the parent dies first while the child is still running. The child is adopted by init/systemd (PID 1), which reaps it with wait() when it finishes. For this reason orphan processes usually cause no trouble. Zombies whose parent has died are cleaned up by PID 1 the same way.

As short definitions, a zombie is a process that has finished but has not been removed from the table. An orphan is a process whose parent has died but which keeps running.

10. CPU-bound or I/O-bound?

  • CPU-Bound: Spends most of its time computing. Image processing and encryption are examples. In terms of process states, it is mostly running.
  • I/O-Bound: Spends most of its time waiting. A database query or an HTTP request, for example. It is mostly waiting.

The right tool depends on this. CPU-bound work needs more than one core: Multithreading (Task.Run in C#) or Multiprocessing. For I/O-bound work, what matters is not tying up a thread while it waits, and that is where Async/Await is used.

An e-commerce API sending a request to a payment service and waiting for the response is I/O-bound work. With await the thread is released and serves other requests. Resizing product images is CPU-bound work.

Python has one detail here. In CPython, because of the GIL, only one thread executes Python code at a time. So adding threads to CPU-bound work does not speed it up, and multiprocessing is needed.

Interview questions

1. What is the difference between a process and a thread? A process is a running program with its own isolated memory space. A thread is a unit of execution inside a process. Threads in the same process share code, heap and open files, but each has its own stack and registers. Common mistake: Saying “threads share nothing” or “they share the stack too”.

2. What is a context switch, and why is it expensive? It is the CPU saving the state of one execution unit to its PCB and loading the next one when it switches. No useful work happens during that time, and the cache and TLB go cold. Common mistake: Counting only the save time and forgetting the cache effect.

3. What is the difference between preemptive and non-preemptive scheduling? In preemptive scheduling the OS can forcibly stop the running job (when the quantum expires or a higher-priority job arrives). In non-preemptive scheduling the job stays on the CPU until it finishes or gives it up. Modern general-purpose operating systems are preemptive. Common mistake: Calling Round Robin non-preemptive.

4. How do you choose the quantum in Round Robin? If it is too short, context switch overhead dominates. If it is too long, RR turns into FCFS and response time gets worse. The quantum should be much larger than the context switch time and a bit longer than the CPU burst of a typical interactive job. Common mistake: Saying “the shorter, the fairer”.

5. What is starvation, and how is it prevented? It is when a process never gets its turn on the CPU. It occurs with priority scheduling and SJF. It is prevented with aging, which raises the priority of a waiting process over time. Common mistake: Confusing starvation with deadlock.

6. What are zombie and orphan processes? A zombie is a finished process that stays in the process table because its parent has not called wait(). An orphan is a process whose parent died first and which is still running. It is adopted by PID 1. If zombies pile up, the PIDs can run out. Common mistake: Saying “I’ll kill the zombie with kill -9”.

7. What is a system call? Why is there a user/kernel mode split? It is a program in user mode requesting a service from the kernel (read, write, fork). The split stops programs from touching hardware directly and crashing the system. Common mistake: Assuming every library function is a system call (printf ends up calling write, but it is not a system call itself).

8. Can you speed up CPU-bound work with async/await? No. Async makes good use of waiting time, it does not parallelize computation. CPU-bound work needs threads or processes that spread it across several cores. Common mistake: Thinking async means “running in parallel in the background”.
