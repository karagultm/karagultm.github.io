Databases and SQL: Query Order, JOINs, Indexes, ACID and Normalization

Programming 101, Part 13

Part 12 covered how an HTTP request reaches the server, along with REST, JWT and sessions. Where that request lands, a database query usually runs. This post is about that query: how it is evaluated, how it gets faster, and how concurrent writes avoid corrupting each other.

I ran every example with Python’s sqlite3 module (SQLite 3.45), and the outputs in the tables come from those runs. Where SQLite lacks a feature, I say so in place.

1. Sample tables

Two small tables are used throughout the post: customers and orders.

CREATE TABLE customers (id INTEGER PRIMARY KEY, name TEXT, city TEXT);
CREATE TABLE orders (id INTEGER PRIMARY KEY, customer_id INTEGER, amount INTEGER, order_date TEXT);

INSERT INTO customers VALUES (1, 'A', 'Ankara'), (2, 'B', 'Izmir'), (3, 'C', 'Ankara');
INSERT INTO orders VALUES
  (101, 1, 250, '2026-01-05'), (102, 1, 100, '2026-02-10'),
  (103, 2, 400, '2026-02-11'), (104, 4,  80, '2026-03-01');

Customer C has no orders. Order 104 belongs to customer 4, who does not exist. In a real schema a Foreign Key would prevent that. Here it is left in on purpose to show the differences between JOINs.

2. The logical execution order of a query

A SQL query starts with SELECT, but the database does not evaluate it in that order. The logical order is:

FROM / JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT -> DISTINCT -> ORDER BY -> LIMIT

Each step works on the intermediate table produced by the previous one.

SELECT customer_id, SUM(amount) AS total
FROM orders
WHERE amount > 50
GROUP BY customer_id
HAVING SUM(amount) > 200
ORDER BY total DESC
LIMIT 10;
customer_id total
2 400
1 350

Customer 4 has a total of 80, so HAVING removed it. ORDER BY total works because sorting comes after SELECT, and the name total exists at that point.

For the same reason an alias cannot be used in WHERE. If SELECT amount * 1.2 AS gross is followed by WHERE gross > 200, then at the time WHERE runs, SELECT has not been evaluated yet and there is no column called gross. In standard SQL and in most databases this is an error, and the expression is repeated as WHERE amount * 1.2 > 200. SQLite is lenient here and accepts the alias, so a query that works in SQLite can fail in another database.

This order is logical. The optimizer may run operations in a different order or merge them, as long as the result does not change. The right answer is not “the database physically runs it this way” but “the meaning of the query is defined by this order”.

3. WHERE vs HAVING

WHERE filters individual rows before grouping. HAVING filters groups after grouping. That is why aggregate functions such as SUM and COUNT cannot be used in WHERE: there are no groups yet at that point.

SELECT city, COUNT(*) AS cnt
FROM customers
GROUP BY city
HAVING COUNT(*) > 1;
city cnt
Ankara 2

A condition that can be written against rows goes into WHERE. HAVING city = 'Ankara' gives the same result, but it groups unnecessary rows first and throws them away afterwards.

4. JOIN types

A JOIN puts the rows of two tables side by side based on a condition. In the queries below only the JOIN type changes:

SELECT c.name, o.id AS order_id, o.amount
FROM customers c
INNER JOIN orders o ON o.customer_id = c.id;   -- LEFT, RIGHT, FULL OUTER

Without ORDER BY, row order is not guaranteed. I listed the rows in a readable order.

INNER JOIN returns only the rows that match on both sides. C and 104 drop out.

name order_id amount
A 101 250
A 102 100
B 103 400

LEFT JOIN returns every row of the left table. Where there is no match on the right, the right-hand columns are NULL.

name order_id amount
A 101 250
A 102 100
B 103 400
C NULL NULL

RIGHT JOIN is the mirror image: every row of the right table is returned. The result is the three INNER JOIN rows plus (NULL, 104, 80).

FULL OUTER JOIN returns every row from both sides: the three INNER JOIN rows, C, NULL, NULL and NULL, 104, 80. SQLite has supported RIGHT and FULL JOIN since version 3.39. Older versions and MySQL have no FULL JOIN, so a LEFT JOIN and a reversed LEFT JOIN have to be combined with UNION.

CROSS JOIN takes no condition and produces the Cartesian product of the two tables. 3 customers and 4 orders give 12 rows.

A Self Join joins a table with itself. There is no separate keyword. The same table gets two different aliases. Finding each employee’s manager in the same table is the typical example:

CREATE TABLE employees (id INTEGER PRIMARY KEY, title TEXT, manager_id INTEGER);
INSERT INTO employees VALUES (1, 'General Manager', NULL), (2, 'Team Lead', 1), (3, 'Developer', 2);

SELECT e.title AS employee, m.title AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
employee manager
General Manager NULL
Team Lead General Manager
Developer Team Lead

The LEFT JOIN and WHERE trap

If a WHERE condition is placed on a right-table column after a LEFT JOIN, the rows where that column is NULL are removed and the query behaves like an INNER JOIN.

-- C disappears: NULL > 200 is not true
SELECT c.name, o.amount FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.amount > 200;

-- C stays: the condition is part of the match
SELECT c.name, o.amount FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.amount > 200;

The first query returns A 250 and B 400. The second adds a C NULL row. Along the same lines, counting orders per customer uses COUNT(o.id), not COUNT(*). COUNT(*) gives 1 for C, while COUNT(o.id) gives 0 because it does not count NULLs.

5. Indexes

An Index is a separate data structure that keeps the values of one or more columns of a table in sorted order and points from each value to the matching row. It works like the index at the back of a book: to find the page where a term appears, nobody reads the book cover to cover. They look it up alphabetically in the index.

How a B-tree works

The default index structure in relational databases is the B-tree (usually its B+ tree variant). It is a balanced tree, and each node corresponds to a disk page, so a single node holds hundreds of keys. That keeps the tree very shallow. Even in a table with millions of rows, the path from root to leaf is three or four steps. Lookup is O(log n), while a full scan without an index is O(n) (Big O from Part 1). Because the leaves are sorted, range queries such as BETWEEN and > also benefit from the index.

In SQLite, EXPLAIN QUERY PLAN shows whether a query uses an index. Without an index, the plan for WHERE customer_id = 1 says SCAN orders, meaning the whole table is read. After an index is added, the plan becomes SEARCH ... USING INDEX.

Faster reads, slower writes

An index is not free. Every INSERT, every DELETE and every UPDATE that touches an indexed column has to update all of the table’s indexes as well as the table. The new key is placed in the right spot in the sorted structure, and if the page is full it is split (a page split). Inserting one row into a table with five indexes means writing to six separate structures.

That is why not every column gets an index. Good candidates are columns that appear often in WHERE, JOIN and ORDER BY and are selective. An index on an is_active column with only two values is usually useless, because walking the index to fetch half of the rows costs more than a scan. An index also cannot be used when the column is wrapped in a function: WHERE UPPER(name) = 'A' scans the table despite an index on name.

Composite indexes and the leftmost prefix rule

A Composite Index is built on more than one column, and column order matters. An index on (customer_id, order_date) is sorted by customer first, and by date within each customer. It is like a phone book sorted by last name and then first name: searching by last name is fast, searching by first name alone is not.

CREATE INDEX ix_orders_customer_date ON orders (customer_id, order_date);

EXPLAIN QUERY PLAN SELECT * FROM orders WHERE customer_id = 1;
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE customer_id = 1 AND order_date >= '2026-02-01';
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE order_date >= '2026-02-01';
Condition Plan
customer_id = 1 SEARCH USING INDEX (customer_id=?)
customer_id = 1 AND order_date >= ... SEARCH USING INDEX (customer_id=? AND order_date>?)
order_date >= ... SCAN orders

This is the Leftmost Prefix rule. An index can be used with a prefix of its columns starting from the left: (a), (a, b), (a, b, c). A search on b alone cannot use the index’s order. Equality conditions go first, and the range condition goes last.

Clustered and non-clustered

A Clustered Index means the table’s rows are physically stored in the order of that index. The rows themselves sit in the index leaves, so a table can have only one. In MySQL’s InnoDB the table is always stored by primary key, and in SQLite by rowid.

A Non-clustered Index is a separate structure. Its leaves hold the key and a pointer to the row’s location (or the clustered key). If the requested columns are not in the index, a second lookup goes to the table. If every column the query needs is in the index, that step is skipped, and such an index is called a Covering Index.

6. ACID and transactions

A Transaction is a group of statements that must succeed together or be undone together. It starts with BEGIN, becomes permanent with COMMIT, and is undone with ROLLBACK. The classic example is a money transfer: debiting one account and crediting another are two separate UPDATEs, and if only one of them happens, money either vanishes or appears out of nowhere.

The four properties a transaction guarantees are known as ACID:

  • Atomicity: Either all statements in the transaction are applied, or none are.
  • Consistency: The transaction moves the database from one valid state to another. Constraints such as primary keys, foreign keys and CHECK are not violated.
  • Isolation: Concurrent transactions see each other’s unfinished changes only as far as the chosen isolation level allows.
  • Durability: A transaction whose COMMIT has returned is not lost, even if the power goes out right after. The database writes the change to a log on disk first (the write-ahead log), then acknowledges the commit.
CREATE TABLE accounts (id INTEGER PRIMARY KEY, balance INTEGER CHECK (balance >= 0));
INSERT INTO accounts VALUES (1, 100), (2, 50);

BEGIN;
UPDATE accounts SET balance = balance + 150 WHERE id = 2;   -- succeeds
UPDATE accounts SET balance = balance - 150 WHERE id = 1;   -- CHECK violation, error
ROLLBACK;                                                   -- the application catches the error and calls it
id balance
1 100
2 50

There is a detail that is easy to miss. An error does not roll back the transaction by itself. In SQLite a CHECK violation undoes only that statement, and the first UPDATE stays pending inside the transaction. If the error is caught and COMMIT is called instead of ROLLBACK, account 2 ends up at 200, account 1 stays at 100, and 150 units of money appear from nowhere. I confirmed this by running it. On the error path, ROLLBACK is always written explicitly.

7. Isolation levels

An Isolation Level determines how much consistency is traded for concurrency. Levels are defined by which read anomalies they allow:

  • Dirty Read: Reading a change that another transaction has not committed yet. If that transaction rolls back, the value that was read never existed.
  • Non-repeatable Read: Reading the same row twice within a transaction and getting a different value because another transaction committed an UPDATE in between.
  • Phantom Read: Running the same query twice and getting a different number of rows because rows were inserted or deleted in between. For example, WHERE amount > 100 returns 3 rows first and 4 rows later.

A non-repeatable read is an existing row changing. A phantom read is rows entering or leaving the result set.

Level Dirty read Non-repeatable read Phantom read
Read Uncommitted Possible Possible Possible
Read Committed Prevented Possible Possible
Repeatable Read Prevented Prevented Possible
Serializable Prevented Prevented Prevented

The table shows the worst case the SQL standard allows at each level. Databases are often stricter. In PostgreSQL, Read Uncommitted behaves like Read Committed, and Repeatable Read also prevents phantom reads because it uses a snapshot. Defaults differ too: Read Committed in PostgreSQL and SQL Server, Repeatable Read in MySQL InnoDB. In SQLite only one writer can be active at a time, so transactions behave as serializable.

8. Normalization

Normalization is splitting tables so as to reduce repeated data and the update errors it causes. If the same fact is stored in two places, updating one and forgetting the other leaves the database contradicting itself.

Starting table:

order_id customer city products
101 A Ankara Pen x3, Notebook x1
102 B Izmir Pen x2

1NF (First Normal Form): Every cell holds a single, atomic value, and there are no repeating groups. The products column breaks this rule. A query for “orders containing pens” turns into a text search. Once each product gets its own row, the table is in 1NF, and the key is the pair (order_id, product):

order_id product qty price customer city
101 Pen 3 20 A Ankara
101 Notebook 1 45 A Ankara
102 Pen 2 20 B Izmir

2NF: In addition to 1NF, every non-key column must depend on the whole key. price depends only on product, and customer and city depend only on order_id. Because of this Partial Dependency, the price of a pen is repeated in every order. The table is split into three: products(id, name, price), orders(id, customer, city) and order_items(order_id, product_id, qty).

3NF: In addition to 2NF, a non-key column must not depend on another non-key column. In the orders table, city depends on the customer, not on the order (a Transitive Dependency). If the customer moves, all of their orders have to be updated. The customer moves to a separate table:

CREATE TABLE customers (id INTEGER PRIMARY KEY, name TEXT, city TEXT);
CREATE TABLE products  (id INTEGER PRIMARY KEY, name TEXT, price INTEGER);
CREATE TABLE orders    (id INTEGER PRIMARY KEY, customer_id INTEGER REFERENCES customers(id));
CREATE TABLE order_items (
  order_id   INTEGER REFERENCES orders(id),
  product_id INTEGER REFERENCES products(id),
  qty        INTEGER,
  PRIMARY KEY (order_id, product_id)
);

When the flat view is needed, it is rebuilt with JOINs. Joining the four tables gave this result:

order_id name city product qty subtotal
101 A Ankara Pen 3 60
101 A Ankara Notebook 1 45
102 B Izmir Pen 2 40

In a real ordering system, order_items usually gets a unit_price column as well. That is not a 2NF violation, because it stores a different fact: not the product’s current price, but its price at the time of the order. When the product’s price changes, the totals of past orders must not change.

When to denormalize

Denormalization is deliberately going back to repeated data for read performance. It is considered where reads far outnumber writes and the same JOIN runs over and over. Reporting tables or an order_count counter kept on the customer row are examples. The cost is that keeping the copies consistent falls to triggers or application code. Normalize first, and denormalize when there is a measured performance problem.

9. Views, stored procedures and triggers

A View is a named, saved SELECT query. It holds no data itself, and the underlying query runs every time it is used. It is used to hide a complex JOIN behind a single name and to grant access through a view instead of the table.

CREATE VIEW customer_summary AS
SELECT c.name, COUNT(o.id) AS order_count, COALESCE(SUM(o.amount), 0) AS total
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name;

SELECT * FROM customer_summary WHERE total > 0;   -- A 2 350, B 1 400

A Materialized View actually stores the result and shows stale data until it is refreshed. In PostgreSQL it is refreshed with REFRESH MATERIALIZED VIEW. SQL Server does the same job with an indexed view, and SQLite has no equivalent. The CREATE MATERIALIZED VIEW statement exists in PostgreSQL and Oracle, not in SQL Server.

A Stored Procedure is code stored in the database that takes parameters and can run several statements. SQLite has no stored procedures. The example below is written in SQL Server (T-SQL) syntax and was not run:

CREATE PROCEDURE AddOrder @CustomerId INT, @ProductId INT, @Qty INT
AS
BEGIN
    SET XACT_ABORT ON;   -- on error, roll back the whole transaction
    BEGIN TRANSACTION;
        UPDATE products SET stock = stock - @Qty WHERE id = @ProductId AND stock >= @Qty;
        IF @@ROWCOUNT = 0 THROW 50001, 'Insufficient stock', 1;
        INSERT INTO orders (customer_id, product_id, qty) VALUES (@CustomerId, @ProductId, @Qty);
    COMMIT;
END;

The stock check happens in the WHERE clause of the UPDATE. If it were done first with a separate SELECT, another order could reduce the same stock between the two statements. The difference from a function: a function always returns a value and can be used inside SELECT, while a stored procedure is called with EXEC. Functions are often said to be lighter, but in SQL Server a scalar function runs separately for each row and can slow large queries down noticeably.

A Trigger is code that runs automatically when an INSERT, UPDATE or DELETE happens on a table. It is common for audit logs. SQLite supports triggers:

CREATE TABLE order_log (order_id INTEGER, action TEXT, logged_at TEXT);

CREATE TRIGGER trg_order_delete AFTER DELETE ON orders
BEGIN
  INSERT INTO order_log VALUES (OLD.id, 'DELETE', datetime('now'));
END;

DELETE FROM orders WHERE id = 104;   -- order_log: (104, 'DELETE', ...)

SQLite and PostgreSQL access the deleted or inserted row through OLD and NEW, while SQL Server uses the deleted and inserted pseudo-tables. For simple rules such as stock never going negative, a CHECK constraint is clearer than a trigger.

10. SQL injection and parameterized queries

SQL Injection happens when user input is pasted directly into the query text and ends up being executed as SQL.

user_input = "' OR '1'='1"

# wrong: the input becomes part of the query text
db.execute(f"SELECT id, name FROM customers WHERE name = '{user_input}'").fetchall()
# [(1, 'A'), (2, 'B'), (3, 'C')]

# right: the input is sent as a separate parameter
db.execute("SELECT id, name FROM customers WHERE name = ?", (user_input,)).fetchall()
# []

The first query becomes WHERE name = '' OR '1'='1', and since the condition is true for every row, all customers come back. With a Parameterized Query the query text and the value are sent to the database separately. Whatever the value contains, it is only compared as data. The second query looks for a customer whose name is literally ' OR '1'='1 and finds none.

Escaping quotes by hand is not enough. Table and column names cannot be parameters. If they come from the user, they are checked against an allowlist.

Interview questions

1. In what order is a SQL query evaluated? Why can’t an alias be used in WHERE? The logical order is FROM and JOIN, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT. An alias is defined in SELECT, and WHERE is evaluated before that, so the alias does not exist yet. ORDER BY comes after SELECT, so it can use the alias. Common mistake: Taking this as the physical execution order. The optimizer can reorder steps as long as the result stays the same.

2. What is the difference between WHERE and HAVING? WHERE filters rows before grouping, HAVING filters groups after grouping. Aggregate functions cannot be used in WHERE. Common mistake: Putting row-level conditions in HAVING. The result is the same, but unnecessary data gets grouped.

3. What is the difference between INNER JOIN and LEFT JOIN? INNER JOIN returns only rows that match on both sides. LEFT JOIN returns every row of the left table, with the right side NULL where there is no match. Common mistake: Adding a WHERE condition on a right-table column after a LEFT JOIN. The NULL rows are removed and the query turns into an INNER JOIN. The condition belongs in ON.

4. Why does an index speed up reads, and why not index every column? A B-tree index keeps values sorted and turns an O(n) full scan into an O(log n) lookup. Every INSERT, DELETE and relevant UPDATE has to update all indexes too, so writes get slower, and indexes take up space. Common mistake: Expecting an index to help on low-selectivity columns or on columns wrapped in a function.

5. With a composite index on (customer_id, order_date), does WHERE order_date = … use the index? Usually not. The index is sorted by customer_id first and is used through a prefix starting from the left. SQLite produces a full scan plan for this query. Common mistake: Assuming column order does not matter. Columns with equality conditions go first, the range column goes last.

6. What is ACID? Atomicity means the transaction is applied entirely or not at all. Consistency means constraints are preserved, isolation means concurrent transactions are kept apart, and durability means committed data survives a crash. Common mistake: Assuming a failing statement rolls back the transaction by itself. On the error path, ROLLBACK is called explicitly.

7. What is the difference between a dirty read, a non-repeatable read and a phantom read? A dirty read is reading uncommitted data. A non-repeatable read is the same row changing between two reads, and a phantom read is rows being inserted or deleted between two runs of the same query. Read Committed prevents the first, Repeatable Read the second, and Serializable all three. Common mistake: Treating non-repeatable reads and phantom reads as the same thing. One is an existing row changing, the other is the result set changing.

8. What is normalization, and when do you denormalize? Normalization is splitting tables to reduce repeated data and update errors. 1NF means atomic values, 2NF removes partial dependencies, and 3NF removes transitive dependencies. Denormalization is deliberately adding repetition back when there is a measured read performance problem. Common mistake: Calling the price stored on an order line at order time a normalization error. It is a different fact.
