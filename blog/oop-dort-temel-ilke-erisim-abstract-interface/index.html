OOP: Dört Temel İlke, Erişim Belirleyiciler, Abstract Class ve Interface

Programlama 101, Bölüm 4

  1. bölümde yapısal, fonksiyonel ve nesne yönelimli programlamayı yan yana koymuştuk. Orada OOP’nin programı veriyi ve o veri üzerinde çalışan kodu bir arada tutan nesnelere böldüğünü söylemiştik. Bu yazı o kısmı açıyor: nesneler nasıl tasarlanır, hangi kurallara uyar?

OOP mülakatlarında sorular genelde aynı yerden gelir. Dört temel ilke, overloading ile overriding farkı, erişim belirleyiciler ve abstract class ile interface arasındaki seçim. Örneklerin hepsi Java’da, çünkü bu soruların çoğu Java üzerinden soruluyor ve sürüme bağlı birkaç ayrıntı da orada çıkıyor.

Aşağıda önce class ve object ayrımını, sonra dört ilkeyi tek tek anlatıyorum. Ardından erişim belirleyiciler, abstract class ve interface farkı ve kısaca composition geliyor. Sonda mülakatta sık gelen sorular ve kısa cevapları var.

1. Class ve object

Class (Sınıf), bir nesnenin hangi verileri tutacağını ve hangi işleri yapabileceğini tanımlayan şablondur. Object (Nesne) ise o şablondan oluşturulmuş, bellekte yer kaplayan somut örnektir. Bu yüzden object yerine Instance (Örnek) de denir.

Class bir ev planına benzer, object de o plana göre yapılmış evlere. Plan bir tane, ondan istenen sayıda ev yapılabilir. Her evin duvar rengi farklı olabilir, ama oda düzeni aynıdır.

public class Hesap {
    String sahip;        // durum (state)
    double bakiye;

    void yatir(double tutar) {   // davranış (behavior)
        bakiye += tutar;
    }
}

Hesap a = new Hesap();   // bellekte yeni bir nesne
Hesap b = new Hesap();   // ayrı bir nesne, ayrı bakiye

new çağrıldığında nesne heap’te oluşturulur ve Constructor (Yapıcı Metot) çalışır. Constructor’ın adı sınıfın adıyla aynıdır ve dönüş tipi yoktur. Sınıfa hiç constructor yazılmazsa derleyici parametresiz bir tane ekler. Python’daki __init__ ne iş görüyorsa Java’da constructor onu yapar.

2. Encapsulation (kapsülleme)

Encapsulation, bir nesnenin verisini dışarıdan doğrudan değiştirilemeyecek şekilde saklamak ve o veriye yalnızca nesnenin kendi metotları üzerinden erişilmesini sağlamaktır.

Banka hesabı bunu iyi gösteriyor. Bakiyeyi kimse doğrudan elle değiştiremez. Para yatırmak ya da çekmek için gişeye gidilir ve gişe kuralları uygular: negatif tutar kabul edilmez, bakiyeden fazla para çekilemez.

public class Hesap {
    private double bakiye;   // dışarıdan görünmez

    public void yatir(double tutar) {
        if (tutar <= 0) throw new IllegalArgumentException("Tutar pozitif olmalı");
        bakiye += tutar;
    }

    public void cek(double tutar) {
        if (tutar > bakiye) throw new IllegalStateException("Yetersiz bakiye");
        bakiye -= tutar;
    }

    public double getBakiye() { return bakiye; }   // okuma serbest, yazma yok
}

Burada setBakiye metodu bilinçli olarak yok. Encapsulation sık sık “alanları private yap, her birine getter ve setter yaz” diye anlatılır, ama her alana koşulsuz bir setter eklemek veriyi yine dışarıya açar. Asıl amaç, nesnenin geçersiz bir duruma düşmesini engelleyen kuralları tek bir yerde tutmaktır. Bakiye ancak yatir ve cek üzerinden değişiyorsa, hatalı bir değer de ancak bu iki metottan gelebilir.

İkinci kazanç, iç yapının değiştirilebilmesi. Yarın bakiye double yerine kuruş cinsinden long olarak tutulursa, dışarıdaki kod bunu fark etmez. Para hesaplarında double yerine BigDecimal ya da tam sayı kullanılır, burada örneği kısa tutmak için double kullandım.

3. Inheritance (kalıtım)

Inheritance, bir sınıfın başka bir sınıfın alanlarını ve metotlarını devralmasıdır. Devreden sınıfa Superclass (Üst Sınıf) ya da parent, devralana Subclass (Alt Sınıf) ya da child denir. Java’da bunun için extends kullanılır.

Bir taşıt sınıfı düşünülebilir. Araba ve kamyon ikisi de taşıttır, ikisinin de plakası ve hızı vardır. Bu ortak kısım taşıtta bir kez yazılır, alt sınıflar yalnızca kendi farklarını ekler.

class Tasit {
    protected String plaka;
    protected int hiz;

    void hizlan(int miktar) { hiz += miktar; }
}

class Kamyon extends Tasit {
    private int yukKapasitesi;   // yalnızca kamyonda var

    void yukle(int ton) { /* ... */ }
}

Kamyon k = new Kamyon();
k.hizlan(20);   // Tasit'ten gelen metot

Inheritance bir is-a (bir türüdür) ilişkisi kurar. “Kamyon bir taşıttır” cümlesi doğruysa kalıtım uygundur. Cümle zorlama geliyorsa, örneğin “Müşteri bir adrestir”, büyük ihtimalle yanlış araç seçilmiştir.

Java’da bir sınıf yalnızca bir sınıftan extends edebilir. Buna Single Inheritance (Tekli Kalıtım) denir. Sebebi Diamond Problem (Elmas Problemi): iki üst sınıf aynı adlı metodu farklı şekilde tanımlarsa, alt sınıfın hangisini kullanacağı belirsiz kalır. Bir sınıf buna karşılık istediği kadar interface’i implements edebilir. Bu konuya 7. bölümde dönüyorum.

Birkaç kural daha var:

  • Constructor’lar kalıtılmaz. Alt sınıfın constructor’ı ilk satırda super(...) ile üst sınıfın constructor’ını çağırır, yazılmazsa derleyici parametresiz super() ekler.
  • final ile işaretlenmiş bir sınıftan kalıtım yapılamaz. String bunun bilinen örneği.
  • Bütün sınıflar dolaylı olarak Object sınıfından türer. toString, equals ve hashCode oradan gelir.

4. Polymorphism (çok biçimlilik)

Polymorphism, aynı çağrının farklı nesnelerde farklı davranış üretmesidir. Uzaktan kumandadaki “aç” tuşu buna benzer. Tuş aynı, ama televizyona basıldığında görüntü gelir, klimaya basıldığında soğuk hava.

Java’da bu iki yolla olur ve mülakatta ikisinin farkı mutlaka sorulur.

Overloading: compile-time polymorphism

Overloading (Aşırı Yükleme), aynı sınıfta aynı adı taşıyan ama parametre listesi farklı olan metotlar yazmaktır. Parametrelerin sayısı, tipi ya da sırası farklı olmalıdır. Yalnızca dönüş tipini değiştirmek yetmez, derleyici bunu hata olarak verir.

class Hesaplayici {
    int topla(int a, int b)          { return a + b; }
    int topla(int a, int b, int c)   { return a + b + c; }
    double topla(double a, double b) { return a + b; }
    // long topla(int a, int b) { ... }  derleme hatası: yalnızca dönüş tipi farklı
}

Hangi metodun çalışacağına derleyici, argümanların tiplerine bakarak derleme sırasında karar verir. Bu yüzden overloading’e Compile-time (Static) Polymorphism denir.

Overriding: runtime polymorphism

Overriding (Ezme / Yeniden Tanımlama), alt sınıfın üst sınıftaki bir metodu aynı imzayla yeniden yazmasıdır.

class Hayvan {
    String ses() { return "..."; }
}

class Kedi extends Hayvan {
    @Override
    String ses() { return "Miyav"; }
}

class Kopek extends Hayvan {
    @Override
    String ses() { return "Hav"; }
}

Hayvan h = new Kedi();      // referans tipi Hayvan, nesne Kedi
System.out.println(h.ses()); // "Miyav"

h değişkeninin tipi Hayvan, ama çalışan metot Kedi’nin metodu. Karar, nesnenin gerçek tipine bakılarak çalışma zamanında verilir. Buna Dynamic Method Dispatch ya da Runtime Polymorphism denir. Bir List<Hayvan> içinde dolaşıp her birinin ses() metodunu çağıran kod, yeni bir hayvan türü eklendiğinde değişmeden çalışmaya devam eder.

@Override zorunlu değildir, ama yazılması iyi olur. İmzada bir yazım hatası yapılırsa, örneğin Ses(), derleyici “bu metot hiçbir şeyi ezmiyor” diye hata verir. Annotation yoksa ortada sessizce yeni bir metot oluşur.

Overriding’in kuralları:

  • Metot adı ve parametre listesi aynı olmalıdır. Dönüş tipi aynı ya da onun bir alt tipi olabilir (Covariant Return Type).
  • Erişim seviyesi daraltılamaz. Üst sınıfta public olan metot alt sınıfta protected yapılamaz.
  • private, static ve final metotlar override edilemez. private metot alt sınıfa görünmez. Alt sınıfta aynı imzayla yazılan static metot üst sınıftakini ezmez, gizler (Method Hiding). Hangisinin çalışacağı referansın tipine göre derleme sırasında belirlenir.
  • Alanlar (field) override edilmez. Alt sınıfta aynı adla tanımlanan alan üst sınıftakini gizler ve hangisinin okunacağı yine referansın tipine bağlıdır.
Overloading Overriding
Nerede Aynı sınıfta (ya da alt sınıfta) Alt sınıfta
İmza Ad aynı, parametreler farklı Ad ve parametreler aynı
Karar zamanı Derleme sırasında Çalışma sırasında

5. Abstraction (soyutlama)

Abstraction, bir şeyin ne yaptığını gösterip nasıl yaptığını gizlemektir. Kullanıcı yalnızca ihtiyaç duyduğu arayüzü görür.

Araba kullanırken direksiyon, gaz ve fren yeterlidir. Gaza basınca motorda yakıtın nasıl püskürtüldüğünü bilmek gerekmez. Motor değişse, örneğin benzinli yerine elektrikli olsa, pedallar aynı kalır.

interface OdemeYontemi {
    void ode(double tutar);
}

class KartlaOdeme implements OdemeYontemi {
    public void ode(double tutar) { /* kart doğrulama, banka isteği */ }
}

class HavaleIleOdeme implements OdemeYontemi {
    public void ode(double tutar) { /* IBAN kontrolü, transfer */ }
}

void siparisiTamamla(OdemeYontemi yontem, double tutar) {
    yontem.ode(tutar);   // hangi yöntem olduğunu bilmiyor, bilmesi de gerekmiyor
}

siparisiTamamla yalnızca ode metodunun var olduğunu biliyor. Yarın yeni bir ödeme yöntemi eklendiğinde bu metot değişmez.

Encapsulation ile abstraction sık karıştırılır, çünkü ikisi de bir şeyleri gizler. Encapsulation veriyi ve onu koruyan kuralları sınıfın içine kapatır, soru “bu veriye kim, nasıl dokunabilir?” sorusudur. Abstraction ise tasarım seviyesindedir ve “dışarıya hangi işlemleri göstereyim, hangi ayrıntıyı saklayayım?” sorusuna cevap verir. Java’da abstraction’ın iki aracı var: abstract class ve interface.

6. Erişim belirleyiciler (access modifiers)

Access Modifier (Erişim Belirleyici), bir sınıfın, alanın ya da metodun hangi koddan görülebileceğini belirler. Java’da dört seviye var. Bunlardan biri anahtar kelime değil, hiçbir şey yazılmadığında geçerli olan varsayılan seviye.

Belirleyici Aynı sınıf Aynı paket Başka paketteki alt sınıf Başka paketteki diğer kod
public Evet Evet Evet Evet
protected Evet Evet Evet (kalıtım yoluyla) Hayır
default (yazılmaz) Evet Evet Hayır Hayır
private Evet Hayır Hayır Hayır

Bir ev üzerinden düşünülebilir. Kapıdaki isim public, herkes görür. Banka kartının şifresi private, yalnızca sahibi bilir, çocuğuna bile söylemez. Default ise apartman içi: aynı binada oturan herkes bilir, dışarıdan gelen bilmez. protected apartmanla birlikte aileyi de kapsar. Başka binada oturan çocuk da erişebilir.

Default (package-private)

Hiçbir belirleyici yazılmazsa üye yalnızca aynı paketteki sınıflara açıktır. Buna Package-Private denir. C# kökenli notlarda bu seviye genelde atlanır, çünkü C#‘ta varsayılan farklıdır (sınıf üyelerinde private). Java’da ise private yazmayı unutmak, alanı bütün pakete açmak demektir.

En üst seviyedeki (iç içe olmayan) bir sınıf yalnızca public ya da default olabilir. private class ve protected class yalnızca başka bir sınıfın içinde tanımlanan sınıflar için geçerlidir.

Protected’ın paket kuralı

protected çoğu zaman “yalnızca alt sınıflar erişir” diye özetlenir. Java’da bu eksik. protected üyeye aynı paketteki bütün sınıflar erişebilir, alt sınıf olmasalar da. Yani protected, default’un sağladığı her şeyi sağlar ve üstüne başka paketteki alt sınıfları ekler.

Başka paketteki alt sınıf için de bir sınır var. Alt sınıf protected üyeye kendi üzerinden (ya da kendi tipindeki bir referans üzerinden) erişir. Üst sınıf tipinde ayrı bir nesne oluşturup onun protected alanına erişemez.

package banka;
public class Hesap {
    protected double bakiye;
}

package kampanya;            // farklı paket
import banka.Hesap;

public class VadeliHesap extends Hesap {
    void faizEkle() {
        bakiye *= 1.02;              // geçerli: kendi devraldığı alan

        Hesap baska = new Hesap();
        // baska.bakiye = 0;         derleme hatası: başka bir Hesap nesnesi
    }
}

Alt sınıf yalnızca kendi devraldığı parçaya erişebilir. Aynı tipten başka bir nesnenin içine bakamaz.

Pratikte hangisi?

Alanlar neredeyse her zaman private olur. Metotlar ihtiyaç kadar açılır: dışarıya sunulan işlemler public, paket içi yardımcılar default, alt sınıfların ezmesi beklenen noktalar protected. En kısıtlı seviyeden başlayıp gerektikçe açmak, sonradan kapatmaya çalışmaktan kolaydır. public olan bir şeyi kullanan kodu bulmak ve değiştirmek her zaman mümkün olmaz.

7. Abstract class ile interface farkı

İkisi de doğrudan new ile nesnesi oluşturulamayan, alt sınıfların doldurması gereken boşluklar tanımlayan yapılardır. Farkları Java sürümleriyle değişti. Eski notlardaki “interface’te yalnızca abstract metot olur” bilgisi Java 8’den beri geçerli değil.

Abstract class

Abstract Class (Soyut Sınıf), abstract anahtar kelimesiyle tanımlanır. Hem gövdesi olmayan abstract metotlar hem de normal metotlar içerebilir. Alanları, constructor’ı ve her erişim seviyesindeki üyeleri olabilir. Bir sınıf yalnızca bir abstract class’tan extends edebilir.

abstract class Calisan {
    private final String ad;
    protected Calisan(String ad) { this.ad = ad; }   // constructor olabilir

    abstract double maasHesapla();                    // alt sınıf doldurur

    String bordroSatiri() {                           // ortak, hazır kod
        return ad + ": " + maasHesapla();
    }
}

class TamZamanli extends Calisan {
    TamZamanli(String ad) { super(ad); }
    double maasHesapla() { return 40000; }
}

Abstract class’ın constructor’ı vardır, ama new Calisan(...) yazılamaz. Constructor, alt sınıf super(...) ile çağırdığında ortak alanları kurmak için çalışır. Abstract metodu olan bir sınıf abstract olmak zorundadır. Tersi gerekmez: hiç abstract metodu olmayan bir sınıf da yalnızca nesnesinin oluşturulmasını engellemek için abstract tanımlanabilir. Bir alt sınıf, kendisi de abstract değilse, bütün abstract metotları doldurmak zorundadır.

Interface ve sürüm değişiklikleri

Interface (Arayüz), bir sınıfın sunacağı işlemleri tanımlayan bir sözleşmedir. Bir sınıf birden fazla interface’i implements edebilir. Interface’in nesne durumu (instance field) yoktur. İçinde tanımlanan her değişken dolaylı olarak public static final, yani sabittir. Constructor’ı da yoktur.

Metot tarafında sürümlere göre şunlar eklendi:

Sürüm Interface’te ne yazılabilir
Java 7 ve öncesi Yalnızca abstract metotlar (dolaylı olarak public abstract) ve sabitler
Java 8 default metotlar (gövdeli, implement eden sınıf ezebilir) ve static metotlar
Java 9 private metotlar ve private static metotlar 
interface Bildirim {
    void gonder(String mesaj);                 // abstract

    default void gonderToplu(List<String> mesajlar) {   // Java 8
        mesajlar.forEach(m -> gonder(formatla(m)));
    }

    static Bildirim sessiz() {                 // Java 8
        return mesaj -> { };
    }

    private String formatla(String m) {        // Java 9
        return "[bildirim] " + m;
    }
}

default metotlar, var olan bir interface’e onu implement eden bütün sınıfları bozmadan yeni metot ekleyebilmek için geldi. Collection arayüzüne Java 8’de eklenen stream() ve Iterable’a eklenen forEach bunun örneği. private metotlar ise birkaç default metodun ortak kodunu, dışarıya açmadan paylaşmaları için var.

İki ayrıntı mülakatta sorulabiliyor:

  • Interface’teki static metot, implement eden sınıfa kalıtılmaz. Bildirim.sessiz() diye interface adıyla çağrılır, EpostaBildirim.sessiz() derlenmez.
  • Bir sınıf aynı imzalı default metodu olan iki interface’i implement ederse derleyici hata verir. Sınıf o metodu kendisi override etmek zorundadır. İçeriden birini seçmek için A.super.metot() yazılır. Elmas problemi Java’da böyle çözülüyor: davranış kalıtılabilir, ama çakışma varsa kararı sınıf verir. Durum (alan) ise interface’ten hiç kalıtılmaz.

Ne zaman hangisi?

Interface, birbiriyle akraba olmayan sınıfların ortak bir yeteneğini tanımlarken seçilir. Comparable, Runnable, AutoCloseable bu türden. Bir dosya da, bir veritabanı bağlantısı da kapatılabilir, ama ortak bir ataları yoktur. Bir tipin dışarıya sunduğu sözleşme de çoğunlukla interface olarak tanımlanır, böylece onu kullanan kod tek bir somut sınıfa bağlanmaz.

Abstract class, yakın akraba sınıflar ortak durum ve ortak kod paylaşıyorsa seçilir. Alt sınıfların hepsinde aynı alanlar varsa, bir constructor bunları kurmalıysa ya da protected yardımcı metotlar gerekiyorsa interface yetmez, çünkü interface durum tutamaz.

İkisi birlikte de kullanılabilir. Java kütüphanesinde List bir interface’tir, AbstractList ise onu kısmen implement eden bir abstract class. Yeni bir liste yazan kişi AbstractList’ten türeyip birkaç metodu doldurarak işi bitirir. Listeyi kullanan kod ise yalnızca List’i bilir.

8. Composition over inheritance

Composition (Bileşim), bir sınıfın başka bir sınıfın davranışını kalıtımla değil, onu bir alan olarak içinde tutarak kullanmasıdır. İlişki is-a değil, has-a (sahiptir) ilişkisidir. “Araba bir motordur” yanlış, “arabanın bir motoru vardır” doğru.

“Composition over inheritance” ilkesi, kod paylaşmak için kalıtım yerine öncelikle composition’ın düşünülmesini söyler. Kalıtım alt sınıfı üst sınıfın iç ayrıntılarına sıkı bağlar. Üst sınıftaki bir değişiklik, onu hiç düşünmemiş alt sınıfları bozabilir. Ayrıca alt sınıf, istemese de üst sınıfın bütün public metotlarını devralır.

Java’nın kendi kütüphanesinde bilinen bir örnek var. java.util.Stack, Vector’dan türer. Bu yüzden bir stack üzerinde get(index) ve add(index, eleman) gibi, yığının ortasına dokunan metotlar da çağrılabilir. Stack’in “yalnızca üstten ekle, üstten çıkar” kuralı böylece delinmiş olur. Bugün Java belgeleri stack için Deque arayüzünü ve ArrayDeque’yi öneriyor.

class Yigin<T> {
    private final Deque<T> elemanlar = new ArrayDeque<>();   // has-a

    void push(T e) { elemanlar.push(e); }
    T pop()        { return elemanlar.pop(); }
    boolean bosMu(){ return elemanlar.isEmpty(); }
    // ortadan erişim yok, çünkü dışarıya açılmadı
}

Bu, kalıtımın hiç kullanılmayacağı anlamına gelmiyor. Gerçek bir is-a ilişkisi varsa ve alt sınıf üst sınıfın yerine her yerde sorunsuz kullanılabiliyorsa kalıtım doğru araçtır. Sorun, kalıtımın yalnızca kod tekrarından kaçmak için kullanılmasıyla başlıyor.

Mülakatta sorulanlar

1. OOP’nin dört temel ilkesi nedir? Encapsulation veriyi sınıf içinde saklayıp yalnızca metotlar üzerinden değiştirilmesini sağlar. Inheritance bir sınıfın başka bir sınıfın üyelerini devralmasıdır. Polymorphism aynı çağrının nesnenin tipine göre farklı çalışmasıdır, abstraction ise ayrıntıyı gizleyip yalnızca gerekli arayüzü göstermektir. Sık yapılan hata: Encapsulation’ı “her alana getter ve setter yazmak” diye tanımlamak.

2. Overloading ile overriding arasındaki fark nedir? Overloading aynı adlı, parametre listesi farklı metotlardır ve hangisinin çalışacağına derleme sırasında karar verilir. Overriding alt sınıfın üst sınıftaki metodu aynı imzayla yeniden yazmasıdır ve karar çalışma sırasında, nesnenin gerçek tipine göre verilir. Sık yapılan hata: Yalnızca dönüş tipi farklı iki metodu overloading saymak. Bu derleme hatasıdır.

3. Static bir metot override edilebilir mi? Hayır. Alt sınıfta aynı imzayla yazılan static metot üst sınıftakini gizler (method hiding). Hangisinin çalışacağı nesneye değil, referansın tipine göre derleme sırasında belirlenir. Sık yapılan hata: @Override yazmadan aynı imzayı kullanıp bunu override sanmak. @Override eklenirse derleyici hata verir.

4. Java’da protected ne anlama gelir? Üyeye aynı sınıf, aynı paketteki bütün sınıflar ve başka paketteki alt sınıflar erişebilir. Başka paketteki alt sınıf bu erişimi yalnızca kendi devraldığı üye üzerinden kullanır, üst sınıf tipindeki başka bir nesnenin protected alanına erişemez. Sık yapılan hata: “Yalnızca alt sınıflar erişir” deyip aynı paket erişimini unutmak.

5. Hiçbir erişim belirleyici yazılmazsa ne olur? Üye package-private olur. Aynı paketteki sınıflar erişebilir, başka paketteki sınıflar, alt sınıflar dahil, erişemez. Sık yapılan hata: C#‘taki gibi varsayılanın private olduğunu sanmak.

6. Abstract class ile interface arasındaki fark nedir? Abstract class’ın alanları, constructor’ı ve her erişim seviyesinde üyesi olabilir, bir sınıf yalnızca birini extends eder. Interface durum tutmaz, alanları yalnızca sabittir ve bir sınıf birden fazlasını implement edebilir. Java 8’den beri interface’te default ve static, Java 9’dan beri private metot yazılabilir. Sık yapılan hata: “Interface’te yalnızca abstract metot olur” demek. Bu Java 7’ye kadar doğruydu.

7. Abstract class’ın constructor’ı neden vardır, nesnesi oluşturulamıyorsa? Constructor, alt sınıf super(...) ile çağırdığında abstract class’taki ortak alanları kurmak için çalışır. Nesne her zaman somut bir alt sınıfın nesnesidir, abstract class onun bir parçasını hazırlar. Sık yapılan hata: “Abstract class’ın constructor’ı olamaz” demek.

8. Composition over inheritance ne demek? Kod paylaşmak için önce bir nesneyi alan olarak içinde tutmayı (has-a) düşünmek, kalıtımı (is-a) gerçek bir tür ilişkisi olduğunda kullanmaktır. Kalıtım alt sınıfı üst sınıfın iç yapısına sıkı bağlar ve istenmeyen metotları da dışarıya açar. Sık yapılan hata: İlkeyi “kalıtım hiç kullanılmaz” diye anlamak.
