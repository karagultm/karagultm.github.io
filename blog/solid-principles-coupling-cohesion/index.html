SOLID Principles, Coupling and Cohesion

Programming 101, Part 6

Part 4 covered the four pillars of OOP, the abstract class vs. interface choice and composition. That post was about how a single class is written. This one asks a question one level up: how should classes connect to each other so that the code does not get harder to change as it grows?

That question has two measures: coupling and cohesion. SOLID can be read as five concrete rules for keeping both measures in good shape. Below I first cover the two concepts, then the five principles one by one. Each principle has a Java example that breaks it and a fixed version. At the end I briefly touch on overusing the principles and then move on to interview questions.

1. Coupling and cohesion

Coupling describes how much two modules depend on each other. A module here can be a class, a package or a service. If changing one class forces you to change other classes too, the coupling between them is high.

Cohesion describes how much the parts inside a module serve the same purpose. If all the fields and methods of a class gather around a single job, cohesion is high. If invoice calculation, sending email and writing logs to a file sit in the same class, it is low.

The goal is low coupling and high cohesion. The two pull in the same direction. When related code is kept in one place, less information has to travel between modules.

Glued parts and snap-together parts make a useful comparison. Try to pull apart two glued pieces and one of them breaks, which is what high coupling feels like. Snap-together pieces hold on to each other only at their connection points. On the cohesion side, compare a multi-tool with a scalpel. The multi-tool does a bit of everything, the scalpel does one job well.

Cohesion Coupling
Looks at The inside of a module The space between modules
Question Do this module’s parts serve the same job? How much of the others does this module know about?
Target High Low
Bad case Unrelated work stuffed into one class A change in one class breaking other classes

Coupling cannot be brought down to zero. Modules that know nothing about each other do not make a program. The aim is not to remove dependencies but to gather them at a narrow and stable point. A class calling another class’s public method is normal. Reaching into its internal fields, having to know the order in which its methods must be called, or steering its internal flow with a flag parameter tightens the bond.

// tight coupling: Order knows the internal structure of Customer
double discount = order.getCustomer().getMembership().getLevel().getDiscountRate();

// loose coupling: only the needed question is asked
double discount = order.getCustomer().discountRate();

The chain on the first line means any change in the membership structure can break that line. In the second, the customer class keeps the details of how the rate is computed to itself.

2. Where SOLID comes from

SOLID is made from the initials of five design principles. Some of them had been known since the 1980s. Around 2000 an author brought them together in a paper on object-oriented design, and the acronym caught on a few years later.

Letter Principle In one sentence
S Single Responsibility A class should have only one reason to change
O Open/Closed New behavior should be addable without modifying existing code
L Liskov Substitution A subtype should work correctly anywhere its supertype is expected
I Interface Segregation A class should not be forced to depend on methods it does not use
D Dependency Inversion High-level code should depend on abstractions, not concrete classes

The five are not independent rules. SRP and ISP raise cohesion, DIP and OCP lower coupling, and LSP makes sure inheritance does not break that arrangement.

3. Single Responsibility Principle (SRP)

The Single Responsibility Principle says that a class should have only one reason to change.

It is often summarized as “a class does one thing”. That summary is incomplete and misleading. The narrower “one thing” is defined, the more every method turns into its own class. The measure is not the size of the job but where the change comes from. If a change requested by accounting and a change requested by reporting both open the same class, that class has two responsibilities.

class Invoice {
    private List<LineItem> items;

    double calculateTotal() { /* tax and discount rules */ }

    void saveToDatabase() { /* SQL query */ }

    String generatePdf() { /* page layout, fonts */ }
}

This class changes for three separate reasons: when a tax rule changes, when the table structure changes and when the PDF template changes. Each comes from different people at different times. If someone breaks the tax calculation while editing the PDF layout, the bug shows up somewhere nobody expected. Testing is harder too, because testing the total means setting up a class that holds a database connection.

class Invoice {
    private List<LineItem> items;
    double calculateTotal() { /* business rules only */ }
}

class InvoiceRepository {
    void save(Invoice invoice) { /* SQL */ }
}

class InvoicePdfWriter {
    String generate(Invoice invoice) { /* page layout */ }
}

Now when a tax rule changes, only Invoice is opened. InvoiceRepository and InvoicePdfWriter depend on Invoice, but Invoice knows about neither of them.

A practical sign of SRP is the class name. A class that is hard to name without the word “and”, or that hides behind a catch-all name like Manager, Processor or Helper, usually has scattered responsibilities.

4. Open/Closed Principle (OCP)

The Open/Closed Principle says that a module should be open for extension and closed for modification. Adding new behavior should be possible by adding new code, rather than opening and editing existing, tested code.

A power strip works this way. Adding a new device does not mean tearing out the wiring in the wall. It gets plugged into a free socket.

class DiscountCalculator {
    double calculate(Customer c, double amount) {
        if (c.getType().equals("STANDARD"))    return amount;
        else if (c.getType().equals("MEMBER")) return amount * 0.95;
        else if (c.getType().equals("VIP"))    return amount * 0.85;
        return amount;
    }
}

When a new customer type is added, this method has to be opened. If the same if chain also exists elsewhere, for example in shipping fees and loyalty points, each one has to be found and updated separately. Forgetting one leads to a silent bug.

interface DiscountPolicy {
    double apply(double amount);
}

class StandardDiscount implements DiscountPolicy {
    public double apply(double amount) { return amount; }
}

class VipDiscount implements DiscountPolicy {
    public double apply(double amount) { return amount * 0.85; }
}

class DiscountCalculator {
    double calculate(DiscountPolicy policy, double amount) {
        return policy.apply(amount);   // this line does not change when a new type arrives
    }
}

A new type means a new class. DiscountCalculator stays the same. The payment method example in Part 4 rested on the same idea: the extension point is an interface plus polymorphism.

Two misreadings are worth watching for. First, “closed for modification” does not mean existing code never changes. Fixing bugs, or updating code when requirements change, is perfectly normal. What should be closed is opening the same place every time the same kind of addition comes along. Second, not every if is an OCP violation. Writing an interface and two classes for a two-branch condition that has not changed in years brings no gain. The principle matters for places that change again and again along the same axis.

5. Liskov Substitution Principle (LSP)

The Liskov Substitution Principle says that an object of a subtype should be usable anywhere the supertype is expected, without breaking the correctness of the program. Code that uses the supertype should not have to know which subclass the object came from.

The compiler only checks the signature part of this. Once Square extends Rectangle is written, Java accepts a square wherever a rectangle is expected. LSP is about behavior: does the square behave like a rectangle?

Square and rectangle

In mathematics every square is a rectangle. That makes the following design look right at first glance.

class Rectangle {
    protected int width, height;
    void setWidth(int width)   { this.width = width; }
    void setHeight(int height) { this.height = height; }
    int area()                 { return width * height; }
}

class Square extends Rectangle {
    @Override void setWidth(int width)   { this.width = width; this.height = width; }
    @Override void setHeight(int height) { this.width = height; this.height = height; }
}

The square ties both setters together to keep its own rule. The problem shows up in code that uses rectangles.

void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20;   // with a Square the area is 16, the expectation breaks
}

resize makes a reasonable assumption about a rectangle: changing the width does not affect the height. That assumption is part of Rectangle’s contract. Square breaks the contract, so even though the code compiles, a square cannot stand in for a rectangle. The mathematical “is-a” relationship does not carry over to software unchanged when the objects are mutable.

The contract

Thinking about LSP in terms of contracts makes it easier. A method’s contract has three parts:

  • Precondition: what the caller must guarantee before calling the method. A subclass cannot strengthen it. If the superclass accepts any positive amount, the subclass cannot say “only amounts under 1000”.
  • Postcondition: what is guaranteed when the method finishes. A subclass cannot weaken it. If the superclass promises to return a sorted list, the subclass cannot return an unsorted one.
  • Invariant: properties of the object that must always hold. A subclass must preserve them.

In the square example, the violated part is the postcondition of setWidth: “the width changes, the height stays the same”. The square cannot give that guarantee.

A subclass overriding a superclass method by throwing UnsupportedOperationException is often a sign of the same problem. If code that makes birds fly throws an error when a penguin comes along, the penguin cannot fulfil the Bird contract. The Java library has an exception worth knowing here. A list created with List.of(...) throws this error on add, but the List documentation defines those methods as “optional” from the start. Since the contract says so explicitly, it is not a violation, though it is still a design choice that calling code has to keep in mind.

The fix

The fix is to not derive the square from the rectangle. The two can share a common supertype without having to replace each other.

interface Shape {
    int area();
}

record Rectangle(int width, int height) implements Shape {
    public int area() { return width * height; }
}

record Square(int side) implements Shape {
    public int area() { return side * side; }
}

The source of the problem was the setters. Once the objects are immutable, there is no longer an expectation like “change the width and the height stays the same”. The bird example is fixed in the same direction: if flying is a capability, it goes into a separate Flyable interface implemented only by birds that can fly, not into the Bird class.

6. Interface Segregation Principle (ISP)

The Interface Segregation Principle says that no class should be forced to depend on methods it does not use. Instead of one large interface that covers everything, small interfaces split by what their users need are preferred.

A restaurant menu is a good picture. A vegetarian customer is not handed the mixed grill and told to eat only the salad. A separate menu is prepared.

interface MultiFunctionPrinter {
    void print(Document d);
    void scan(Document d);
    void fax(Document d);
}

class BasicPrinter implements MultiFunctionPrinter {
    public void print(Document d) { /* prints */ }
    public void scan(Document d)  { throw new UnsupportedOperationException(); }
    public void fax(Document d)   { throw new UnsupportedOperationException(); }
}

BasicPrinter can only print, but the interface forces it to write the scan and fax methods too. Those two empty methods bring along the LSP problem from the previous section. On top of that, a client that only prints has to be recompiled when the signature of the fax method changes.

interface Printer { void print(Document d); }
interface Scanner { void scan(Document d); }
interface Fax     { void fax(Document d); }

class BasicPrinter implements Printer {
    public void print(Document d) { /* prints */ }
}

class OfficeMachine implements Printer, Scanner, Fax {
    /* actually implements all three */
}

Since a Java class can implement more than one interface, this principle is easy to apply in Java. The splitting criterion is the client: interfaces are split according to the code that uses them, not the class that implements them. A reporting module that only prints sees Printer and does not know what else the machine can do.

SRP and ISP look alike. SRP looks at a class’s reasons to change, ISP at an interface’s clients. One organizes the inside of a class, the other the face it shows to the outside.

7. Dependency Inversion Principle (DIP)

The Dependency Inversion Principle says two things. High-level modules should not depend on low-level modules, both should depend on abstractions. Abstractions should not depend on details, details should depend on abstractions.

High level means the application’s actual business rules: how an order is approved, when a notification is sent. Low level means the details those rules use: which database, which email library.

The electrical wiring in a house is not soldered directly to a lamp. A socket goes in between. The wiring knows the socket standard, and the lamp knows the plug standard. When the lamp changes, nobody has to break the wall.

class EmailSender {
    void send(String to, String message) { /* SMTP */ }
}

class OrderService {
    private final EmailSender sender = new EmailSender();   // hard-wired to a concrete class

    void approve(Order order) {
        // ... business rules
        sender.send(order.customerEmail(), "Your order has been approved");
    }
}

OrderService carries the business rule, but it is tied directly to an email class. When notifications move to SMS, or when a test should not send real email, this class has to be opened.

interface Notifier {
    void send(Order order, String message);
}

class OrderService {
    private final Notifier notifier;

    OrderService(Notifier notifier) {   // the dependency is passed in
        this.notifier = notifier;
    }

    void approve(Order order) {
        // ... business rules
        notifier.send(order, "Your order has been approved");
    }
}

class EmailNotifier implements Notifier { /* SMTP */ }
class SmsNotifier implements Notifier { /* SMS provider */ }

What does “inversion” invert?

In the first design the dependency arrow points down: OrderService -> EmailSender. In the second, both arrows point at the interface in the middle: OrderService -> Notifier <- EmailNotifier. The low-level class now conforms to a contract defined by the high level.

There is a detail that often gets skipped. The Notifier interface belongs to the business-rule side that uses it, not to the email side. Putting the interface in the email package and naming it EmailInterface still points the dependency at the low level, it only adds a layer in between. What gets inverted is the direction of the source-code dependency. The direction of the call at runtime stays the same.

DIP vs. dependency injection

Dependency Injection means an object receives the objects it needs from outside, usually through its constructor, instead of creating them itself with new. OrderService(Notifier notifier) above is an example of constructor injection.

The two are often confused, but they sit at different levels:

DIP Dependency injection
What A design principle A technique
Question What should code depend on? How does a dependency reach the object?
Answer An abstraction, not a concrete class From outside: constructor, setter or a framework

DI is the most common way to apply DIP, but they are not the same thing. Taking a concrete EmailSender through the constructor is DI, but because the class is still tied to a concrete class, it does not follow DIP. The reverse is possible too: depending on an abstraction through a factory or a service locator follows DIP without DI. DI frameworks are tools that automate creating these objects and wiring them together. Inversion of Control is a broader idea: creating objects and managing the flow are taken away from the code itself and handed to an outside structure. DI is one form of it.

Notes sometimes say “if you write new inside your code, you are violating DIP”. That is too broad. Creating new ArrayList<>(), new BigDecimal("10") or a value object is fine, since these are stable and not expected to change. DIP targets volatile details: the database, the network, the file system, third-party services. These are also usually the dependencies you want to replace with a fake in tests.

8. The cost of overdoing it

Every SOLID principle comes with a cost: more classes, more interfaces, more jumping between files while reading code. The cost is worth paying when the problem the principle prevents actually exists.

Common excesses:

  • Writing an interface for every class that has a single implementation and is never expected to have another. If no fake is needed for tests, that interface is just a layer of indirection.
  • Reading SRP as “one method per class” and splitting logic into dozens of tiny classes. Cohesion does not go up in that case, it goes down, because code that belongs together gets scattered.
  • Turning every if into a strategy hierarchy because something might come along in the future.

A good measure is change itself. When the same place is opened a second or third time for the same reason, it is time to put an abstraction there. An abstraction added earlier often ends up on the wrong axis, because it is not yet known in which direction the code will change.

Interview questions

1. What are coupling and cohesion, and which one should be high? Coupling measures how much modules depend on each other, cohesion measures how much the parts of a module serve the same purpose. The goal is low coupling and high cohesion. That way a change stays in one place and does not break other modules. Common mistake: Saying coupling should be zero. The aim is not to remove dependencies but to gather them at a narrow and stable point.

2. What do the letters of SOLID stand for? Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation and Dependency Inversion. In order: one reason to change, extending without modifying, a subtype being able to replace its supertype, small client-specific interfaces, and depending on abstractions. Common mistake: Reciting the principles without being able to give an example for each.

3. What does Single Responsibility mean? A class should have only one reason to change. The measure is not how many methods the class has, but how many different sources its change requests come from. Common mistake: Reading SRP as “each class contains one method”.

4. Should Square extend Rectangle? Not for a mutable rectangle class. The rectangle’s contract says changing the width does not affect the height. A square cannot give that guarantee and breaks code that relies on it. With immutable objects, or a shared Shape interface, the problem goes away. Common mistake: Assuming LSP holds because the code compiles. The compiler checks signatures, not behavior.

5. Under LSP, how can a subclass change preconditions and postconditions? It cannot strengthen preconditions, it can only weaken them. It cannot weaken postconditions, it can only strengthen them. It must also preserve the superclass’s invariants. Common mistake: Getting it backwards, thinking a subclass may demand stricter input.

6. Does the Open/Closed Principle mean existing code is never changed? No. Bugs get fixed, and code is updated when requirements change. The principle asks that the same code is not opened every time the same kind of addition comes along, so new behavior can be added with a new class. Common mistake: Treating every if block as an OCP violation.

7. Why does interface segregation matter? A large interface forces implementing classes to write methods they do not use, either empty or throwing an error. Client code is also affected by changes to methods it never calls. Interfaces are split according to the code that uses them. Common mistake: Splitting interfaces according to the implementing class.

8. What is the difference between dependency inversion and dependency injection? DIP is a design principle saying code should depend on abstractions rather than concrete classes. DI is the technique of giving an object its dependencies from outside, for example through the constructor. DI is a common way to apply DIP, but injecting a concrete class is DI without being DIP. Common mistake: Treating them as the same thing, or saying “I use a DI framework, so I follow DIP”.
