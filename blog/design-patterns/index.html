Design Patterns: Singleton, Factory, Builder, Adapter, Decorator, Strategy, Observer

Programming 101, Part 7

Part 6 covered the SOLID principles: a class should have one responsibility, code should be extendable without being modified, and code should depend on abstractions rather than concrete classes. The principles say what to aim for, but they do not describe how to get there. Design patterns fill that gap. They are named solutions to common design problems, tried many times over.

Pattern questions in interviews usually come in two forms. Either a pattern is named and the question is what it does, or a problem is described and the question is which pattern fits. Answering the second kind takes knowing the problem a pattern solves more than knowing its code.

Below I first explain what a pattern is and the three groups. Then I go through eight patterns one by one: the problem, the solution and a short Java example for each. After that come the link between patterns and SOLID, and the trap of memorizing patterns. At the end there are common interview questions.

1. What a design pattern is

A Design Pattern is a general solution template for a recurring problem in object-oriented design. It is not a piece of code to copy and paste. The description of the problem, the structure of the solution and the cost of that solution come together.

It is similar to the landing on a staircase in architecture. Every building has a different staircase, but splitting a long flight in the middle with a place to rest is a known solution with a name. The name lets two architects agree without long explanations. That shared vocabulary is the biggest benefit of patterns. Saying “a decorator would fit here” in a code review replaces five sentences of explanation.

Most of the pattern list in use today comes from the classic patterns book published in 1994. The book defines 23 patterns and splits them into three groups. Its examples were written in C++ and Smalltalk, and in Java some patterns can be written more briefly using the language’s own features.

2. Three groups: creational, structural, behavioral

Patterns are grouped by the question they answer.

Group The question it asks Examples in this post
Creational How is an object created, and by whom? Singleton, Factory Method, Builder
Structural How are classes and objects put together? Adapter, Decorator
Behavioral How do objects communicate, and how is responsibility shared? Strategy, Observer, Mediator

Creational patterns collect object creation in one place instead of scattering new calls throughout the code. Structural patterns place objects inside one another to connect incompatible parts or to add features to an object. Behavioral patterns organize the communication between objects and the choice of algorithm.

3. Singleton

Singleton guarantees that only one object of a class is created during the lifetime of the application and provides a global access point to it. It is considered for objects that should exist only once, such as a configuration manager, a connection pool or a logger.

The classic solution has three parts: the constructor is made private, the single object is kept in a static field, and a static method hands that object out. The first version found in the source notes and in many tutorials looks like this:

public class Config {
    private static Config instance;
    private Config() { }

    public static Config get() {
        if (instance == null) {         // two threads can both see null
            instance = new Config();
        }
        return instance;
    }
}

This code is correct with one thread and wrong with several. If two threads pass the instance == null check at the same time, two separate objects are created. It is a race condition and rarely shows up in tests, because it depends on timing.

The thread-safe version

The shortest fix is to make the method synchronized, but then every call takes a lock. Once the object exists, that lock is a pointless cost. The approach recommended in Java is the Initialization-on-demand Holder:

public class Config {
    private Config() { }

    private static class Holder {
        static final Config INSTANCE = new Config();
    }

    public static Config get() {
        return Holder.INSTANCE;   // Holder is loaded on the first call
    }
}

The inner class Holder is not loaded until get() is called for the first time. When the JVM initializes a class’s static fields, it guarantees that only one thread does so. This gives lazy creation and thread safety without writing a lock.

There are two other options. Double-Checked Locking checks for null twice, once before the lock and once inside it, but the field must be volatile. Without volatile the JVM may reorder the writes, and another thread can see a reference to an object whose constructor has not finished. The second option is a single-element enum: enum Config { INSTANCE; }. An enum cannot be instantiated a second time through reflection and stays single through serialization. The other approaches need extra measures for those two cases.

Why it is called an anti-pattern

Singleton appears on “things to avoid” lists as often as on pattern lists. The reasons:

  • It is global state. Because Config.get() can be called from anywhere, what a class depends on is not visible in its signature. The dependency is hidden inside a method.
  • It makes testing harder. When testing a class that uses the singleton, there is no way to swap in a fake object. Tests share the state of the same object and affect each other.
  • It does two jobs: its actual work and the management of its own lifecycle. That goes against the single responsibility principle.
  • “Single” is less certain than it looks. Each class loader can create its own copy. In a system running in several processes, each process has its own object.

These are problems with the global access path, not with the idea of a single object. If one configuration object is needed, it can be created once at startup and passed to the classes that need it through their constructors. The “singleton scope” in dependency injection frameworks is exactly that: the object is single, but classes receive it from outside instead of pulling it with get().

4. Factory Method

Every place where code writes new Truck(), it ties itself to the Truck class. When some deliveries later have to go by ship, all of those lines must be found and changed.

Factory Method leaves object creation to a method and lets subclasses decide which class to instantiate. The superclass writes the workflow and asks an abstract method for the object it needs along the way.

A logistics company is a good example. Planning a delivery is always the same process: prepare the vehicle, load it, send it off. Only the vehicle type changes. The road division uses trucks, the sea division uses ships.

interface Transport { void deliver(); }
class Truck implements Transport { public void deliver() { /* by road */ } }
class Ship  implements Transport { public void deliver() { /* by sea */ } }

abstract class Logistics {
    abstract Transport createTransport();     // factory method

    void planDelivery() {
        Transport t = createTransport();      // does not know the concrete class
        t.deliver();
    }
}

class RoadLogistics extends Logistics { Transport createTransport() { return new Truck(); } }
class SeaLogistics  extends Logistics { Transport createTransport() { return new Ship(); } }

When air freight is added, a new Plane and a new AirLogistics are written. Logistics and the existing subclasses do not change.

This pattern is often confused with something else. A single class that looks at a parameter and returns an object, as in if (type.equals("Road")) return new Truck();, is a Simple Factory. It is useful and collects new calls in one place, but it is not one of the patterns in the classic book. Adding a new type means touching the if chain inside the factory. With Factory Method, extension happens through a new subclass. Static methods like List.of(...) or Integer.valueOf(...) are a third thing. They are called Static Factory Methods and can be thought of as named alternatives to a constructor.

5. Builder

When a class has two required fields and five optional ones, constructors start to multiply: one with two parameters, one with three, one with four. This is called a Telescoping Constructor. In new User("admin", null, null, 30, true) it is hard to tell which null means what, and if two String parameters are swapped, the compiler will not notice.

Builder separates the step-by-step construction of a complex object from the object itself. Its most common form in Java is a helper class inside the class, with methods that can be chained.

public class User {
    private final String name;    // required
    private final String email;   // optional
    private final int age;

    private User(Builder b) { name = b.name; email = b.email; age = b.age; }

    public static class Builder {
        private final String name;
        private String email;
        private int age;

        public Builder(String name) { this.name = name; }
        public Builder email(String e) { this.email = e; return this; }
        public Builder age(int a)      { this.age = a; return this; }
        public User build()            { return new User(this); }
    }
}

User u = new User.Builder("admin").age(30).build();

The name of each value is readable in the call. Since the fields are final, the object does not change once it is built. Validation rules, such as “age cannot be negative”, can be checked in one place inside build(). In the Java library, java.net.http.HttpRequest.newBuilder() is an example of this form.

One note: the Builder in the classic book aimed to produce different representations from the same construction process (for example both HTML and PDF from the same document) and included a “director” class that ran the process. In everyday Java, Builder means the fluent form above.

6. Adapter

The code expects one interface, the class at hand offers a different one, and that class cannot be changed. A third-party library or an old module is usually like this.

Adapter is an intermediate class that translates an incompatible interface into the expected one. A travel plug adapter is similar. Neither the device’s plug nor the wall socket changes, the piece in between makes them fit.

interface PaymentService {
    void pay(long cents);
}

// third-party library, cannot be changed
class LegacyPaymentLibrary {
    void sendMoney(double amount, String currency) { /* ... */ }
}

class LegacyPaymentAdapter implements PaymentService {
    private final LegacyPaymentLibrary library = new LegacyPaymentLibrary();

    public void pay(long cents) {
        library.sendMoney(cents / 100.0, "EUR");   // unit and signature translation
    }
}

The rest of the application only knows PaymentService. When the library is replaced, only the adapter is rewritten. In Java, InputStreamReader is an adapter that turns a byte stream into a character reader, and Arrays.asList makes an array usable through the List interface.

Here the adapter holds the library as a field. This is called an Object Adapter. There is also a Class Adapter form that inherits from the library class, but it is used less in Java because of single inheritance.

7. Decorator

When writing to a data source, sometimes compression is needed, sometimes encryption, sometimes both. If a separate subclass is written for each combination, the number of classes grows quickly: CompressedFile, EncryptedFile, CompressedEncryptedFile.

Decorator adds behavior to an object at runtime by wrapping it in another object that implements the same interface. The wrapper forwards the work to the inner object and adds its own contribution before or after. Layers of clothing in winter are a reasonable comparison. Each layer adds something, and layers can be put on and taken off in any order.

interface DataSource { void write(String data); }

class FileDataSource implements DataSource {
    public void write(String data) { /* write to disk */ }
}

class CompressionDecorator implements DataSource {
    private final DataSource inner;
    CompressionDecorator(DataSource inner) { this.inner = inner; }
    public void write(String data) { inner.write(compress(data)); }
    private String compress(String s) { /* ... */ return s; }
}

// EncryptionDecorator is written the same way
DataSource ds = new CompressionDecorator(new EncryptionDecorator(new FileDataSource()));
ds.write("report");   // compressed first, then encrypted, then written

Each decorator does one job and they can be combined in any order. Java’s I/O classes are built on this pattern: in new BufferedReader(new InputStreamReader(new FileInputStream("a.txt"))) each layer wraps the previous one. Collections.unmodifiableList is also a decorator that wraps a list and blocks the methods that modify it.

To keep it apart from Adapter: an adapter changes the interface and leaves behavior alone. A decorator keeps the interface and adds behavior.

8. Strategy

When an order total is calculated, the discount rule depends on the customer type. The first solution that comes to mind is an if (type == STUDENT) ... else if (type == CORPORATE) ... chain. Every new rule makes that method longer, and the calculation code has to know about every rule.

Strategy puts interchangeable algorithms into separate classes and lets the choice between them be made at runtime. In a navigation app, the car, walking and public transport options are each a separate route calculation. The rest of the app calls the chosen calculation without caring what is inside it.

interface DiscountStrategy {
    double apply(double amount);
}

class Order {
    private final DiscountStrategy discount;
    Order(DiscountStrategy discount) { this.discount = discount; }

    double total(double subtotal) { return discount.apply(subtotal); }
}

Order student   = new Order(t -> t * 0.90);
Order corporate = new Order(t -> t > 1000 ? t - 100 : t);
Order regular   = new Order(t -> t);

Because DiscountStrategy is an interface with a single method, since Java 8 each strategy can be written as a lambda. In the classic book each strategy was a separate class. The most familiar example in Java is Comparator: in list.sort(Comparator.comparing(Person::getAge)) the sorting algorithm stays the same and the comparison strategy is passed in from outside.

Strategy is structurally very close to the State pattern. The difference is intent: a strategy is chosen by the calling code. With State, the object changes its own behavior as its state changes.

9. Observer

When a product comes back in stock, the users who asked to be notified should get an email, a push notification and a text message. If the product class calls these three services directly, every new notification channel means changing the product class. The other option is for the notification services to keep asking “is it in stock yet” (polling), which means wasted requests.

Observer makes sure that when an object’s (the Subject’s) state changes, the objects registered with it (the Observers) are notified automatically. The subject does not know who its observers are, only their common interface. It works like a newspaper subscription. A reader subscribes once, and the publisher sends every issue to the subscriber list.

interface StockListener {
    void backInStock(String productName);
}

class Product {
    private final String name;
    private final List<StockListener> listeners = new ArrayList<>();
    Product(String name) { this.name = name; }

    void subscribe(StockListener l)   { listeners.add(l); }
    void unsubscribe(StockListener l) { listeners.remove(l); }

    void addStock(int count) {
        if (count > 0) listeners.forEach(l -> l.backInStock(name));
    }
}

product.subscribe(name -> sendEmail(name));
product.subscribe(name -> sendPush(name));

A few points need attention. If an observer is done but unsubscribe is never called, the subject keeps a reference to it and the garbage collector cannot reclaim it. This is the Lapsed Listener problem and a well-known cause of memory leaks in Java. Notifications in this example are synchronous: a slow observer holds up the whole chain, and an observer that throws can stop the ones after it from running. The order in which observers are called should not be relied on either.

Java’s java.util.Observer and Observable classes have been deprecated since Java 9. The recommendation is to write your own interface or use PropertyChangeListener. The Publish-Subscribe model in message queues is a relative of Observer. The difference is the broker in between: the publisher does not keep the subscriber list, and communication is usually asynchronous.

10. Mediator

If every plane at an airport had to talk to every other plane before landing, n planes would need n·(n−1)/2 connections. Instead, each plane talks only to the tower. The tower decides who uses the runway. The planes do not know each other.

Mediator stops objects from connecting to each other directly and runs their communication through a single center. Each object knows only the mediator.

class Tower {
    private final Queue<Plane> queue = new ArrayDeque<>();
    private boolean runwayFree = true;

    void requestLanding(Plane p) {
        if (runwayFree) { runwayFree = false; p.cleared(); }
        else queue.add(p);                 // queues it without asking other planes
    }
    void runwayCleared() {
        Plane next = queue.poll();
        if (next != null) next.cleared(); else runwayFree = true;
    }
}

class Plane {
    private final Tower tower;             // knows only the tower
    Plane(Tower tower) { this.tower = tower; }
    void wantToLand() { tower.requestLanding(this); }
    void cleared()    { /* land */ }
}

It is also common in UI programming. If choosing a “country” in a form changes the “city” list, and choosing a city changes the shipping fee, the form itself can act as the mediator instead of spreading these rules across the fields.

It has a cost. Dependencies do not disappear, they move to the center. Without care, the mediator turns into a class that knows every rule and gets harder to change as it grows. The difference from Observer is the shape of the relationship: in Observer one subject broadcasts to many listeners. In Mediator many objects affect each other, and the rules for that interaction live in the center.

11. Patterns and SOLID

Most patterns are a concrete application of one of the SOLID principles. Naming the related principle when explaining why a pattern works leaves a good impression in an interview.

Pattern Related principle How
Strategy Open/Closed A new rule is added as a new class or lambda, Order does not change
Factory Method Open/Closed, Dependency Inversion The superclass knows the Transport interface, not the concrete class
Decorator Single Responsibility, Open/Closed Each wrapper does one job, features are added without touching the existing class
Decorator, Adapter Liskov Substitution The wrapper must be usable anywhere the wrapped type is expected
Adapter Dependency Inversion The application depends on its own interface, not on the third-party library
Observer Interface Segregation The listener interface has a single method
Singleton Goes against Single Responsibility and Dependency Inversion It also manages its own lifecycle, and calling code is tied to the concrete class

The last row matters as much as the rest of the table. Using a pattern does not automatically mean the principles are followed.

12. The trap of memorizing patterns

After learning patterns, trying to fit one to every problem is a common mistake. Adding DiscountStrategy, DiscountStrategyFactory and DiscountManager to code that has a single discount rule does not make it flexible, it only makes it harder to read. Four classes end up doing the work of a two-line if.

A pattern is not a goal, it is a known answer to a problem. A healthy order is this: write the simplest solution first, and move to a suitable pattern when the code starts to strain at a place that really needs to change (the third else if, the same new call repeated in ten places). Adding flexibility where nothing will change is paying in advance for a need that never arrives.

The language also plays a part. Some of the patterns in the classic book existed to cover gaps in the languages of the time. In languages where functions can be passed as values, Strategy or Command does not need a class hierarchy, a lambda is enough. In Java, enum can make the classic Singleton code unnecessary, and records can do the same for some uses of Builder.

That is why interviews tend to ask “what is wrong with this code and how would you fix it” more than “draw the UML diagram for Observer”. Starting the answer with the problem rather than the pattern name is more convincing: “Every new rule changes this method. If I move the rules into separate objects, the method stays closed. That is called Strategy.”

Interview questions

1. What is a design pattern, and what groups are there? It is a named, general solution to a recurring design problem. Creational patterns organize object creation, structural patterns how objects are combined, and behavioral patterns how objects communicate. Common mistake: Describing a pattern as a ready-made library or a piece of code to copy.

2. How do you write a thread-safe Singleton? With the initialization-on-demand holder: the single object lives in a final field of a static inner class, and the JVM guarantees that class initialization happens on one thread. The alternatives are a single-element enum and double-checked locking with a volatile field. Common mistake: Writing double-checked locking without volatile. Another thread can see a half-constructed object.

3. Why is Singleton seen as an anti-pattern? It creates global state and hides the dependency inside a method, so a fake object cannot be swapped in during tests. The class also manages both its own work and its own lifecycle. If a single object is needed, creating it once and passing it through constructors is preferred. Common mistake: Thinking the problem is having one object. The problem is the global access path.

4. What is the difference between Factory Method and a simple factory? A simple factory is a single class that looks at a parameter and returns an object through an if or switch, and it changes when a new type is added. In Factory Method the superclass defines an abstract creation method, subclasses decide which object to create, and extension happens through a new subclass. Common mistake: Calling every create() method a Factory Method.

5. When is Builder used? For objects with many optional parameters, especially ones that should be immutable. It replaces telescoping constructors, every value is passed by name, and validation happens in one place inside build(). Common mistake: Writing a builder for a simple class with two fields.

6. How does Decorator differ from inheritance, and from Adapter? Inheritance fixes behavior at compile time and at the class level, so each combination needs its own subclass. Decorator adds behavior at runtime by wrapping the object, and layers can be combined in any order. Adapter changes the interface, while a decorator keeps the interface and adds behavior. Common mistake: Not being able to explain why Java I/O classes are created nested inside each other.

7. What problem does the Strategy pattern solve? It moves algorithms that are chosen through growing if-else or switch chains into separate objects and makes them swappable at runtime. When a new algorithm is added, the class using it does not change. Comparator is the well-known Java example. Common mistake: Mixing up Strategy and State. A strategy is chosen by outside code, while in State the object changes based on its own state.

8. How does a memory leak happen with the Observer pattern? The subject holds strong references to registered observers. If an observer is no longer used but is never removed from the list, the garbage collector cannot reclaim it. This is the lapsed listener problem, and the fix is for an observer to unsubscribe when it is done. Common mistake: Treating Observer and publish-subscribe as the same thing. In pub/sub a broker sits in between and the publisher does not know its subscribers.
