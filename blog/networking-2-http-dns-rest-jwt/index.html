Networking 2: HTTP, DNS, REST, JWT, Cookies and Sessions

Programming 101, Part 12

Part 11 covered how data travels from one machine to another over TCP, UDP and QUIC. This post moves one layer up, to the application layer. The topic is what happens between typing an address into a browser and seeing the page.

First come DNS and setting up the connection, then HTTP methods, status codes, headers and REST principles. The last part is about authentication: cookies, sessions, JWT and CORS. At the end there are interview questions with short answers.

1. From the address bar to the page

When https://example.com/products is typed into a browser and Enter is pressed, things happen roughly in this order:

  1. The address is split up: scheme https, domain example.com, path /products. No port is given, so 443 is used.
  2. The domain’s IP address is found through DNS, checking caches first.
  3. A TCP connection is opened to port 443 of that address (one RTT).
  4. A TLS handshake runs on top of it (one more RTT with TLS 1.3).
  5. The HTTP request goes over the encrypted channel: GET /products.
  6. The server returns a response made of a status code, headers and a body.
  7. The browser makes new requests for the CSS, JavaScript and images in the HTML, most of them over the same connection.

With HTTP/3, steps 3 and 4 merge into a single round trip inside QUIC.

2. DNS: from domain name to IP address

DNS (Domain Name System) is a hierarchical database, distributed around the world, that maps domain names to IP addresses. It resembles a phone book, except there is no single book. Each level only knows who holds the level below it.

The resolution chain

The browser first checks its own cache, then the operating system’s. If the answer is not there, it sends the question to a Recursive Resolver. This is usually the internet provider’s DNS server or a public one configured by hand. The resolver asks every question needed to find the answer on the client’s behalf:

  1. Root Server: The resolver asks about example.com. The root server does not know the answer and returns the servers responsible for .com. There are 13 root server names, each spread across hundreds of physical machines via anycast.
  2. TLD Server (Top-Level Domain): The .com server does not know the answer either. It says which name servers hold the example.com zone.
  3. Authoritative Server: The server that actually holds the domain’s records. It returns the IP address.

The resolver returns the answer to the client and stores it in its cache. The questions the resolver sends to the other servers are iterative: at each step it gets an “ask this one” reply and goes to the next server itself.

Caching and TTL

Every DNS record has a TTL (Time To Live) in seconds, which says how long the record may be cached. With a TTL of 3600, the resolver will not ask the same question again for an hour. Most steps in the chain therefore rarely run in practice. The addresses of the .com servers are almost always in the cache.

There is a side effect. When an IP address changes, the old record lives on in some caches until its TTL runs out. What is called “DNS propagation” is really old caches expiring. Lowering the TTL to a few minutes before a migration is common for this reason.

In Python, the operating system’s resolver is called like this:

import socket

for info in socket.getaddrinfo("example.com", 443, proto=socket.IPPROTO_TCP):
    print(info[0].name, info[4][0])
# AF_INET 203.0.113.10
# AF_INET 203.0.113.11

Getting several addresses back is normal. If one does not respond, the client tries another. The addresses in the output are from the documentation range, real output will differ.

3. TCP, TLS and HTTPS

Once the IP address is known, the TCP handshake from Part 11 takes place. If HTTPS is used, TLS follows.

TLS (Transport Layer Security) is the protocol that encrypts traffic between two ends and verifies the server’s identity. HTTPS is not a separate protocol, it is HTTP spoken over a TLS connection. Three things happen during the handshake:

  • The client sends the cipher suites it supports and the domain it wants to reach (SNI).
  • The server sends its certificate, which binds the domain to a public key and is signed by a certificate authority. The browser checks the signature chain and the domain.
  • Both sides derive a shared session key through asymmetric key exchange. Later traffic is protected with this key using symmetric encryption, which is much faster.

With HTTPS, the path, query parameters, headers and body are encrypted. The IP address being contacted, and in most cases the domain in the SNI, can still be seen by someone on the network.

4. The structure of an HTTP message

HTTP (Hypertext Transfer Protocol) is an application protocol in which the client sends a request and the server answers. In HTTP/1.1 messages are plain text:

GET /products?page=2 HTTP/1.1
Host: example.com
Accept: application/json
Authorization: Bearer eyJhbGciOi...

The request line holds the method, path and version. The headers are followed by an empty line, then the body if there is one. The response has the same shape, with a status line such as HTTP/1.1 200 OK first. HTTP/2 and HTTP/3 carry the same information in binary frames.

5. Methods, safe and idempotent

The method says what the client wants to do with the resource.

Method What it does Safe Idempotent
GET Reads the resource Yes Yes
HEAD Same as GET, without a body Yes Yes
OPTIONS Asks which options are supported Yes Yes
POST Creates a new resource or triggers an action No No
PUT Replaces the resource entirely with the given one, may create it No Yes
PATCH Changes part of the resource No Not guaranteed
DELETE Deletes the resource No Yes

A safe method does not change state on the server. Browsers and caches repeat and prefetch GET requests freely, so a GET endpoint that deletes an order is dangerous.

An idempotent method leaves the server in the same final state whether it is sent once or ten times. If PUT /users/42 is sent ten times with the same body, the user ends up in the same state. A second DELETE /orders/7 may return 404, but the server’s state is the same: the order is gone. Idempotency is about the state being the same, not the response.

This matters in practice when the network fails. If the connection drops before the response arrives, the client cannot know whether the request was processed. Retrying an idempotent request is safe, retrying a POST is not: the same payment request sent twice creates two payments. Payment APIs therefore ask for a unique Idempotency-Key header and do not process a second request with the same key.

The common list “REST has four methods: GET, POST, PUT, DELETE” leaves out PATCH. PUT also does not mean “update”, it means “replace the resource entirely with this”. Fields that are not sent are treated as removed.

6. Status codes

The first digit of a status code gives its class:

Class Meaning
1xx Informational
2xx Success
3xx Redirection
4xx Client error
5xx Server error

Common ones:

Code When
200 OK Success, the result is in the body
201 Created A resource was created with POST, the Location header gives its address
204 No Content Success, nothing to return (most DELETEs)
301 / 308 Permanent redirect
302 / 307 Temporary redirect
304 Not Modified The cached copy is still valid
400 Bad Request Malformed request, validation error
401 Unauthorized Not authenticated, token missing or invalid
403 Forbidden Identity known, but not allowed to do this
404 Not Found The resource does not exist
429 Too Many Requests Rate limit exceeded
500 Internal Server Error Unexpected error on the server
502 / 504 A proxy got an invalid response from the server behind it / got no response in time
503 Service Unavailable The server temporarily cannot serve

Although 401 is named “Unauthorized”, it means “I don’t know who you are”. 403 means “I know who you are, and you are not allowed”. 307 and 308 keep the method when redirecting, while with 301 and 302 a client may turn a POST into a GET.

7. Headers and a request from Python

Headers carry metadata about the request and the response. Common ones:

  • Host: The requested domain. Required in HTTP/1.1, it makes hosting several sites on one IP possible.
  • Content-Type and Accept: The body’s format and the formats the client accepts.
  • Authorization: Credentials, for example Bearer <token>.
  • Cache-Control: Caching rules, for example no-store or max-age=60.
  • ETag and If-None-Match: The client sends the version it holds, and if the resource has not changed the server returns a bodiless 304.
  • Set-Cookie and Cookie: Set a cookie and send it back.

An HTTPS request with Python’s standard library:

import http.client

conn = http.client.HTTPSConnection("example.com", timeout=10)
conn.request("GET", "/", headers={"Accept": "text/html"})
resp = conn.getresponse()
print(resp.status, resp.reason, resp.version)  # 200 OK 11
print(resp.getheader("Content-Type"))          # text/html; charset=utf-8
body = resp.read()
conn.close()

HTTPSConnection does the DNS lookup, the TCP connection and the TLS handshake internally. A resp.version of 11 means HTTP/1.1. urllib.request.urlopen, on the other hand, raises 4xx and 5xx codes as HTTPError.

8. HTTP/1.1, HTTP/2 and HTTP/3

HTTP/1.1 HTTP/2 HTTP/3
Transport TCP TCP QUIC (over UDP)
Message format Text Binary frames Binary frames
Concurrent requests on one connection No, one after another Yes, as streams Yes, as streams
Header compression None HPACK QPACK
Head-of-line blocking At the application layer At the TCP layer Only in the stream with the loss
TLS Optional Required in practice by browsers Part of the protocol

Multiplexing, introduced by HTTP/2, means carrying many requests interleaved over one connection. HTTP/3, as described in Part 11, replaces the transport layer with QUIC.

9. REST principles

REST (Representational State Transfer) is an architectural style that describes access to resources over a network. It was defined in a doctoral dissertation in 2000. It is not a protocol and is not tied to HTTP, although in practice it is almost always implemented with HTTP.

The principles expected in an interview:

  • Resource-oriented URLs: A URL points to a resource, not an action. The method states the action.
  • Stateless: Each request carries everything needed to process it, credentials included. The server keeps no client context between requests.
  • Right method and right code: On an error, a fitting 4xx or 5xx code is used instead of returning {"error": true} inside a 200.
Action-oriented (avoided) Resource-oriented
GET /getAllOrders GET /orders
POST /createOrder POST /orders
GET /deleteOrder?id=7 DELETE /orders/7
GET /getUserOrders?userId=42 GET /users/42/orders

The benefit of statelessness shows up in scaling: consecutive requests can go to different servers. It does not mean there is no database. What is ruled out is keeping session context in server memory and having later requests depend on it.

10. Cookies and sessions

HTTP is stateless, so the server cannot tell from the protocol that two requests come from the same user. There are two common ways to recognize a logged-in user: a server-side session and a token.

A Cookie is a small key-value item the server gives the browser with the Set-Cookie header, which the browser sends back with the Cookie header on later requests to the same site. A cookie is a transport mechanism. It can hold a session ID or a JWT.

In the Session approach, after a successful login the server generates a random, unguessable ID and stores the user’s data under that ID on its own side. It gives the browser only the ID:

HTTP/1.1 200 OK
Set-Cookie: session_id=Xk29fQa7Lm; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600

On every later request the browser sends Cookie: session_id=Xk29fQa7Lm, and the server looks the ID up in its store to find the user. It works like a coat check ticket. The ticket only has a number on it, the coat stays with the attendant.

With more than one server, the session store is kept somewhere all of them can reach.

Cookie flags

Flag What it does Protects against
HttpOnly JavaScript cannot read the cookie through document.cookie Cookie theft via XSS
Secure The cookie is only sent over HTTPS Eavesdropping on unencrypted connections
SameSite=Strict Not sent on any request that starts from another site CSRF
SameSite=Lax Sent on top-level GET navigations from other sites, not on other cross-site requests CSRF, without breaking usability
SameSite=None Sent on every request, must be combined with Secure No protection, for cross-site use

CSRF (Cross-Site Request Forgery) is another site sending a request to the target site through the user’s browser. Because the browser attaches the cookie automatically, the request looks like it comes from the logged-in user, and SameSite limits this. XSS (Cross-Site Scripting) is an attacker injecting their own JavaScript into the page, and HttpOnly stops that script from reading the cookie.

11. Sessions versus tokens

In the token approach the server does not store the user’s data. It signs the data and hands it to the client. The client brings it back on every request, and the server uses the signature to confirm the data has not been changed.

Server-side session Signed token (JWT)
Where user data lives In the server’s store Inside the token
What the client holds A meaningless ID Readable but signed data
On every request A store lookup A signature check, no store needed
Logout and revocation Deleting the record is enough Hard, valid until it expires
Several servers and services Needs a shared store Any service with the key can verify

For a single web application a session is simple and secure. Tokens make sense when many services need to verify the user independently.

12. JWT

JWT (JSON Web Token) is a token format made of three parts separated by dots: header.payload.signature.

  • Header: The signing algorithm and type, for example {"alg": "HS256", "typ": "JWT"}.
  • Payload: Fields called claims. Standard ones are sub (user ID), iat (issued at), exp (expiry), iss (issuer), aud (intended service).
  • Signature: The first two parts signed with a key.

The header and payload are not encrypted, only encoded with Base64URL. Base64URL is not encryption, it is an encoding that turns binary data into characters that are safe in a URL. Describing JWT as an “encrypted token” is wrong. A JWT is signed, not encrypted. Anyone who gets hold of the token can read its contents, but cannot change them without breaking the signature. If the contents must stay secret, there is a separate encrypted format called JWE.

The code below builds a JWT by hand, decodes it without the key and tries to verify a modified copy:

import base64, hmac, hashlib, json

def b64url(data):
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def b64url_decode(s):
    return base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))

secret = b"secret-key"
header = {"alg": "HS256", "typ": "JWT"}
payload = {"sub": "42", "role": "user", "iat": 1794873600, "exp": 1794874500}

h = b64url(json.dumps(header, separators=(",", ":")).encode())
p = b64url(json.dumps(payload, separators=(",", ":")).encode())
sig = b64url(hmac.new(secret, f"{h}.{p}".encode(), hashlib.sha256).digest())
token = f"{h}.{p}.{sig}"

# the payload can be read without the key
print(json.loads(b64url_decode(token.split(".")[1])))
# {'sub': '42', 'role': 'user', 'iat': 1794873600, 'exp': 1794874500}

def verify(tok):
    h, p, s = tok.split(".")
    expected = b64url(hmac.new(secret, f"{h}.{p}".encode(), hashlib.sha256).digest())
    return hmac.compare_digest(s, expected)

forged = b64url(json.dumps({**payload, "role": "admin"}, separators=(",", ":")).encode())
print(verify(token), verify(f"{h}.{forged}.{sig}"))  # True False

The payload with its role changed to admin fails verification with the old signature, since a valid signature needs the key. The payload, however, can be read by anyone, so no secret data goes into it. In a real project this is done not by hand but with a library that also checks exp and the algorithm.

HS256 signs and verifies with a single secret key. RS256 signs with a private key and verifies with a public key, so other services can verify tokens but cannot issue them. The verifying side must take the algorithm from its own configuration, not from the token’s header. Otherwise an unsigned token with "alg": "none" may be accepted, a vulnerability that has actually been seen in the past.

Expiry and refresh tokens

The biggest weakness of JWT is that it cannot be revoked. Since the server does not keep the token anywhere, a token with a valid signature and an unexpired exp is accepted. This holds even if the user logs out or the token is stolen.

The usual solution is two tokens:

  • Access Token: A short-lived JWT, for example 15 minutes. Sent with every API request, so a stolen one is useful only briefly.
  • Refresh Token: Long-lived, used only to get a new access token. The server records these, so they can be revoked.

On logout the refresh token is deleted, and the user is out of the system after at most one access token lifetime. If the refresh token is replaced with a new one on every use (rotation), reuse of an old one signals that it was stolen.

A blocklist of revoked tokens is also possible, but that means a store lookup on every request and partly gives back the “no server-side state” advantage of JWT.

Where is the token stored?

Any JavaScript on the page can read a token in localStorage, so an XSS hole steals it directly. A token in an HttpOnly cookie cannot be read from JavaScript, but since it is sent automatically it needs CSRF protection. Mobile apps keep the token in the operating system’s secure storage and send it with the Authorization: Bearer header.

13. CORS

Browsers enforce the Same-Origin Policy. JavaScript on a page can send a request to another origin but cannot read the response. An origin is the combination of scheme, domain and port. https://example.com and https://api.example.com are different origins, and so are http://example.com and https://example.com.

CORS (Cross-Origin Resource Sharing) is the server declaring, through headers, which origins may read its responses:

Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, DELETE
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Allow-Credentials: true

For a DELETE or a request with an Authorization header, the browser first sends an OPTIONS request (the preflight) and sends the real request only if the response allows it.

CORS is not a firewall. The browser enforces it. Someone sending the same request with curl or a Python script is not stopped by CORS. CORS only prevents another site from reading data through the user’s browser with that user’s session. The API’s real protection is still authentication and authorization. With cookie-bearing requests * cannot be used, the origin has to be named explicitly.

Interview questions

1. What happens when you type an address into a browser? The browser finds the IP address through DNS, checking caches first. It opens a TCP connection, runs the TLS handshake if it is HTTPS, and sends the HTTP request. While the HTML is processed, new requests are made for sub-resources. Common mistake: Skipping the DNS caches and the TLS step and saying “the request goes to the server”.

2. How does DNS resolution work? The client sends the question to a recursive resolver. If the answer is not cached, the resolver learns the TLD server’s address from a root server, the authoritative server’s address from the TLD server, and gets the answer from the authoritative server. The answer is cached for its TTL. Common mistake: Assuming every query goes to a root server.

3. What do idempotent and safe mean? How is POST different from PUT? A safe method does not change server state. An idempotent method leaves the same final state no matter how many times it is sent. PUT replaces the resource at a known address entirely and is idempotent. POST creates a new resource, and sending it twice can create two. Common mistake: Confusing idempotency with returning the same response. What matters is the final state on the server.

4. What is the difference between 401 and 403? 401 says the identity is not authenticated, the token is missing or invalid. 403 says the identity is known but lacks permission. Common mistake: Reading the name “Unauthorized” and treating 401 as a permission error.

5. What does it mean for REST to be stateless? Each request carries everything needed to process it, credentials included. The server keeps no client session context between requests. This lets requests be routed to any server. Common mistake: Describing stateless as the application storing no data at all.

6. What is the difference between a session and a JWT? With a session the data lives in the server’s store, the client holds only an ID, and revoking means deleting the record. With a JWT the data sits signed inside the token, no store is needed, but it cannot be revoked until it expires. That is why JWTs are kept short-lived and renewed with a refresh token. Common mistake: Claiming JWT is always more secure than sessions.

7. Is a JWT encrypted? What should not go in the payload? No, the header and payload are only Base64URL-encoded and anyone can read them. The signature only prevents tampering. Passwords and sensitive personal data do not go in the payload. Common mistake: Taking Base64 for encryption.

8. What do HttpOnly, Secure and SameSite do? What does CORS protect? HttpOnly hides the cookie from JavaScript, Secure sends it only over HTTPS, and SameSite limits sending it on cross-site requests, which makes CSRF harder. CORS decides whether the browser lets a page from another origin read the API’s response. Common mistake: Treating CORS as server-side access control. It has no effect on requests made outside a browser.
