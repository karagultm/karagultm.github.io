Networking 1: The OSI and TCP/IP Models, TCP vs UDP, QUIC

Programming 101, Part 11

This post is about how data sent by a program on one computer reaches a program on another. In between there are cables, wireless links, routers and packets that can get lost. Most of the time the data still arrives complete and in order.

The thing that makes this work is a protocol stack split into layers. Each layer deals with one problem and relies on the service of the layer below it.

Below I first cover the OSI and TCP/IP models and how data is wrapped as it moves through the layers. Then I go over the difference between TCP and UDP, where each one is used, and what QUIC changes. At the end there are common interview questions with short answers.

1. Why layers?

A browser requesting a page does not know whether the cable is copper or fiber. The Ethernet card does not know that the bytes it sends form an HTTP request. Each part does only its own job.

The benefit of this split is replaceability. Moving from a wired connection to Wi-Fi does not change the browser’s code. Writing a new application protocol does not require updating routers.

It works like a parcel service. The sender packs the box, the courier company routes it to a branch by address, the branch puts it on a truck. The sender does not care which truck is used, and the driver does not care what is in the box.

2. The OSI model: seven layers

The OSI (Open Systems Interconnection) Model is a conceptual model that describes network communication in seven layers. The internet does not actually run on OSI protocols, but the layers are used as a common vocabulary. Phrases like “an L4 load balancer” or “an L7 firewall” come from this numbering.

From the bottom up:

No Layer What it does Example protocol / device
1 Physical Turns bits into electrical, optical or radio signals Copper cable, fiber, hub, the radio part of Wi-Fi
2 Data Link Carries frames between devices on the same local network, uses MAC addresses Ethernet, Wi-Fi (802.11), switch
3 Network Finds a path between different networks, uses IP addresses IP, ICMP, router
4 Transport End-to-end delivery between two programs, port numbers TCP, UDP
5 Session Opens, maintains and closes a communication session RPC mechanisms, session management
6 Presentation The format of the data: encoding, compression, encryption UTF-8, JPEG, the encryption part of TLS
7 Application Protocols the application uses directly HTTP, DNS, SMTP, SSH

A few details are useful in interviews:

  • A switch works at layer 2 and forwards frames by MAC address. A router works at layer 3 and moves packets to other networks by IP address. A hub copies the incoming signal to every port without reading any address, so it is layer 1.
  • A MAC Address only has meaning on the local network. Every time a packet passes a router, the frame is rebuilt and the MAC addresses change. IP addresses stay the same along the way (unless NAT is involved).
  • Layers 5 and 6 have no clean real-world counterpart. Protocols like TLS are open to debate about which layer they belong to. Saying so in an interview is not a wrong answer, it is an accurate one.

Rather than memorising the layers with a mnemonic, it sticks better to remember which address each layer uses: MAC at 2, IP at 3, port at 4.

3. The TCP/IP model and how it maps to OSI

The model the internet actually uses is the TCP/IP Model. It has four layers:

TCP/IP layer Matching OSI layers Example
Link 1 Physical, 2 Data Link Ethernet, Wi-Fi
Internet 3 Network IP, ICMP
Transport 4 Transport TCP, UDP
Application 5 Session, 6 Presentation, 7 Application HTTP, DNS, TLS

The core difference: OSI was designed as a model first, with protocols meant to follow. In TCP/IP the protocols existed first and the model was written to describe them. The top three OSI layers collapse into a single application layer in TCP/IP, because in practice the application or its library does that work.

Some textbooks split the Link layer in two and teach a five-layer model. In an interview it is enough to say which model you mean.

4. Encapsulation

As data moves down the stack, each layer adds its own header in front of it. This is called Encapsulation. On the receiving side each layer reads and strips its own header and passes the rest up. That is Decapsulation.

It is like putting an envelope inside another envelope. A letter goes into an envelope with the recipient’s name on it. That envelope goes into a bag for intercity transport, and the bag only shows the city. At each stage only the outermost label is read.

The data has a different name at each layer:

Layer Name of the data What the added header contains
Application Data (message) Application information such as HTTP headers
Transport Segment (TCP) / Datagram (UDP) Source and destination port, sequence number
Network Packet Source and destination IP, TTL
Data Link Frame Source and destination MAC, error check at the end (FCS)
Physical Bits No header, just signal

Headers have a cost. On Ethernet the largest payload a frame can carry (the MTU) is typically 1500 bytes. Of that, 20 bytes go to the IPv4 header and 20 bytes to the TCP header. Without options, 1460 bytes are left for application data in a TCP segment. This value is called the MSS (Maximum Segment Size).

5. IP addresses and ports

An IP Address identifies a network interface on the internet. An IPv4 address is 32 bits (192.168.1.10), which allows about 4.3 billion addresses. Because that is not enough, devices on home networks share a single public address through NAT. An IPv6 address is 128 bits (2001:db8::1).

A Port identifies which program on that machine receives the data. It is a 16-bit number, from 0 to 65535. Ports 0–1023 are the well-known ports: HTTP 80, HTTPS 443, DNS 53, SSH 22.

An apartment building is a good fit here. The IP address is the building’s street address, the port is the flat number. The mail carrier finds the building by IP, and the port says which door the letter goes to.

A TCP connection is identified by four values: source IP, source port, destination IP, destination port. Thousands of clients can connect to port 443 on the same server at once, because each one has a different source IP or source port. On Linux, open connections can be listed with:

ss -tn
# State  Local Address:Port    Peer Address:Port
# ESTAB  192.168.1.10:52344    203.0.113.5:443

52344 is a temporary port the operating system assigned on the client side (an ephemeral port).

6. TCP: setting up a connection

TCP (Transmission Control Protocol) is a transport protocol that provides a reliable, ordered byte stream between two programs. It sets up a connection before sending data. This setup is called the 3-Way Handshake:

  1. The client sends SYN with its initial sequence number: seq = x.
  2. The server replies with SYN-ACK: its own initial number seq = y, and ack = x + 1 to confirm it received the client’s SYN.
  3. The client sends ACK: ack = y + 1. The connection is established.

It resembles a phone call. “Hello, can you hear me?”, “I can, can you hear me?”, “Yes.” After three messages both sides know the other one can both hear and speak.

Why three and not two? With two steps, the server cannot be sure that its own number reached the client. The third message proves that both directions work. These steps also synchronise the sequence numbers of both sides.

Initial sequence numbers are chosen at random. If they were fixed, an outsider could guess the number and inject forged segments into the connection.

The handshake costs one RTT (Round-Trip Time). If the RTT to a server is around 40 ms, the first HTTP request can leave no earlier than 40 ms after the start. With HTTPS a TLS handshake is added on top. With TLS 1.3 that is one more RTT, so two RTTs in total before the request is sent.

7. TCP: how reliability works

IP can lose packets, duplicate them or deliver them out of order. TCP builds a reliable stream on top of that with three mechanisms.

Sequence numbers

TCP numbers every byte it sends. The common explanation that “TCP numbers packets 1, 2, 3” is wrong. A segment’s sequence number is the position of its first byte in the stream. If a 500-byte segment starts at 1000, the next segment starts at 1500.

The receiver keeps out-of-order segments in a buffer and hands only the contiguous part to the application.

ACKs

The receiver writes the number of the next byte it expects into the ack field. ack = 1500 means “I have everything up to 1499”. This works as a cumulative ACK: one ACK confirms everything before it. The sender does not wait for an ACK per segment. It sends several segments back to back and collects the acknowledgements later.

Retransmission

Loss is detected in two ways:

  • Timeout: The sender starts a timer for each segment (the RTO, Retransmission Timeout). If no ACK arrives before it expires, the segment is sent again. The RTO is not fixed, it is adjusted based on the measured RTT.
  • Fast Retransmit: When the receiver notices a missing segment, it keeps sending the same ACK. After three duplicate ACKs the sender resends the missing segment without waiting for the timeout.

Every segment also has a checksum. A segment corrupted on the way is dropped and treated as lost.

One limit is worth stating: TCP does not guarantee that data is never lost. If the cable is cut or the other side shuts down, the data does not arrive. What TCP guarantees is that the data that does arrive is complete and in order, and that a failure to deliver is reported as an error.

8. Flow control and congestion control

These two are often confused. Both limit how fast the sender sends, but they protect different things.

Flow Control protects the receiver. With every ACK the receiver reports how much free buffer space it has. This value is the receive window (rwnd). The sender keeps the amount of unacknowledged data below this window. If a slow-reading application fills its buffer, the window drops to zero and the sender waits.

Congestion Control protects the network. If a router along the path has a full queue and starts dropping packets, the problem is not at the receiver but on the path. For this the sender keeps its own congestion window (cwnd):

  • Slow Start: The connection starts with a small window. It roughly doubles every RTT. The name is misleading, the growth is exponential.
  • Congestion Avoidance: After a threshold, the window grows only a little each RTT.
  • When loss is detected, the window shrinks. In the classic algorithms it is halved.

The amount of data the sender can have in flight is the smaller of the two windows: min(rwnd, cwnd).

Think of filling a glass from a tap. Flow control looks at how much room is left in the glass. Congestion control looks at the pressure in the pipes.

The sentence “TCP doesn’t clog the network thanks to flow control” is common, but it mixes up the two. The mechanism that protects the network is congestion control, not flow control.

9. TCP: closing a connection

A TCP connection is two-way, and each direction is closed separately:

  1. The side that wants to close sends FIN: “I have nothing more to send”.
  2. The other side confirms with ACK. At this point it can still send data.
  3. When the other side is done, it sends its own FIN.
  4. The first side confirms with ACK.

That is why closing is often called a 4-way handshake. If the other side combines its ACK and FIN in one segment, it can finish in three messages.

The side that started the close waits in TIME_WAIT for a while after the last ACK. The wait is twice the maximum time a segment can live in the network (MSL). It exists so the last ACK can be resent if it is lost, and so delayed segments from the old connection do not leak into a new one. On a server that opens and closes many short connections, thousands of TIME_WAIT entries are normal.

There is also the abrupt way: an RST segment cuts the connection immediately, without a handshake. Trying to connect to a closed port also gets an RST in return.

10. UDP

UDP (User Datagram Protocol) is a transport protocol that does nothing beyond adding port numbers and a checksum. It does not set up a connection, keep order or resend what is lost. Its header is 8 bytes: source port, destination port, length, checksum.

UDP also preserves message boundaries. If a 100-byte datagram is sent, the receiver gets a 100-byte datagram or nothing at all. TCP has no concept of messages, only a byte stream. Two send calls of 100 and 200 bytes may be read as a single 300-byte chunk on the other side. On top of TCP, the application itself has to mark where messages begin and end.

The difference shows up in Python socket code:

import socket

# TCP: connect first, then a byte stream
tcp = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
tcp.connect(("example.com", 80))       # 3-way handshake happens here
tcp.sendall(b"GET / HTTP/1.1\r\nHost: example.com\r\n\r\n")
print(tcp.recv(100))
tcp.close()                            # sends FIN

# UDP: no connection, each sendto is a separate datagram
udp = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
udp.sendto(b"hello", ("127.0.0.1", 9999))  # no way to know if it arrived
udp.close()

In TCP, connect() puts three segments on the wire. In UDP, sendto() returns without error even if nobody is listening on the other side.

TCP vs UDP

Property TCP UDP
Connection Yes, 3-way handshake No
Reliability Loss is detected and resent No retransmission
Ordering Yes No, in arrival order
Data model Byte stream Separate messages (datagrams)
Header 20–60 bytes 8 bytes
Error checking Checksum Checksum (optional in IPv4, mandatory in IPv6)
Flow and congestion control Yes No, the application does it if needed
Per-connection state Server keeps state per connection None

Two mistakes are common in tables like this. The TCP header is not a fixed 20 bytes, it starts at 20 and grows up to 60 with options. UDP does have error checking, that is what the checksum field is for.

“UDP is fast” also needs care. UDP packets do not travel faster on the wire than TCP packets. The gain comes from having no handshake, no waiting for acknowledgements, and no stalling of later data because one packet was lost.

11. When to use which

The deciding question is: is late data still useful?

Video calls

In a call, a piece of audio from half a second ago is no longer useful. While TCP waits to resend it, it also holds back everything behind it, and the picture freezes. That is why real-time audio and video go over UDP. A lost frame is skipped, the picture glitches for a moment, but the stream keeps going. WebRTC, the real-time communication standard in browsers, also carries media over UDP. On networks where UDP is blocked it can fall back to TCP, but latency goes up.

Watching recorded video is different. The player buffers a few seconds ahead, so there is time to resend a late packet. Completeness matters here, and the video comes over HTTP. The claim “recorded video uses TCP” is no longer always true, since with HTTP/3 recorded video can also travel over QUIC, which runs on UDP. The real difference is not the transport protocol but whether late data can be tolerated.

DNS

A DNS query and its answer usually fit in one packet each. With UDP the job is done in a single round trip, with no connection to set up. If no answer comes, the client simply repeats the query.

Describing DNS as UDP-only is incomplete. DNS uses port 53 for both UDP and TCP. If the answer is too large for a UDP packet, the server marks it as truncated (the TC flag) and the client repeats the same query over TCP. Zone transfers between servers also use TCP. Encrypted DNS (DNS over TLS, DNS over HTTPS) runs over TCP or QUIC.

Games

In a multiplayer game, player positions are sent dozens of times per second. If a position from 50 ms ago is lost, resending it makes no sense, a newer one is already on the way. So position and movement updates go over UDP.

Not all game data is like that. An item purchase or a chat message must not be lost. Game engines either build their own acknowledgement and resend layer on top of UDP for such messages, or send them over a separate TCP connection. Choosing UDP does not mean giving up reliability. It means the application decides which data needs to be reliable.

12. QUIC and HTTP/3

QUIC is a reliable, encrypted transport protocol that runs over UDP. The IETF standardised it in 2021 as RFC 9000. HTTP/3 is the version of HTTP that runs over QUIC, published in 2022 as RFC 9114.

Why on top of UDP?

QUIC does most of what TCP does: handshake, sequence numbers, ACKs, retransmission, congestion control. There are two reasons it does this on top of UDP instead of as a new transport protocol.

First, firewalls, NAT devices and other middleboxes on the internet only recognise TCP and UDP. Packets sent with a new transport protocol number are mostly dropped along the way. Second, TCP lives in the operating system kernel, and changing it means updating the OS on every device. QUIC runs in user space, as a library inside the application, and is updated together with the application.

Head-of-line blocking

Head-of-Line Blocking is when a delay at the front holds back everything behind it. Like a supermarket checkout where one item’s barcode will not scan and the whole queue stops.

Each version of HTTP runs into this problem at a different layer:

  • HTTP/1.1: Requests on one connection are answered in order. A slow response holds back the ones behind it. Browsers work around this by opening around six parallel connections to the same server.
  • HTTP/2: Carries many requests as separate streams inside one TCP connection. That solves the blocking at the application layer. But TCP sees everything as one byte stream. If one segment is lost, TCP hands nothing behind it to the application until that segment is resent. Even if the loss belongs to a single image, every stream waits.
  • HTTP/3: QUIC knows about streams at the transport layer. If a packet belonging to one stream is lost, only that stream waits and the others keep going.

The difference shows on networks with high loss rates. Mobile connections and crowded Wi-Fi are the typical cases.

Faster setup and 0-RTT

QUIC folds TLS 1.3 into its own handshake. The transport connection and the encryption keys are set up in the same round trip:

Before the first request is sent
TCP + TLS 1.3 2 RTT
QUIC, first connection 1 RTT
QUIC, server seen before (0-RTT) 0 RTT

0-RTT means the client uses information saved from an earlier connection to send an encrypted request in its very first packet. The price is paid in security. 0-RTT data can be captured and sent to the server again in a replay attack. That is why 0-RTT should only be used for requests that are harmless to repeat, such as a GET that reads a page. A POST that transfers money is not sent as 0-RTT. 0-RTT also exists in TLS 1.3 and is not unique to QUIC. What QUIC adds is combining it with the transport setup.

Connection migration

A TCP connection is identified by the IP and port four-tuple, so when a phone moves from Wi-Fi to mobile data the IP changes and the connection breaks. QUIC connections are identified by a Connection ID. Even when the IP address changes, the connection continues with the same ID and a download resumes where it left off.

Current status

QUIC and HTTP/3 are standards, and all major browsers support them. In 2026 measurements, roughly 38–40 percent of websites offer HTTP/3. Its share of actual requests is lower. Depending on the measurement, around one fifth of web requests are carried over HTTP/3. The large remainder still goes over HTTP/2 and HTTP/1.1 on TCP.

There are several reasons for this. Some corporate networks block or throttle UDP on ports other than 53. A browser usually learns that a server supports HTTP/3 from the Alt-Svc header in a first response or from a DNS record, so the first connection is still made over TCP. Because QUIC runs in user space and encrypts every packet, it can use more server CPU than TCP. For these reasons every HTTP/3 client must be able to fall back to TCP if QUIC fails. TCP is not going away. QUIC is an option added next to it.

Interview questions

1. What are the layers of the OSI model? At which layer do switches and routers work? From the bottom: Physical, Data Link, Network, Transport, Session, Presentation, Application. A switch forwards by MAC address at layer 2, a router by IP address at layer 3. The TCP/IP model groups these into four layers: Link, Internet, Transport and Application. Common mistake: Assuming the MAC address stays the same as the packet travels across networks.

2. How does the TCP 3-way handshake work, and why three steps? The client sends SYN, the server SYN-ACK, the client ACK. Through these steps both sides exchange initial sequence numbers and confirm that both directions work. With two steps the server could not be sure its own SYN arrived. Common mistake: Describing the handshake as a mere “connection check” and skipping the sequence number exchange.

3. How does TCP achieve reliability? Every byte is numbered, and the receiver reports the next byte it expects in an ACK. If the ACK does not arrive in time, or three duplicate ACKs are seen, the segment is resent. A checksum catches corrupted segments, and sequence numbers fix ordering and duplicates. Common mistake: Calling the sequence number a packet counter. It is a byte position.

4. What is the difference between flow control and congestion control? Flow control protects the receiver’s buffer and follows the window the receiver advertises (rwnd). Congestion control protects the network, and the sender adjusts its own window (cwnd) based on loss and delay. The sender can keep the smaller of the two in flight. Common mistake: Treating them as the same mechanism.

5. What is the difference between TCP and UDP, and when do you pick each? TCP offers a connected, ordered, reliable byte stream. UDP carries connectionless datagrams with no ordering and no retransmission. If late data is useless (a live call, player positions in a game) UDP fits. If every byte must arrive (a file, a web page) TCP fits. Common mistake: Saying “UDP is unreliable, so no serious application uses it”.

6. Why does DNS use UDP? Does it always use UDP? A query and its answer usually fit in one packet, and setting up a connection would double the work. If the answer is too large, the server returns a truncated response and the client asks again over TCP. Zone transfers also use TCP. Common mistake: Saying “DNS only uses UDP port 53”.

7. What is TIME_WAIT and why does it exist? It is the state the closing side stays in for 2×MSL after the last ACK. It lets the last ACK be resent if it is lost, and keeps delayed segments from the old connection out of a new connection with the same four-tuple. Common mistake: Treating TIME_WAIT as an error or a sign of a leak.

8. Did HTTP/2 solve head-of-line blocking? What did QUIC change? HTTP/2 solved the application-level blocking with streams, but because it uses a single TCP connection, one lost segment stalls every stream. QUIC separates streams at the transport layer, so a loss only affects the stream it belongs to. It also folds TLS into the handshake and brings connection setup down to one RTT. Common mistake: Saying QUIC is unreliable because it runs over UDP.
